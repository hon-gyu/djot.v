## Statements

Names are suggestions.

1. **BA3, accumulation.**  A run of spec lines `s1 ... sk`, each complete
   on its line, then a document `ls` whose first line is not blank and
   not a spec:

   ```
   parse_lines (s1 :: ... :: sk :: ls)
   = decorate_head (merge ak (... (merge a1 []))) (parse_lines ls)
   ```

   Prove it by induction on the run, from `parse_lines_attr_done` and a
   lemma for a spec line arriving at `PPend`.  `attr_uniformity`
   becomes the case `k = 1`.

2. **BA2, continuation.**  A spec split over lines, every line after the
   first indented past the opener, parses as the same spec written on
   one line.  The cleanest form compares two documents:

   ```
   parse_lines (spec_lines ++ ls) = parse_lines (joined :: ls)
   ```

   where `joined` is the lines concatenated with a space, under the same
   side condition as 1.  Whether the join is exactly a space depends on
   how the machine treats a line break inside a value; check the
   quoted-value case in the probe before fixing the statement.

3. **BA2, the "must".**  If a continuation line is not indented, the
   spec fails and its lines become a paragraph
   (`block_attributes_multiline_unindented`).  State it for the
   two-line case at least.

## Pitfalls

- A blank line inside an unfinished spec: indented past the opener it is
  a continuation (fed to the machine, not recorded), otherwise it ends
  the spec.  djot.js records it; the comment on the `PAttr` arm says why
  we do not.
- `run_safe` and `pad_safe` in `ListUniformity.v` exclude an open spec
  at a line boundary.  Lemmas in this plan are about top level and need
  no such condition, but do not reuse list lemmas without checking it.
- A spec followed by a blank line is dropped; that is why `pend_ready`
  rejects a blank.
- `battrs` is a configuration switch; carry it as a hypothesis.
