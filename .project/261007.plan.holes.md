# Plan: holes (article template literals)

Source: Crichton and Krishnamurthi, "A Core Calculus for Documents"
(POPL 2024), section 3.2.3. No djot implementation has the construct,
so the discipline in [[extension-decisions]] applies rather than
[[project-engineering-lessons#Ask djot.js]].

## The idea

The paper's article template literal is an article literal with holes:
the template parts are text, a node whose children are a template, and
an interpolated expression. Djot is already the article literal, and
custom tags (`:kbd[...]`, `::: details`) already give any named node a
spelling with a text-mode body. What is missing is the hole.

````
Today I am going shopping for %{List.length items} things:

``` %
ul (List.map (fun i -> li [ p [ text i ] ]) items)
```
````

`%{e}` is an inline hole, a new node the parser builds. A code fence
whose info string is `%` is a block hole by convention only: the parser
builds the ordinary code block, and the consumer treats it as a hole
(D10). The parser records the expression as an opaque string.
What the expression language is, how a hole is evaluated, and whether
the result is a node, a list or an option are the consumer's, as a
custom tag's name is.

Templates without loops or bindings are the paper's "template literal"
level. `set`, `foreach` and `if` (template programs) are out of scope;
they belong in the host expression.

| this plan | djot, custom tags | `%{e}`, ```` ``` % ```` |

Only the hole half is taken from ppx_html. Its tag half would be a
second spelling of nodes djot already spells, and raw HTML stays out
([[beyond-djot]]). Scribble's `@` would claim every email address and
`@mention` in prose.

## Compatibility (discipline 4)

The inline half is non-conservative: every document with `%{` outside
verbatim contexts changes. The loud subset is `%` followed by an
attribute block (the fourth to sixth baseline rows), which today
attaches attributes to a word ending in `%`.

The block half changes nothing in the parser. Every djot parser reads a
```` ``` % ```` fence as the code block it is today, and only a
consumer that evaluates holes reads it differently.

Step 0 counts `%{` in the corpus.

## Decisions

### Made by a human (2026-10-07)

**D1. Spelling.** `%{e}` inline. JSX's `<...>` and Scribble's `@` were
rejected above. The cheaper alternative `` %`e` ``, a sigil on djot's
verbatim span as `` $`x` `` is for math, was considered and declined:
`%{e}` reads better, and the cost is a scanner candidate of dollar
math's size (section "Cost").

**D2. The closer is found by brace depth.** `{` inside the hole raises
the depth and `}` lowers it; the `}` that returns the depth to zero
closes. So `%{ {r with x = 1} }` is one hole. A brace that should not
count is escaped (D7). Lexing the host language's strings was rejected:
it would tie the parser to one expression language.

**D3. `%{` wins over an attribute block.** With the setting on,
`a %{.c} b` is a hole holding `.c`, not a span around `%`. Attributes
on a word ending in `%` need the word in brackets: `[50%]{.c}`.

**D4. An inline hole may span lines, within one block.** The block
stage runs first and never looks inside a hole, so:

- a blank line ends the paragraph, and a hole that has not closed by
  then is text;
- a line the profile lets interrupt a paragraph (`bmarker_interrupts`,
  for example a list marker) starts its block, and cuts the hole the
  same way;
- container prefixes (`> `, list indentation) are removed before the
  scanner sees the payload, and so, per the baseline, are a continuation
  line's leading spaces. A whitespace-sensitive expression belongs in a
  block hole.

Table cells and captions are one line, so a hole there is too.

**D5. One kind in v1; `%*{` and `%?{` reserved.** ppx_html's three
sigils exist because its expansion must know, without type inference,
whether to insert `[e]`, `e` or `Option.to_list e`. Here the consumer
takes one value type, a fragment (the paper's fragment strategy), and
can offer `of_list` and `of_option`. The ppx_html spellings themselves
are not available: `*{` would break `*a*{.c}`, attributes on strong.
If kinds are added later they are `%*{e}` and `%?{e}`, and
```` ``` %* ````, ```` ``` %? ````. In v1 all four stay what the
baseline says.

**D9. A hole is always closed, and a closed hole wins over what it
overlaps.** A `%{` with no closing `}` before the end of its block is
text, and the source after it reads as if the `%` had been escaped.
The alternative, an unclosed hole that runs to the end of the
paragraph as an unclosed verbatim span does, was considered and
declined: it would have made the overlap question disappear and saved
the second reading, but a hole is something the author closes.

So the scanner carries a candidate and the ordinary reading of the
same bytes, as `IDollarMath` does (`InlineScan.v`). Winning is not a
separate rule but how the candidate closes: the hole is emitted onto
the state from before `%{`, and the ordinary reading is dropped,
including anything it closed. `*a %{b* c}` is the text `*a `, then a
hole holding `b* c`; the `*` is still open in the state before `%{` and
becomes text at the end of the paragraph. Letting the strong close and
the hole die instead would be the extra work, since the candidate
would have to watch the ordinary reading. Dollar math's rule 10 is the
same outcome, and pandoc and remark-math read `*a $b* c$` this way.

With verbatim, whichever opens first wins, with no rule between them:
a verbatim span commits at its backtick, and a hole drops the other
reading when it closes.

| input | result |
| --- | --- |
| `` `a %{b}` `` | code `a %{b}` |
| `` `a %{b` c} `` | code `a %{b`, then text ` c}` |
| ``%{ f "`" }`` | a hole holding `` f "`" `` |
| ``%{ a `b } c` `` | a hole holding ``a `b``, text ` c`, then a verbatim span from the last backtick |
| ``%{ a `b`` | text `%{ a `, then code `b` |

The last row is why the ordinary reading has to be stepped on every
byte inside the hole: it is the result when no closer arrives, and it
may hold a verbatim span.

**D10. The block hole is a convention on code blocks, not a node.** A
code block whose language is exactly `%` is a block hole to a consumer
that evaluates holes; the parser, the renderer and the HTML output
treat it as the code block it is. The consumer's pass is local and one
to one:

```ocaml
let rec block = function
  | CodeBlock ("%", s) -> eval_blocks s
  | b -> map_children block b
```

A fence already keeps blank lines and indentation, a payload holding a
fence uses a longer one, and attributes before the fence stay on the
block. The costs: the two holes have different shapes in the AST, and
such a consumer cannot show code whose language is `%`. No language
after the sigil in v1: ```` ``` %ocaml ```` is an ordinary code block
to the consumer too.

### Proposed by the agent, to review

**D6. Empty holes are text.** `%{}` and `%{  }` are text, as dollar
math's content must be nonempty. Reopen if a consumer wants an empty
hole as a placeholder.

**D7. Escapes inside a hole.** `\{`, `\}` and `\\` give `{`, `}` and
`\` and do not count toward the depth. A backslash before any other
byte is kept with it, so OCaml's `"\n"` reaches the consumer as
written. A string literal holding an unbalanced brace is written with
the escape: `%{ print_string "\}" }` hands over `print_string "}"`.

**D8. Where `%{` is not an opener.** An escaped `%` (`\%{x}`), and
inside anything read verbatim: code spans, math, raw inline, autolinks,
link destinations, attribute blocks, and another hole's payload. This
is dollar math's rule 11.

**D11. AST and HTML.** `Hole (s : string)` in inlines, the payload
after escape decoding. HTML renders an unevaluated hole visibly rather
than dropping it: `<code data-hole="">s</code>`. Whether to give
`Hole` a kind field now, so D5's later kinds add no constructor, is
open; with one kind it would be a one-constructor type.

## The canonical spelling

A hole renders as `%{`, the payload with every `{`, `}` and `\` that
D7's decoder would read differently escaped, then `}`. Escaping every
brace is simpler than tracking balance and costs nothing in the
roundtrip; whether it counts as a redundant escape under
[[261007.plan.irredundant-escapes]] is a question for that plan, which
would then want balanced braces bare.

Text needs one new escape. `%` is not in `InlineView.needs_escape`
today, and the canonical spelling of a braced delimiter starts with
`{`, so the text `a %` followed by emphasis renders as `a %{_x_}`,
which is a hole with the setting on. With the setting on, `%` directly
before a rendered `{` is escaped.

The block hole needs nothing: it is a code block (D10).

## Linear time

Letting a closed hole win (D9) is O(1): the ordinary reading is
dropped, nothing is read again. Inside an open hole each byte is
stepped twice, once by the hole and once by the ordinary reading.

The risk is nesting. The ordinary reading treats a later `%{` as a new
candidate with its own ordinary reading. Built as `IDollarMath` is, the
state is a chain `H1{ sh1 = H2{ sh2 = H3{ ... } } }` and each byte steps
every link, so `%{` repeated n times with no closer is Θ(n²). Dollar
math is bounded because its content holds no unescaped `$`, so at most
two candidates are live; a hole may hold `%{`.
`iscan_str_no_reread` would still hold for the chain, since nothing is
read again, which is the gap [[no-backtracking]] describes between that
theorem and linear time.

Two facts collapse the chain. Both readings count the same braces
under the same escapes, so if H2 opens inside H1:

1. H2 closes before H1, since H1's depth stays at least one above
   H2's from H2's opener on.
2. If H2 never closes, neither does H1, for the same reason.

So the open holes are a bracket stack. The state keeps one shared depth
counter, a stack of frames (where the `%{` started, the depth there,
and the state before it), and one ordinary reading, the innermost. A
byte costs one step of that reading and an O(1) depth update; a `}`
that returns the depth to a frame's level pops it. Payloads are source
slices, so open holes do not each copy the same bytes. The
well-formedness invariant gains the frame stack: depths strictly
increasing, the counter at least the top frame's.

This is a different state shape from `IDollarMath`, so its proofs are
not a case-by-case copy of dollar math's.

## Cost

Measured against dollar math, whose main commit `3f558aa` was
+764 / -118 lines over 10 files (`InlineScan.v` 216, `Wf.v` 198,
`InlineInvert.v` 155, `InlineSpans.v` 132, `InlineLocated.v` 99).

Same as dollar math:

- one setting with its `with_` function, isolation lemma and
  `dev/check/Capabilities.v` row;
- a candidate carrying the ordinary reading of the same bytes, as
  `IAttr` and `IDollarMath` do;
- the proofs that case on scanner states: well-formedness, no-reread,
  locations, inversion, span theorems.

More than dollar math:

- **A new node.** Dollar math produced the existing `Math` node and the
  roundtrip was untouched. `Hole` goes through `Ast.v`, `Render.v`,
  `Html.v`, `Readable.v`, `Document.v`, the inversion lemmas and the
  OCaml and Python bindings.
- **The frame stack and depth counter** of the previous section, and
  their invariant in `Wf.v`.
- **Stacking on `IAttr`.** The ordinary reading sees the `{` of `%{` as
  a possible attribute block, so an attribute candidate lives inside
  the hole's ordinary reading. It fails within a few bytes on most
  payloads, but it is a case dollar math never had.
- **The `%` escape** in the renderer and its obligation in
  `InlineView.v`.

Less than dollar math: one inline spelling instead of three, no display
form across lines, and no block half at all (D10).

  expression evaluator and produces the article.

  and is the costliest of the three positions.
- Template programs: `set`, `foreach`, `if`.
