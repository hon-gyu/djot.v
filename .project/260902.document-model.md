# What a document is, and the API that follows

Brainstorm response: incremental block splicing,
generated blocks (TOC), a notes directory as a site, wikilinks and
rename.

Every claim marked **[probed]** was run against the current build; the
scratch files are throwaway and not kept. Everything else is a proposal.

## The one rule the four use cases share

All four are about *identity under change*: name a block and replace it,
name a heading and link to it, name a note and rename it. So the design
question is not "what is a document" first, it is **where does a name's
referent come from**.

There are three answers available and only one of them survives.

| identity | stable under a local edit | in the source | usable across files |
| --- | --- | --- | --- |
| position in the list | no | no | no |
| source span | no | is the source | no |
| a unique explicit `{#id}` | yes | yes | yes |

`Roundtrip.block_replace` already notes that its own statement "needs no
address": splitting the list is what picks the block. That is right for a
locality theorem and wrong for an API, because the caller has to produce
the split, and "the block I mean" has to survive the last edit.

**The rule.** A name whose referent depends on the rest of the document
cannot have an unconditional locality theorem. Its dependency has to be
named as a hypothesis, just as `reparse_only_new` names equality of the
parser state. Stable addressing avoids that dependency: it uses explicit
ids and admits the operation only when those ids are unique.

**[probed] djot's auto-identifiers break the rule, today.**

```
ids "# N"       = ["N"]
ids "# N\n\n# N" = ["N"; "N-1"]
```

Inserting the second example's first heading before the old `# N`
renames that old heading from `N` to `N-1`. A link spelled `[](#N)`
silently retargets, although the old heading did not change.
`Document.v` computes this deliberately (djot.js
`getUniqueIdentifier`) and it is the only nonlocal thing in the
pipeline.

The same rule kills the wikilink convention where `[[note]]` resolves to
the shortest unique suffix: adding an unrelated note can make a third
note's link ambiguous. Prefer exact paths, or explicit ids, in both
layers. Auto-identifiers stay -- they are djot -- but nothing we build
may *address* through them. Duplicate explicit ids remain parseable
Djot, but make a document ineligible for id-addressed editing: choosing
the first occurrence would make inserting a duplicate silently retarget
the next replacement.

## The model

A document is not a tree. On the canonical fragment, it is **a block
list and its canonical source rendering in bijection, plus a derived
rendering view**. `doc_pass` may restructure visible blocks and move
footnote definitions into a side table, so that view is not editable
storage. That is what the repo already is, and the three things it
separates are the three the API needs to keep apart:

```
list cblock  --  cb_lines -->  source lines        the editing unit
             <-- parse ----
      |
      |  doc_pass                                  ids, sections, notes, refs
      v
    doc                                            the rendering unit
      |
      |  render_page (needs an env for links)
      v
    html                                           the output unit
```

Three consequences worth stating out loud, because each one is a design
decision the code has already half-made.

**The editing unit is `list cblock`, not `blocks` and not `string`.**
`cblock` is the type where both projections exist (`cb_lines` and
`cb_ast`) and `render_cb_lines` says they agree. An editor that holds
`list cblock` gets `block_replace` for free and never reparses. An editor
that holds arbitrary text gets `Uniformity.reparse_only_new`, which needs
the state hypothesis. The SSG case is the first one; the second is a text
editor's problem and should not shape the API.

**[probed] `blocks` is not a document.** `doc_pass` is idempotent on the
block tree and on `doc_references`, and is *not* idempotent on
`doc_footnotes`: the pass removes footnote-definition blocks, so a second
pass over `doc_blocks` returns an empty note map.

```
doc_footnotes (D src)                        = [("a", ...)]
doc_footnotes (doc_pass (doc_blocks (D src))) = []
```

So `doc_blocks` does not determine the document, and no operation may
take a `doc` apart and put it back together through its block list.
`cblock` has no footnote-definition constructor either, so today the
canonical fragment simply excludes them; when it stops excluding them
this is the trap.

**Positions stay out of the AST.** `pos` exists and is `NoPos`
everywhere. Populating it would make `roundtrip_blocks` false as an
equality (a block rendered alone starts at line 1), and it would make
`cb_ast` depend on where a block sits in the list, which is the
non-injectivity the engineering-lessons file names as the tell for a
non-canonical constructor. Spans belong in an editor's side table keyed
by id, not in the tree.

## The API, in cost order

### L0. Addressing: the one blocker

Everything else needs "the block named `i`", and **the canonical fragment
cannot express a named block**. `cblock` has ten constructors and none
carries an attribute; every `cb_ast` is `mk`-wrapped, so `Node NoPos []`.

The minimal extension is one constructor:

```coq
| CId (i : string) (inner : cblock)
cb_lines (CId i cb) = ("{#" ++ i ++ "}") :: cb_lines cb
cb_ast   (CId i cb) = add_attr [("id", i)] (cb_ast cb)
```

Only the id, not the full `{#id .cls k=v}`: canonical means one spelling
per value, and full attributes drag in the class-merge and
insertion-order rules `Ast.v` documents. Widening later is a separate
step.

There are two scopes, deliberately not collapsed into one operation.
`top_level_ids` drives block replacement and matches `block_replace`'s
`pre ++ block :: post` boundary. `all_explicit_ids` descends through
containers and drives page-wide uniqueness and link checks. Recursive
replacement needs a structural path and is a later API.

Parsing accepts duplicate explicit ids. Addressed operations require:

```coq
explicit_ids_unique : list cblock -> bool
```

to hold in the relevant scope. Auto-identifiers do not enter this
predicate, and a heading is stably addressable only when its id was
explicit in the source.

**[probed] The identity boundary is observable.** djot.js and the
current parser agree on all four cases, now pinned in
`ParserExamples.v` and `Document.v`:

- two separate `{#x}` specs are both retained; parsing does not enforce
  uniqueness;
- `{# }` is consumed but contributes no id;
- an id inside a quote decorates the nested block, so recursive link
  validation and top-level replacement really are different scopes;
- an explicit `x` makes a later `# x` use the automatic id `x-1`, so
  explicit and automatic ids share the rendered fragment namespace even
  though only the explicit one is an editing address.

**[probed] The parser already does the right thing, and the attribute
line is a separator.**

```
B "{#x}\n# H"           = [Node [("id","x")] (Heading 1 "H")]
B "- a\n\n{#x}\n- b"    = two tight BulletLists, the second carrying id x
B "- a\n\n- b"          = one loose BulletList
```

So `is_clist (CId _ _)` is `false` and `cb_pairs_ok` gets *weaker*: an
id'd list does not merge with its neighbour. Naming a block makes it
easier to place, not harder.

**[probed] The obstruction, and it is not where the constructor is.**
`Roundtrip.cb_ast_pristine : forall cb, pristine_node (cb_ast cb) = true`
is unconditional, and `Document.pristine_block` returns `false` for a
heading carrying an explicit id -- by design, because after the pass an
explicit id and an auto-assigned one are the same tree (both land on the
`Section`), so `undo_pass` cannot tell them apart. `CId` on a heading
makes `cb_ast_pristine` false, and that lemma feeds `roundtrip_doc`.

**The repair is to change the theorem, not the constructor.** State the
doc-level roundtrip as a commutation instead of an erasure:

```coq
Theorem roundtrip_doc_pass :
  forall cbs, cblocks_ok cbs = true ->
  parse_doc (render_djot (blocks_of_cblocks cbs)) = doc_pass (blocks_of_cblocks cbs).
Proof. intros cbs H. unfold parse_doc. f_equal. apply roundtrip_blocks, H. Qed.
```

**[probed]** That compiles as written, inside `Section WithTable`, and
`Check` reports both binders. It is strictly more useful than the present
form for an editor, because it recovers the *side tables* too, and it
does not mention `undo_pass`, so `pristine` stops gating anything above
the block layer. Keep `pass_erase` as the fact about `undo_pass` that it
is; stop routing the roundtrip through it.

Addressing must represent absence and ambiguity rather than silently
choosing the first occurrence:

```coq
find_top_ids :
  string -> list cblock -> list (list cblock * cblock * list cblock)
resolve_top_id :
  string -> list cblock -> result (list cblock * cblock * list cblock) address_error
```

Every returned split reconstructs the input; under
`explicit_ids_unique`, a present id resolves exactly once.
`replace_at_id i new_body` preserves the `CId i` wrapper itself, so an
edit cannot erase the identity by which the next edit will find it. It
inherits `block_replace` by rewriting with the resolved split.

### L1. Generated blocks: the TOC

A generated block is a *section of a projection*. Give it a view:

```coq
Record derived (V : Type) := {
  d_id   : string;
  d_view : list cblock -> V;      (* headings, for a TOC *)
  d_make : V -> cblock }.

Definition refresh D cbs := replace_at_id (d_id D) (d_make D (d_view D cbs)) cbs.
```

Here `replace_at_id` replaces the body while retaining the named
wrapper. If the id is missing or ambiguous, refresh returns that error;
it does not turn a partial lookup into a build result.

The property that makes a build a function rather than an iteration is
one-step convergence:

```coq
Theorem refresh_stable :
  d_view D (refresh D cbs) = d_view D cbs ->
  refresh D (refresh D cbs) = refresh D cbs.
```

The hypothesis is the whole content, it is decidable by running the view
once, and it is *false* in a case worth naming: if the generated block
contains a heading, installing it can move an auto-identifier and change
the view. This is the document-level echo of `reparse_only_new`'s state
hypothesis, and it should get the same treatment -- return the check,
never assume it.

The efficiency claim the brainstorm wants falls out of `block_replace`:
the untouched blocks are named on the right-hand side through the same
`map cb_ast` they had before, so they are shared subterms and nothing
reparses. The change-detection granularity is `d_view`: recompute only
when the view moves.

### L2. A directory of notes

```coq
Definition site  := list (path * list cblock).
Definition summ  := ...             (* title, ids, outgoing links *)
Definition env   := list (path * summ).
route       : path -> url
render_page : env -> path -> list cblock -> html
```

The load-bearing decision is that `render_page` reads other notes **only
through `env`**. Everything an SSG wants follows from that factorization
and is cheap once it holds; nothing follows without it.

- **Route injectivity.** `route` must be injective on `dom site`, and it
  is decidable. This is exactly where the `_index` rule goes wrong:
  `a/_index.dj` and `a.dj` both want `/a/`. State the rule *with* the
  sibling exclusion or the site silently loses a page. This is the first
  theorem to write, because it is the one a real tree violates.
- **Build locality.** `summ d = summ d' -> build (site[p := d']) =
  (build site)[route p := render_page env p d']`. Same shape as
  `parse_span`: one summand per region, and the others are shared
  subterms. The consequence to say out loud is conditional: an edit that
  preserves the note's summary cannot break another note's links.
  Editing its title, ids or outgoing links changes `summ` and may move
  `env`, just as creating, deleting or renaming a note does.
- **Link closure.** `links_closed env`, decidable, is "no broken links".

### L3. Rename

A correct rename is a commuting square, which is the right definition
because it says what "correct" means without enumerating cases:

```coq
Theorem rename_correct :
  q \notin dom site ->
  build (rename p q site) = map_urls (route p) (route q) (build site).
```

The efficiency statement is separate and is what an implementation runs:
the rename must rewrite `{p} \cup backlinks env p` and **need touch
nothing else**, where `backlinks` is computable from `env` alone. That
is a corollary of build locality, not a new induction.

The precondition `q \notin dom site` is not bureaucratic: without it the
square is false, because two notes collapse to one URL. It is the same
condition as route injectivity, one edit later.

## What to do first

In cost order, and each one is worth landing alone.

1. `roundtrip_doc_pass` -- land it next to `roundtrip_doc` and stop
   treating `pass_erase` as the route above the block layer.
2. **Done:** probe duplicate, consecutive, nested, empty and invalid
   explicit ids; define the top-level and recursive identity scopes and
   their uniqueness contract above.
3. **Done.** `CId` is in `cblock`, `roundtrip_blocks` covers it, and
   `Generate.v` enumerates one named copy of every block (depth counts
   262/3112/35938 to 278/3470/41186, all matching djot.js).
   `theories/Address.v` holds the addressing API: `top_level_ids` and
   `page_ids` for the two scopes, `find_top_ids` returning splits rather
   than an index, `resolve_top_id` reporting `AddrMissing` and
   `AddrAmbiguous n`, and `replace_at_id` rebuilding the wrapper so an
   edit does not spend the address it used (`replace_at_id_ids`).
   `replace_at_id_parse` is `block_replace` at an address.

   Three of the standing quantifiers needed *repairs*, not arms, and the
   prediction that they would not is the thing to read here.

   - `render_cb_lines`. The renderer had no node level at all:
     `render_blocks_lines` was `map (render_block_lines o node_contents)`,
     so attributes were dropped everywhere. It now goes through
     `render_node_lines`, which prefixes `id_spec_lines` -- the `id` key
     and nothing else, since a div's class is part of its fence. The
     statement moved with it.
   - `cb_pair_ok`. A wrapper is a line in *front* of its block, so "is
     this a list?" splits in two: `ends_clist` / `ends_ctable` of the
     first argument, `is_clist` / `closes_table` of the second. A named
     list still merges into the next list, and an unnamed one no longer
     merges into a named one. `is_ctable` had no other user and is gone.
   - `cdef_head_ok`. `Ast.def_split` drops a term paragraph's attributes
     (djot.js does too, and `Ast.v` says so), so a named head cannot
     round-trip; a definition item's first block may not be named, and
     `def_head_ok` asks the same of the AST side.

   The parse side is one theorem, `Uniformity.attr_uniformity`: a
   complete spec line resolves against the next line and its attributes
   ride on whatever the run emits next. Its side condition is that the
   next line is neither blank nor another spec, which is
   `Roundtrip.cb_lines_first_ready` for every canonical block -- and the
   list arm of that is `OrderedList.ck_lines_first_ready`, since a
   list's first line is a marker line and nothing about `cb_ok` says so.
4. **Done.** `refresh_stable` is in `Address.v`, over a `derived V`
   record, and it rests on `replace_at_id_idem`: writing the same body
   twice is writing it once, because the wrapper leaves the address
   where the first edit found it. The counterexample is
   `refresh_not_stable`, a generated block holding a heading: installing
   it takes the automatic id `H`, the document's own heading becomes
   `H-1`, the view moves, and a second refresh writes a different block.
   `refresh_converges` is the same view with a block that generates no
   heading, discharged through the theorem rather than by computation.
5. The site layer, starting with route injectivity, because it is the
   only one of the four that a real notes tree already violates.

Steps 4 and 5 do not depend on each other. Step 3 depends on 1 and 2,
and everything above the block layer depends on 3. Only step 5 is left.

## What this does not settle

Whether `cblock` should grow footnote definitions and definition lists
before or after `CId`; the note-map idempotence result above says the
footnote case has a trap in it and deserves its own note. And whether
`summ` is a fixed record or a parameter -- the parameter version is the
one the engineering-lessons file would ask for, and the question is
whether it can stay implicit.
