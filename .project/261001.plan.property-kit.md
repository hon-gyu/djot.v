# Plan: property checks for other implementations

## Goal

Someone writing a djot parser, an extension or a dialect can run their
implementation against the properties this project proves, and get a
yes or no per property with a failing input when the answer is no.

The properties come from two sources:

- djot's design goals, as this project's README states them: container
  uniformity, safe hard-wrapping, local interpretation, no dependence
  on later lines, block structure before inline;
- the rules of the djot syntax reference,
  <https://github.com/jgm/djot/blob/main/doc/syntax.md>.  Each check
  names the section of the reference it comes from and quotes the
  sentence, so a user can run the rules they care about and a dialect
  can name the rules it changes.

## Shape

There are three kinds of check.  They differ in where the expected
answer comes from, and so in what they can say about a dialect.

1. **Relational.**  Run the parser on two related inputs and compare
   the two outputs.  No expected output is needed, so the check applies
   to a dialect whose output we cannot predict.  The design properties
   are all of this kind.
2. **Rule.**  One input from a generated family, and a feature of the
   output that the rule itself names: `###` then whitespace is a level 3
   heading, a row with three bars between its ends has four cells, a
   blank line between items makes the list loose.  The expected answer
   comes from the sentence in the reference, not from this parser.
3. **Example.**  One input and its pinned output.  The reference's own
   examples are the cases.  This is a conformance test for djot and says
   nothing useful about a dialect that changes the rule.

Each relational or rule check is three parts:

1. **Cases**: inputs, generated in Gallina and filtered by the theorem's
   own side conditions.
2. **Transformation**: the second input, built from the first
   (relational checks only).
3. **Relation**: a boolean on the outputs.

The relational checks:

| Property | Input A | Input B | Relation |
| --- | --- | --- | --- |
| Quote uniformity | `L` | each line prefixed `> ` | B is A inside one quote |
| Div uniformity | `L` | `L` between `:::` fences | B is A inside one div |
| List uniformity | items `L_1 .. L_n` | each `L_i` under a marker | B is one list of the A's |
| Safe hard-wrapping | a text line, then nonblank lines | (single input) | one paragraph |
| Link locality | document | definition changed or removed | same shape and text |
| No later-line dependence | `L`, blank | `L`, blank, `R` | A's blocks are a prefix of B's |
| Block structure first | document | inline delimiters swapped out | same block shape |

Candidate rule checks, by section of the syntax reference.  A rule is a
candidate when it quantifies over inputs (any indentation, any length,
any number) and its outcome is visible in the output.

| Section | Rule | Read from the output |
| --- | --- | --- |
| Heading | one or more `#` then whitespace; the count is the level | heading level |
| Heading | the text may continue on following lines, with or without the `#`s | one heading |
| Block quote | a line beginning `>` then a space or end of line | block kind |
| Block quote | lazy continuation of a paragraph line | nesting |
| List item | lines indented past the marker belong to the item | nesting |
| List item | an indented marker directly after paragraph text is not a sublist; after a blank line it is | nesting |
| List item | the marker table: bullets, ordered styles, definition, task | list style |
| List item | any number in the series is a valid ordered marker | list style |
| List | changing bullet or ordered style starts a new list | number of lists |
| List | an ambiguous marker continues the open list if it can | number of lists |
| List | the start number is the first item's; later numbers are ignored | start number |
| List | tight unless a blank line separates items or blocks in an item | tight or loose |
| Code block | opens with three or more backticks and at most an info string | block kind |
| Code block | closes at a backtick line at least as long, or the end of its container | block content |
| Thematic break | three or more `*` or `-`, with only spaces or tabs otherwise | block kind |
| Raw block | an info string `=FORMAT` makes the block raw | block kind |
| Div | opens with three or more colons and at most a class | block kind, class |
| Div | closes at a colon line at least as long, or the end of its container | nesting |
| Pipe table | a row starts and ends with a bar; bars separate cells | cell count |
| Pipe table | a separator line makes the row before it a header and sets alignments | header, alignment |
| Pipe table | an escaped bar, or one in a verbatim span, does not separate cells | cell count |
| Reference link definition | label in brackets, colon, then the URL | link target |
| Footnote | content indented past the reference; lazy continuation | nesting |
| Block attributes | attributes on the line before a block attach to it; repeated ones accumulate | attributes |
| Precedence | the first opener that gets closed wins; braces force opener or closer | inline nesting |
| Ordinary text | every ASCII punctuation character can be backslash-escaped | text |
| Smart punctuation | runs of hyphens divide into em and en dashes | text |

The list is a starting point taken from the rules this project has
theorems for.  The rest of the reference (links, images, verbatim,
emphasis flanking, inline attributes, symbols, math) has example checks
only until someone states a rule check for it.

## What exists

- `dev/Generate.v`: exhaustive enumeration of small canonical documents
  (`enum_cblock`, `accepted`), extracted as `Djot_fixtures.Generate`.
- `test/parsers.ml`: a parser as a function from djot to HTML, run as a
  subprocess; batch framing so one process handles a whole pool.
- `test/diff.ml`: `--subject CMD` already plugs in an arbitrary command,
  and `shape` projects HTML to block structure.
- The side conditions are booleans: `item_ok`, `items_ok`,
  `div_content_ok`, `quote_header`, `forallb nonblank`, `bcuts`.
- Two foreign implementations in the tree to try it on: `djot.js`,
  `djoths`.

## Decisions

- **Output is HTML.**  It is the one output implementations in every
  language share, and it is what the harness already speaks.  An AST
  interface would need a format each implementation agrees on, and
  dialects do not.  Relational checks compare block shape.  Rule checks
  read more (heading level, cell count, alignment, attributes, inline
  tags), so they depend on how an implementation renders, and each
  relation has to say what it assumes.
- **No QuickChick.**  What a user plugs into is an extracted program or
  a case file, so the generator's proof-side tooling does not reach
  them.  Exhaustive small-scope enumeration is deterministic and can be
  shipped as a static file.  Revisit if a property needs inputs the
  enumerator cannot reach.
- **Cases and transformations live in Gallina**, next to the theorem,
  and the theorem is stated with the same transformation function.  Then
  a case is an instance of the theorem and the two cannot drift.  The
  relation on HTML is OCaml and is the unverified part.

## Steps

1. **Quote uniformity, end to end.**
   - Gallina: a pool of `(L, map ("> " ++) L)` pairs from
     `Generate.accepted`, filtered by `quote_header l = None`.
   - OCaml: the relation on HTML shape (B = `blockquote` around A), and
     an executable taking `--subject CMD` and a property name.
   - Run on the extracted parser (must pass: it is the theorem), then on
     djot.js and `djoths`.
   - Decide here whether HTML shape is enough.  Known risks: section
     wrappers around headings, heading ids, footnote lists at the end of
     the document.
2. **Safe hard-wrapping and div uniformity**, to check the pattern holds
   for a single-input check and a second container.
3. **The remaining relational rows**, one at a time.
4. **Examples.**  Export the reference's examples (pinned in
   `dev/check/Reference.v`) with their section and expected HTML.
   Cheap, and it covers every section of the reference at once.
5. **Rule checks**, from the table above.  Rules that read the same
   thing from the HTML share a helper, so the first one pays for the
   rest.  The rules about one line's spelling (heading, quote, code
   fence, thematic break, div fence) come first: their families need no
   document generator.
6. **A static case file** (JSON: section, quoted rule, kind, inputs,
   expected output for examples) so an implementation in another
   language needs only the checker binary, or can reimplement the
   relations.
7. **README**: how to run it against your own parser, and how to select
   or exclude checks by section.

Stop after step 1 if the HTML relation turns out fragile, and
reconsider the output format.

## Limits to state in the documentation

- A pass is evidence, not a proof.
- No backtracking is about how a parser works inside.  Only its visible
  consequence (no later-line dependence) is checked.
- For a dialect outside the configurable family, the side conditions
  are computed with this parser, so the cases are a reasonable sample
  and not instances of a theorem about that dialect.
- A dialect that deliberately gives up a property will fail its check;
  that is the answer, not a bug in the kit.

## Done when

- One command checks a foreign parser against the relational checks,
  the rule checks and the examples, selectable by section, and reports
  the first failing input per check.
- The extracted parser passes every check under djot's configuration.
- The results for djot.js and `djoths` are recorded, with failures
  triaged in `djotjs-divergences.md` where they are djot.js's.
