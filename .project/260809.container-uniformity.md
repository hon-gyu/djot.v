# Proposal: what to factor before the third container

Phase 2 item 4 ([[260802.plan.autonomous]]) asks for uniformity "quantified over all `BlockSpec`
entries: container contents parse as they would at top level. One proof,
every container." We have two containers, each with its own hand proof.
This says what to do about that, and it contradicts the recommendation it
was asked to write up.

---

## The claim this replaces, and why it was wrong

The recommendation was: add **divs** next rather than ordered lists,
because divs are the third container and the third container is where
factoring the uniformity argument stops being optional. The supporting
evidence was real (the tightness fix was one guard in `step` and cost
~420 lines of `Parser.v` to repair around `list_uniformity`), but it does
not support that conclusion.

Two checks, both cheap, both skipped at the time.

**1. Divs strip nothing.** `djot.js/src/block.ts:634-648`: `fenced_div`'s
`continue` returns `true` for every line that is not a closing fence.
There is no prefix to remove and no column to shift. Confirmed against
the oracle:

| input                                     | djot.js                                  |
| ----------------------------------------- | ---------------------------------------- |
| `:::` / `- a` / `- b` / `:::`             | the list, parsed exactly as at top level |
| `::::` / `:::` / `x` / `:::` / `::::`     | nested by fence length, like code fences |
| `:::` / ` ``` ` / `:::` / ` ``` ` / `:::` | the inner `:::` is code, not a close     |

So div uniformity is the quote argument *minus* the prefix machinery:

```coq
Theorem div_uniformity :
  forall content, div_content_ok content = true ->
    parse_lines (div_open :: content ++ [div_close]) (PPara [])
    = [mk (Div (parse_lines content (PPara [])))].
```

**The side condition is sharper than "no line is a closing fence", and
the obvious statement of it is false.** djot.js advances past a line's
indentation before running any container's `continue`, so a div's close
fence is visible through arbitrary indentation and arbitrary nesting
depth. The counterexample, from the oracle:

| input                                | djot.js                                     |
| ------------------------------------ | ------------------------------------------- |
| `- a` / `  :::` / `  b`              | one item, para `a / ::: / b`                |
| `:::` / `- a` / `  :::` / `  b` / `:::` | div closes at `  :::`; `b` / `:::` is a top-level para |

The list-item continuation and the div close both match that line, and
the div wins. A quote survives the same test (`> :::` does not close the
div) only because `>` is non-whitespace and blocks the fence match at
the position the scan reaches.

So the side condition must reach **every line of the content, nested
lines included**, not only the content's top-level lines. The wrong
statement is the one a reader writes down first, and it is refutable in
one oracle run.

A whitespace-stripping `forallb` over all content lines would be sound,
and that is as far as reasoning got before the proof was attempted. It is
also wrong — see "Outcome" below, where the code-fence exception forces a
run predicate instead. The lesson is that the analogy to `code_ok` was
doing the arguing, and it does not survive contact with `#109`.

**Consequence for the probe documents.** Row 2 stays outside the family:
a fixed `:::` fence, the choice `CCode` already makes for its three
backticks, cannot express nesting by fence length, so it pins as an
oracle-agreement `Example`. Row 3 turns out to be *inside* the family
under the run predicate (`div_code_fence_uniform`), which is precisely
the evidence that the lexical condition was the wrong shape.

**2. The containers do not share machinery, so there is little to
factor.** Counting proofs by the name they are stated about:

|                          | supporting lemmas |
| ------------------------ | ----------------- |
| quote                    | 16                |
| list / item / scan / pad | 55                |

(`grep -cE '^(Lemma|Theorem|Corollary) .*<name>' theories/Parser.v`, out
of 118 total.)

Quote re-derives its prefix on every line. A list item's continuation is
whitespace, so its descent is a column shift, which is the entire
`pad_state` / `run_pad_safe` / `run_lines_pad_shift` layer. Divs need
neither — they need a lexical guard on content lines instead. Three
containers, three disjoint mechanisms. A "one proof, every container"
theorem over those three would be a case split wearing a quantifier.

**Where the duplication actually is: inside the list family.** Ordered
lists, task lists and definition lists all go through djot.js's single
`list` / `list_item` spec — there is no separate definition-list spec —
and they reuse the whole pad and scan layer. That is the copy-paste that
would hurt, and it is one family, not the container axis.

They do not, however, differ *only* in the marker, and a marker
parameter is not the whole of what they need:

- **Task lists** genuinely are the bullet case at a different width
  (`- [ ] `, 6 characters). A marker parameter is the whole job.
- **Ordered lists** additionally need style narrowing. `getListStyles`
  (`block.ts:9-31`) returns *two* candidate styles for an ambiguous
  marker — `i.` is both roman and alpha — and `block.ts:389-399` narrows
  the candidate set as later items arrive, closing the list when it
  empties. There is also a start number. None of that is a width.
- **Definition lists** share the spec via the `:` marker but build a
  term/definition item shape rather than a block sequence.

So B2 below buys task lists outright and ordered lists only partway.
Its exit criterion is stated in `lists.test` mismatches for that reason:
the number is what says whether style narrowing has been reached.

## What a marker generalization costs

Bounded, and less than it looks, because the hard part is already
generic.

**Already width-generic:** `pad_state` takes an arbitrary `n`, and
`run_lines_pad_shift` an arbitrary blank prefix `p`, shifting by
`String.length p`. The pad layer never needed to know the marker is two
characters wide.

**Fixed at the call sites:** `bullet_open := "- "` and
`bullet_cont := "  "` (`Line.v:597-598`), mentioned 63 times in
`Parser.v`, 17 in `Line.v`, 8 in `Render.v`, 4 in `Roundtrip.v`.

**One trap worth naming now.** `"> "` and `"  "` are both two characters
long, so the literal `2` in `Parser.v` is currently ambiguous between the
quote pad and the item pad: 6 occurrences of `pad_state 2` belong to the
quote section and 19 to the list section, and nothing in the text
distinguishes them. An ordered-list marker (`1. `, width 3) is the first
thing that separates them, and it will separate them by breaking proofs
rather than by reporting. Renaming the two constants and replacing the
literal with `String.length _` is worth doing as its own step, before any
marker parameter exists, precisely so that step's diff is mechanical and
reviewable.

## Options

**A. Divs now, no factoring.** Third container, new `CDiv` case in
`cb_ok` / `cb_lines` / `cb_ast` (`Div` already exists in `Ast.v:156`).
Reuses the quote skeleton with less work. Independent of everything
below.

**B. Un-fix the marker in the list family, then ordered and task lists.**
Split into two steps: (B1) rename the pad constants and replace the
literal `2` by `String.length` at all 25 sites, no semantic change; (B2)
thread a marker parameter through `bullet_open` / `bullet_cont` /
`item_ok` / `list_lines` and the uniformity chain. Ordered and task lists
then land against a generic list theorem rather than against a copy.

**C. `BlockSpec` record plus a genuinely generic uniformity.** What Phase
2 item 1 asks for as written, and what Phase 4 would need. Rejected for
now: the evidence above says quote, list and div share nearly nothing, so
a record-indexed uniformity at three containers buys a quantifier over a
case split, at the cost of restructuring a parser whose proofs were just
reworked. Phase 4 is unsettled, and this should not be pre-paid for it.

---

## Recommendation

**A, then B1, then B2.** A is cheap and independent, and it is also the
test of this proposal's central claim. B1 is mechanical and removes a
trap that would otherwise be discovered by proof breakage. B2 is the
factoring that the duplication evidence actually supports.

Do **not** do C on the strength of "three containers". Revisit it when
either the `Config` audit for Phase 4 goes ahead, or a container turns up
that shares structure with an existing one.

### The prediction that would refute A's premise

Div uniformity should come in **under ~150 lines** of `Parser.v` and need
**no new shared apparatus**: no pad layer, no scan projection, no
acceptance predicate beyond the fence-length condition. If it instead
needs any of that, then containers do share structure after all, the
count above measured the wrong thing, and C moves back on the table.
Write the theorem statement and run the probe documents above through
`Compute` before starting the proof — as the indented-close
counterexample shows, that step is what the statement costs.

### Outcome: the prediction half failed (executed 2026-08-09)

**Line count: held.** `div_uniformity` plus its continuation lemma is
about 60 lines of `Parser.v`, and the proof went through on the first
attempt. `parse_lines_div_cont` is the quote argument with the prefix
machinery deleted, exactly as claimed.

**"No new acceptance predicate": failed, on the criterion above.** The
side condition is `run_div_open`, a fold of `step` over the contents
checking at each line that the div does not close there. That is
structurally a `run_pad_safe` — a run predicate over parse states, not a
`forallb` over lines — and the section above says a lexical condition
would do. It will not, for two independent reasons found by `Compute`:

- `div_close` strips leading whitespace, so the condition must reach
  nested lines (`div_indented_close_differs`);
- a `:::` inside an open code fence is *not* a closer (djot.js
  `block.ts:635-638`, issue #109), so whether a line closes the div
  depends on the state it is reached in. `div_code_fence_uniform` is a
  document that *is* uniform and that a lexical condition would reject.

The second one also required a `in_fence` predicate in the parser —
djot.js's `this.tip()` — which is genuinely new apparatus, and without it
the parser disagreed with both oracles on `fenced_divs.test:123`.

**What this does and does not change.** It does not put C back on the
table: a run predicate over `step` is not shared *structure* between
containers, it is the third distinct continuation rule, and quote and
list still share nothing with it. But the section "Divs strip nothing …
Divs are the cheapest container" was too strong: divs are the cheapest to
*prove* and not the cheapest to *state*, and the whole cost sits in the
side condition. The general lesson — a container's cost is its
continuation rule's dependence on parse state, not its prefix — belongs
in `project-engineering-lessons.md` if it recurs with a fourth container.

### Exit criteria

- **A**: `div_uniformity` proved with a stripped-line side condition;
  `CDiv` in the `cblock` family; `Generate.v` enumeration extended and
  still roundtripping; the indented-close counterexample pinned as a
  failing-by-construction `Example`, and rows 2 and 3 pinned as
  oracle-agreement `Example`s outside the family.
- **B1**: `bullet_cont` and the quote prefix have distinct names, no
  bare `2` remains in the list or quote sections, and the build is
  unchanged otherwise (`git diff` reviewable as a rename).
- **B2**: `list_uniformity` quantified over a marker; the bullet case is
  it instantiated; `make shape` shows `lists.test` mismatches falling
  from 15 as ordered and task lists land.

### Outcome for B1 and B2 (executed 2026-08-09)

**B1: done, and it was a true no-op.** `quote_open` moved from `Render`
into `Line` (Parser needs to name its width), and `quote_pad` /
`item_pad` replaced all 25 bare `pad_state 2` sites — 6 quote, 19 list,
exactly the split predicted. The generated-corpus numbers were
byte-identical before and after (341/593 at the time), which is the
evidence that nothing moved.

**B2: done, and the plan's proposed shape was wrong in a way worth
recording.** The plan says "thread a marker parameter through". Done that
way it is a 21-lemma edit in which every proof carries a parameter it
never uses, and every downstream application grows two arguments. A
`Section` with `Variable mrk : marker` / `Hypothesis Hmrk` does the same
job with *no* change to any proof body: `End ListMarker` generalizes
exactly the statements that mention the marker and leaves the rest alone.

Two details that made it work:

- `bullet_open` / `bullet_cont` / `item_pad` had to become `Notation`s
  for `mk_open bullet` etc., not `Definition`s. The generalized theorem
  rewrites against a canonical rendering, and `rewrite` needs the names
  to be *syntactically* the instantiation.
- The classify destructs already bind `m` for the marker character, so
  the section variable is `mrk`. Worth knowing before starting.

`star_uniformity` and `plus_uniformity` are the payoff: two further list
styles, each `exact (list_uniformity <marker> <ok>)`, no new proof.

**The B2 exit criterion above is not met and could not be.** `make
shape`'s `lists.test` count moves when ordered and task lists *land*,
which is follow-on work, not B2. B2 is the seam they land against. What
B2 does not supply, and what the section above already flagged, is
`getListStyles`' style narrowing — an ordered marker needs a candidate
*set* that later items narrow, which no `marker` value can express. That
is the next real design question, and it is bigger than a parameter.

## Postscript 2026-08-09 — what block attributes said about option C

Option C was deferred with an explicit revisit criterion: *"when a
container turns up that shares structure with an existing one."* Two new
`pstate` constructors have since landed (`PAttr`, `PPend`; commit
`7d57af2`). Neither meets it, and the way they miss is informative.

**`PAttr` is the most state-dependent continuation rule yet and still
shares nothing.** Its `continue` consults a character state machine
carried in the state, and closes on that machine reaching `ADone` — not
on a prefix, not on a fence, not on a column. That is a fourth distinct
continuation mechanism after quote-prefix, list-column and div-fence.
The div outcome above already generalized the cost of a container to
"its continuation rule's dependence on parse state"; `PAttr` is the
extreme of that scale and it cost about what the others did.

**`PPend` is not a container at all, and that is the finding.** djot.js
keeps pending block attributes in a document-wide variable, not on the
container stack. Modelling it as a `pstate` constructor nonetheless
worked with no friction: `lazy_ok`, `in_fence`, `list_open`, `pad_state`,
`finish` and both `state_wf` / `state_supported` thread through it
transparently, and the only interesting rule is where the decoration
attaches. So `pstate` is not a stack of *containers*; it is a stack of
*line consumers*, which is a wider notion than `BlockSpec` and admits
things `BlockSpec` has no name for. A record-indexed uniformity would
have had to exclude `PPend` by hand.

**Verdict: C moves further away, not closer.** Five of the eight
constructors are now containers and three are not, and the three that
are not are the ones that were cheapest to add.
