# A failed block attribute spec re-reads its lines with attributes off

Working doc for the `attributes:253` gap. It carries the measurement,
the hypotheses, the step plan and a progress log, so that picking the
work up does not mean re-deriving any of it.

Status line at the top of this file is the one thing to keep current.

## The gap

`{` at the start of a line opens a block attribute container that keeps
a live `AttributeParser`. When the spec fails, or when the indentation
runs out with the spec unfinished, djot.js converts the container to a
paragraph and re-reads the lines it consumed with **attribute
recognition switched off** (`block.ts:533-596`, `inline.ts:637`). We
accumulate the same lines and re-read them with attributes **on**.

```
{%
c
%}
```
| | |
| --- | --- |
| djot.js | `<p>{%\nc\n%}</p>` |
| ours | `<p></p>` |

The paragraph is the three lines either way. The difference is that our
re-read opens a `{% %}` comment spec across them, which closes, attaches
to nothing and is dropped.

`attributes.test:253` is this with an SPDX line in the middle. It is the
only corpus case, and the corpus is not the measurement.

## The mechanism, in our terms

Two places lose the bit.

`Step.v:1493-1499`, the `PAttr` failure arm:

```coq
if ap_failed ap'
then step_fuel n' off l (PPara slices)
```

`slices` becomes an ordinary paragraph, indistinguishable from lines the
paragraph read itself.

`Step.v:739-746`, `finish` on a spec that never finished:

```coq
| PAttr _ _ ap slices =>
    if ap_done ap then []
    else match slices with
         | [] => []
         | _ => [mk (Para (para_inlines (rev slices)))]
         end
```

Both call `para_inlines`, which is `ifinish (iscan_lines l istart)` and
scans with `inline_attrs_enabled`, the ambient setting.

The inline layer already has the bit. `f159676` threaded
`attrs_enabled` through `istep_at` and `ibreak_at` for the inline
shadow, so what is missing at block level is a way to say "the first
`k` lines of this paragraph take the bit false".

## Hypotheses

Each is stated so that its failure names something, per
[[project-engineering-lessons#Predict the falsifier at the right
granularity, or the prediction teaches nothing]].

**H1. The attributes-off region is a whole number of leading lines.**
`block.ts:552` and `:570` push slices as `{startpos: this.pos, endpos:
this.starteol}`, one per line, so the block path never cuts inside a
line. This is the one place the block gap is *easier* than the inline
one: `islice_end`, the disposition that makes `{a--` two hyphens, has no
counterpart here and must not be reused.
*Falsifier*: a document where the recovered paragraph's first `k` lines
scanned attributes-off still differs from djot.js.

**H2. `para_inlines_off k` is the whole of the inline-layer change.**
Defining `iscan_lines_off k`, which scans the first `k` lines with
`istep_at false` / `ibreak_at false` and the rest with the ambient
setting, and `para_inlines_off k ls := ifinish (iscan_lines_off k ls
istart)`, closes all 82.
*Falsifier*: any of the 82 needing something other than the count.

**H3. No inline statement acquires a hypothesis.** `para_inlines_off 0 =
para_inlines` definitionally, so every existing statement about
`para_inlines` stands unchanged and unconditioned.
*Falsifier*: a lemma in `Inline.v` that has to be restated over the new
definition rather than instantiated from it.

**H4. The new state is canonically unreachable, so the downstream chain
keeps its statements at `k = 0`.** No `cb_ok` document contains a failed
block attribute spec, so `Render.v`, `Roundtrip.v`, `Uniformity.v`,
`ListUniformity.v` and `OrderedList.v` see the new shape only as a case
to discharge, never as one to reason about.
*Falsifier*: any statement in those files that needs a genuine argument
about `k > 0` rather than a contradiction or a `reflexivity`.

## Out of scope, deliberately

Three divergences touch this code and are not part of the target.

**A container prefix lands inside the recovered paragraph.**
`> {%` / `> c` / `> %}` gives djot.js `<p>{%\n&gt; c\n%}</p>`, with the
blockquote marker of the second line inside the paragraph text: upstream
replays absolute source positions, so `this.pos = lastpos + 1` re-reads
bytes the container prefix had already eaten. djoths gives a third
answer again (`<p>{%</p><p>c\n%}</p>`). Nobody agrees, no prose covers
it, and reproducing it would mean keeping source offsets that our parser
does not have. Fix the top-level family; log this one and leave it.

**A spec that spans a blank line and then fails.** Already decided:
djot.js keeps the blank inside the paragraph, and a paragraph containing
a blank line is what `wf_block` excludes because it does not round-trip.
See [[project-engineering-lessons#When the oracle's answer is
unrepresentable]]. Unchanged by this work.

**The 10 EOF cases.** `djotjs-bug`, adjudicated against djoths above.
Log, do not match.

## The design decision

One state has to carry the count, and the choice is the first thing to
settle because everything after it is mechanical.

The three candidates, with what each actually costs:

**(A) A field on `PPara`.** `PPara (k : nat) (cur : list string)`. 556
mentions, all of which become call sites. Almost no *proof* uses the new
field, so by [[project-engineering-lessons#Check whether a proof uses the
structure before pricing its removal]] the work may be far below the
diff. But the diff itself is the liability: 556 edits, ~30 destruct
patterns gaining a binder, and every canonical statement acquiring a
literal `0` it did not ask for.

**(B) A new constructor.** `PParaOff (frozen : list string) (cur : list
string)`. `PRef`, a comparable constructor, is mentioned 20 times in the
whole development, so the mention count is small. The cost is one arm in
each of ~20 pstate-matching definitions and ~30 exhaustive destructs,
plus a second copy of the `PPara (c :: cur')` step logic (lazy
continuation, underline test, interrupt test), which is the part that can
drift.

**(C) Keep the failed spec in `PAttr`.** The state already holds
`slices`, and `ap_failed` already distinguishes the failed spec from a
live one. `finish` already turns a non-`done` `PAttr` into a paragraph
of its slices, so half of this exists. Adding no constructor means no new
destruct arm anywhere: the arms all exist and become conditional on
`ap_failed`. The cost is one extra field for the lines accumulated after
the failure, which changes `PAttr`'s arity at 15 sites and ~30 destruct
patterns, and the same duplication of paragraph step logic as (B).

(C) looked cheapest until the extra field: a failed spec keeps taking
lines, and they cannot go in `slices` without destroying the count. That
puts (B) and (C) within a field of each other, and (B) says what it means
in its name.

**Leading choice: (B).** Decide it for real with the spike in Step 1,
not from this paragraph.

The standing quantifiers a new `pstate` shape has to answer to, per
[[project-engineering-lessons#Probe the definitions a theorem already
constrains, too]]: `step_fuel_shift` (`Step.v:2130`), `step_fuel_pad`
(`Step.v:3262`), `step_blank_finish` (`ListUniformity.v:833`),
`finish_wf` (`Wf.v:2373`), `finish_supported` (`Wf.v:3337`). The first
two are the ones with teeth, because `PParaOff` records no column and so
must be invariant under `pad_state` -- which is what makes it a
paragraph and not an attribute state.
