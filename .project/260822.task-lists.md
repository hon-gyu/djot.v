# Plan: task lists

Measured against djot.js on 2026-08-22, djoths where it says so.

## 0. What is different from definition lists

A task list is the same discovery one step further on: `getListStyles`
gives `- [ ]` the style `"-X"` (`block.ts:12`), the same `list` and
`list_item` containers open and continue it, and `-list` picks the node
from the style.  So §1's marker work is small for the same reason it was
last time.

**But the checkbox is per *item*, and that is new.**  Every datum a list
has carried so far belongs to the list: a style, a start number, a
spacing.  `- [ ] a` / `- [x] b` is *one* list whose two items differ, so
the state has to record something per item that is not in the item's
blocks -- unlike the definition term, which
[[260822.definition-lists]] read back off the item at close for free.
That is the whole cost of this construct, and §2.2 is where it lands.

## 1. What the oracle does

### 1.1 The marker

`pattTaskListMarker` is `[*+-] \[[Xx ]\][ \t\r\n]` (`block.ts:60`):
bullet, exactly one space, `[`, one of `x`/`X`/space, `]`, then
whitespace or end of line.  It is tried *after* `pattListMarker` matches
and replaces the marker when it does, so a task marker is a bullet
marker that happens to continue.

| line | verdict |
| --- | --- |
| `- [ ] a`, `- [x] a`, `- [X] a` | task item |
| `- [ ]`, `- [ ] ` | task item with no content |
| `- [ ]  a` | task item whose content is ` a` |
| `- []`, `- [y] a` | plain bullet item |
| `- [ ]a` | plain bullet: the pattern needs whitespace after `]` |
| `-  [ ] a` | plain bullet: it needs exactly one space before `[` |
| `1. [ ] a`, `: [ ] a` | plain ordered / definition item |

`[x]` and `[X]` are both checked; the status is per item and does not
enter the style.

### 1.2 Everything else is the list machinery

- `- [ ] a` / `- b` is **two lists**, and so is `- a` / `- [ ] b`: the
  styles are `-X` and `-`, which do not intersect.  `- [ ] a` /
  `* [ ] b` is two lists for the same reason.
- `- [ ] a` / `- [x] b` is **one** list: the checkbox is not the style.
- Continuation is `indent > marker indent`, so one space is enough and
  the marker's width is not consulted -- `- [ ] a` / `  b` is one
  paragraph, exactly as `- a` / `  b` is.
- A task list does not interrupt a paragraph; it nests in a quote or an
  item with no special handling; `{#i}` above it attaches to the `<ul>`.
- The content after the marker is ordinary block content: `- [ ] # h`
  is a heading inside the item, and `- [ ] - [ ] b` a nested task list.

### 1.3 The rendering

```
<ul class="task-list">
<li>
<input disabled="" type="checkbox"/>
a
</li>
```

The `class` precedes the node's own attributes (`{#i}` gives
`<ul class="task-list" id="i">`), which is the order `ol_attrs` already
establishes for ordered lists.  The `<input>` sits on its own line
directly after `<li>`, before the item's content and outside whatever
the tightness does to it, and carries `checked=""` when complete.

**djoths renders this construct differently** -- `<li class="checked">`
and a `<label>` wrapper (`- [x] b` gives
`<li class="checked">\n<label><input type="checkbox" checked="" />b</label>`).
The parse agrees on every case probed; only the HTML differs.  djot.js
is the authority and the corpus pins it, so this is a rendering
divergence to log, not a decision.

## 2. The change

### 2.1 The marker, in `Line.v`

`lstyle` gains `STask (c : ascii)`, which is what keeps a task list and
a bullet list apart under `narrow`.  `list_marker` recognizes the
checkbox after the bullet and reports it, so `KList` gains a fourth
field:

```coq
| KList (sty : list lstyle) (core : string) (chk : option task_status)
        (rest : string)
```

`chk` is `Some` exactly when `sty` is a task style.  This is the
classifier carrying what the step needs, which is `KRow`'s shape rather
than a second recognizer over the same line.

**Obligation prediction.**  No statement acquires a hypothesis.  34
`KList` sites and ~15 `list_marker` sites widen by one binder or one
`_`; the eleven `forall a b c, classify next <> KList a b c` in
`OrderedList.v` and `ListUniformity.v` gain a fourth binder and nothing
else.  All mechanical.

### 2.2 The state: add a field, never widen `ls_items`

`ls_items : list blocks` is the tempting place to put the status, and it
is the expensive one: 22 places in `ListUniformity.v` manipulate
`rev (ls_items ls) ++ ...` structurally, so changing its *element type*
is [[project-engineering-lessons#Check whether a proof uses the
structure before pricing its removal]] answered the wrong way.  Two new
fields instead, which no existing statement mentions:

```coq
  ; ls_check : task_status          (* the open item's *)
  ; ls_checks : list task_status    (* the closed ones, reversed *)
```

parallel to `done`/`last` and `ls_items` respectively, pushed together
in `list_next`, so `combine (rev (ls_check :: ls_checks)) (rev (last ::
ls_items))` pairs by construction.  A non-task list carries a
meaningless `Incomplete` in every slot and nothing reads it -- djot.js
does the same, with `checkbox: null` on every list item container.

`list_block` gains its third arm, keyed on `STask` as the colon's is on
`SBullet ":"`.

### 2.3 `Html.v`, and `Document.v`

The `TaskList` arm is `Html.v:327`'s stub plus the same arm in
`render_block_foot`.  `Document.v` is the definition-list step again:
five passes descend into the items, and `block_ind2` gains a fifth
predicate, since `list (task_status * blocks)` is not `D`'s type.

## 4. The canonical view: a kind that carries a list

The four-piece `list_kind` interface assumes a list's markers are a
function of the kind and the item's *index* -- `dec_items` renumbers,
`same_marker` repeats.  A task list's markers depend on per-item data
that `ck_items`' `list (list string)` does not carry.

**Propose:** `LKTask (checks : list task_status)`, with
`ck_ok (LKTask cs) n = (length cs =? n)` tying the two together, and
`marker` gaining `MTask (c : ascii) (st : task_status)` whose `mk_open`
is `- [x] ` and whose `mk_pad` is therefore 6.  The kind carrying a list
is new; the kind carrying *data* is not (`LKDecimal d start`), and
`ck_ok` already exists to state a condition the data has to satisfy.

Then `ck_items (LKTask cs)` zips rather than counts, and `ck_uniformity`
instantiates the *general* `list_uniformity` rather than
`list_uniformity_same` -- the markers differ between siblings, which is
the case that theorem exists for and which the ordered kinds already
use.  `items_ok` is trivial: every `MTask c st` offers `[STask c]`.

**Probe before writing it.**  `mk_pad` is 6 where every bullet is 2, and
the pad layer is the part of this development most sensitive to a column
(`step_fuel_pad`, `pad_state`).  Nothing in the *parser* consults a
marker's width -- §1.2 -- so the risk is confined to the rendering side,
but check `indent_lines`/`item_ok` at a six-wide marker before
committing, the way the ordered kinds' widening markers were checked.

## 5. Open questions

- Whether `MTask` should carry the bullet character at all.  Only `-`
  can be canonical (the view has no reason to spell `*`), and dropping
  it would make `mk_open` constant per status.  Keep it if `mk_sty` and
  `narrow` read better with it, which they should, since a task list's
  style is the bullet's.
- Whether `ls_check`'s meaningless value for a non-task list should be
  `option task_status` instead.  `combine` would then need a default at
  the one place that reads it, which is worse: a silent default hides a
  mismatch where a meaningless-but-total field cannot have one.

## 6. Progress

Steps 1, 2 and 4 landed on 2026-08-22.  Step 3 did not, and §6.3 says
what stopped it.

### Steps 1 and 2: the marker, the state, and the passes

`lstyle` gained `STask`, `list_marker` reads the checkbox after the
bullet's one space, and `KList` carries it as a fourth field -- the
classifier answering with what the step needs, which is `KRow`'s shape.
The prediction that no statement acquires a hypothesis was **wrong**,
and in a way the plan should have caught: `Line.classify_marker_open`
says a marker followed by any line classifies as that marker, and with
`- [x] ` a marker that is now false.  So `item_ok` gained a conjunct,
which is [[project-engineering-lessons#Probe the definitions a theorem
already constrains, too]] -- the standing theorem was over *lines*
rather than states, and the check is the same.

The conjunct is `negb (task_start l0)`, which does not mention the
marker, and that spelling is the whole reason the step stayed small.
The natural condition is `negb (task_shadow m l0)` -- the *marker's*
line does not become a task marker -- and it is viral:
`OrderedList.item_ok_thematic_indep`, with nine users, says the
thematic test is the whole of `item_ok`'s dependence on its marker, so
a marker-dependent conjunct would have taken a hypothesis through all
nine.  Asking it of the line alone costs an ordered or definition item
nothing it can canonically spell, since a canonical `Str` escapes its
brackets.  [[project-engineering-lessons#Prefer the stronger
precondition when the weaker one is viral]], applied without having to
discover it the hard way.

**The state.**  `ls_items : list blocks` was the tempting place for the
statuses and the expensive one -- twenty-two proofs in
`ListUniformity.v` manipulate `rev (ls_items ls) ++ ...` structurally --
so `ls_check` and `ls_checks` are new fields beside it, pushed with it
in `list_next`.  No existing statement mentions them; what the change
cost is the thirty-odd `LSt` constructions, which are mechanical, and
the five `pad_*` field lemmas, which each gained two projections.

`Ast.task_items` pairs the two lists at close.  It recurses on the
*items*, not on `combine`: a short status list then pads instead of
truncating, and every lemma about the fold is unconditional where
`combine` would have needed a length hypothesis in each.

`Document.v` was the definition-list step again -- five passes and a
fifth predicate `K` on `block_ind2`, since `list (task_status * blocks)`
is not `D`'s type.  `wf_block`'s task clause lost its per-item
`nonempty`: `- [ ]` alone is an item with no blocks, which djot.js
renders as `<li><input/></li>`, the same evidence the definition list's
clause rests on one construct over.

**Measured.**  Corpus **275 -> 278/287**: `task_lists.test` is 3 of 3
and every construct in `Ast.v` now has a parser.  `--shape` stays
287/287, generated 4742/4742, roundtrip 31272, all clean.

### Step 3: landed 2026-08-24

The proposed representation survived the proof: `LKTask checks` carries the
source-order status list, `ck_ok` requires its length to equal the item count,
and `ck_items` zips statuses with canonical `MTask` markers.  The six-column
marker passed through the existing padding theorems without a new hypothesis.

The proof boundary moved in the smallest useful way.  `styles_list_checked`
adds the parallel status list to the generic uniformity result; every non-task
style ignores it definitionally.  `item_checks` states the induction invariant
once as the reversed statuses already in `list_state` followed by the future
markers' statuses.  This removed `no_task_style` rather than weakening it or
copying a task-only parser proof.

`CList (LKTask checks)` is therefore the canonical representation: no new
`cblock` constructor and no new public roundtrip case.  `cb_ok_list`'s existing
nonempty-item condition keeps empty task items outside the canonical fragment,
while the total source and HTML renderers still support parser-produced empty
items.  `canonical_task_list_roundtrip` applies `roundtrip_blocks`; the
separate generated task pool alternates statuses and checks every accepted
one by computation.

### Source-rendering prerequisite (2026-08-24)

`Render.render_block_lines` is now total on `TaskList`.  It writes mixed
complete/incomplete items, preserves empty items as `- [x]` / `- [ ]`, and
uses the marker's six-column continuation prefix.  The executable
`task_list_source_render_roundtrip` witness pins parser recovery for a mixed
three-item list including an empty item.

This checkpoint was the prerequisite for the now-landed canonical work above.
Empty task items intentionally remain a total-renderer/parser feature rather
than a canonical `cblock` inhabitant, because the shared list fragment requires
every item to contain at least one block.
