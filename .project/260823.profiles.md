# Profiles compose capabilities

## Contract

A profile is a named pairing of the proof-bearing inline table and block
configuration. It is not an enum and does not hide the underlying knobs.
`with_inline_profile` and `with_block_profile` let a caller start from Djot or
Markdown-like behavior and replace either half with any independently
constructed configuration.

The first two values are `djot_profile` and `markdown_like_profile`. The
latter is not called CommonMark yet: Djot-only constructs remain enabled and
GFM table semantics do not exist.

## First cross-profile capability: fenced divs

`bdivs` is the fifth block decision. Djot enables it; `markdown_bconfig`
disables it. With divs off, a `:::` opener is complete paragraph text and
`cb_ok` excludes `CDiv`, so the generic roundtrip theorem remains true.
`with_divs` preserves block incrementality and the unrelated prefix-overlap
invariant.

## Task lists preserve syntax before gating semantics

`Line.task_marker` keeps the semantic status, the literal box character, and
the optional whitespace separator after `]`. The AST still receives only
`task_status`; the extra source evidence exists solely so another profile can
decline task semantics without inventing text.

`btasks` is the sixth block decision. Recognition remains uniform. At list
construction, Djot projects a recognized task marker to `TaskList`; the
Markdown-like profile projects the same classification to its original bullet
marker and literal item prefix. Thus `[x]` versus `[X]`, a space versus a tab,
and a bare checkbox all survive disabled fallback exactly.

The canonical side is gated at `ck_ok (LKTask checks)`: disabled task lists are
outside `cb_ok`, while the generic roundtrip theorem is unchanged. `with_tasks`
preserves every unrelated block setting and can restore task semantics on any
composed profile.

## Table flavors

`btables` continues to mean Djot tables. A future GFM recognizer will justify
replacing it with an `Off | Djot | Gfm` dialect choice. Until then,
`markdown_like_profile` keeps Djot tables off and no value claims GFM
compatibility.

## Raw blocks become code without losing source

`braw_blocks` is the seventh block decision. Fence recognition and the
verbatim `PFence` state remain shared. Only `fence_block` projects an info
string beginning with `=` to `RawBlock`; with the capability off, it instead
produces `CodeBlock` with the complete `=format` language string.

The canonical view now distinguishes `CCode` from `CRaw`. This makes its AST
projection injective enough to state the boundary directly: `CRaw` requires
raw blocks to be enabled, while a code block whose language begins with `=`
is canonical only when raw interpretation is disabled. `with_raw_blocks`
preserves every other block decision.

## Raw inline reuses literal candidate fallback

`dc_raw_inline` is independent of the delimiter rows and smart typography.
The scanner still recognizes a verbatim followed by `{=format}` through its
existing `IRaw` state. When raw inline is disabled, a successful candidate
takes the same fallback as a rejected candidate: it emits `Verbatim` and
replays the complete `{=format}` region as `Str`.

`with_raw_inline` preserves the delimiter-table admissibility conditions and
every unrelated inline setting. Canonical `CIRaw` requires the capability, so
the generic inline and document roundtrip theorems continue to describe the
profile-specific canonical fragment.

## Math needs no canonical clause

`dc_math` is the third scanner capability, beside smart typography and raw
inline. The `$` prefix keeps its own scanner state at every setting; only the
backtick branch is gated, and when math is off that branch falls through to
the byte's ordinary handling. So the dollars join the pending text and
`ilead` opens the verbatim they were about to prefix: ``$`x` `` is
`Str "$"` followed by `Verbatim "x"`, and ``$$$`x` `` keeps all three
dollars.

Unlike every capability before it, this one changes nothing on the canonical
side. `cinline` has no math constructor, so math was already outside the
roundtrip fragment and `ci_ok` needs no new clause. The whole cost was one
condition in `idollar_step` and the three proof sites that case on its
branch. `with_math` preserves delimiter admissibility and every unrelated
inline setting.

## Definition lists are gated at the close, not at the open

`bdeflists` is the eighth block decision and the first whose gate is the
*closing* projection. Every capability before it decides what a line opens;
this one cannot, because a definition list has no opener of its own. The
colon is a bullet character, `: t` is an ordinary list item at every setting,
and the only thing that distinguishes the construct is `styles_list` reading
the style `:` as a term/definition split at close. With the capability off
that split is what goes away: the same items become the bullet list any other
marker would have made, markers included.

Making that one arm configured meant `styles_list` had to see a `bconfig`,
and it lived in `Marker.v`, below `Step.v`. Moving the four definitions into
`Step.v`'s `Section WithTable` is what kept the argument implicit: none of
the twenty-odd call sites in the uniformity chain changed, and the whole
diff outside the definition itself is four proof sites and one new lemma
(`marker_list_checked_colon`), which is the colon instance the generic
uniformity theorem now rewrites through.

`ck_ok LKDef` is the canonical gate, so a definition list leaves the accepted
fragment exactly where the split does. Nothing else needed a clause: a
colon-marked bullet list is not canonical at either setting, since canonical
`LKBullet` renders `-`.

## Block attributes gate the opener, and stop there

`battrs` is the ninth block decision. `open_attr` is the whole gate: with
the capability off the spec never opens, `PAttr` is unreachable, and the
line is the paragraph text its own spelling makes. Nothing else in the state
machine changed, because every other mention of `PAttr` is a total function
over a state that can no longer arise.

Two statements had to be restated rather than given a hypothesis.
`step_attr_open` and `step_list_attr_close` named `PAttr` in their
conclusions; phrased through `open_attr` instead, they hold at both settings
and their one consumer needed a `surjective_pairing` and `open_attr_fst`.
That is the cheaper spelling of the same fact -- a hypothesis on those two
would have travelled into `ListUniformity`'s case analysis.

Like math, this needs no canonical clause: `cblock` has no attribute
carrier, so block attributes were already outside the roundtrip fragment.

**Why the inline half had to follow immediately.** With block attributes off
and inline ones still on, a `{...}` line that closes across a line break was
read by the inline layer instead, and a spec with nothing before it in its
scope replays its source literally -- newline included. Harmless to the
roundtrip, since `ci_ok`'s `no_nl` excludes such a `Str`, but not a shape to
ship in a profile. `dc_attrs` removes it: with both halves off the paragraph
keeps its lines (`markdown_like_multiline_attribute_is_prose`).

## Inline attributes are the same capability, one layer down

`dc_attrs` is the fourth scanner capability and covers the two things a `{`
can do that are not a delimiter row: attach an attribute, and -- after a
`]` -- open a span. Both gates reuse the existing failure path rather than
inventing one. `ibrace_step` takes `iattr_feed`'s immediate-`AFail` exit, so
the `{` goes back into the text and the byte after it is dispatched afresh;
`IClosed` falls through to `bclosed_lit`, which is what a `]` followed by
anything else already did.

The braced rows are deliberately *not* covered. They are reached from the
same `{`, but through `dstyle_of` and one branch earlier, so a table with
attributes off and djot's rows still reads `{-x-}` as a delete
(`rows_survive_inline_attrs_off`). Which containers exist stays a question
for the table.

No canonical clause again: `cinline` has neither a span nor an attribute
carrier.

## Footnotes are one capability with a field in each record

A footnote reference and a footnote definition are two halves of one
construct: a reference nothing can define is dead, and so is a definition
nothing can reference. But the reference is an inline decision and the
definition a block one, and neither record can name the other's field.

So `bfootnotes` and `dc_footnotes` exist, and `Profile.with_footnotes` sets
both. It is the first thing `Profile.v` does beyond pairing two
independently built halves, and the first argument that the profile is a
level rather than a bundle: this capability is only statable there.

The gates match the two shapes already established. `open_foot` is the block
one, exactly as `open_attr` was, and `step_foot_open` and
`step_list_foot_close` were restated through it for the same reason. The
inline one is a conjunct on `ilead`'s footnote guard, after which a `^`
falls through to the table as it does everywhere else, so `[^1]` is the
literal bracket text it spells.

`ci_ok (CINote _)` is the canonical gate. This is the first capability whose
canonical side is inline rather than block, and `iscan_note_text` -- the
lemma that says a reference's source scans back to its node -- gained the
one hypothesis, discharged at its four call sites from the `ci_ok` they
already had.

**Both shipped profiles keep footnotes on.** CommonMark has no footnotes but
GFM does, so the Markdown-facing answer is not "off"; the capability is
pinned at a profile of its own (`no_footnotes_profile`) instead. A
capability need not be off anywhere to be worth having -- what it has to be
is stated, gated on both sides, and proved not to disturb the roundtrip.
