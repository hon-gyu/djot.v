# Profiles compose capabilities

## Contract

A profile is a named pairing of the proof-bearing inline table and block
configuration. It is not an enum and does not hide the underlying knobs.
`with_inline_profile` and `with_block_profile` let a caller start from Djot or
Markdown-like behavior and replace either half with any independently
constructed configuration.

The first two values are `djot_profile` and `markdown_like_profile`. The
latter is not called CommonMark yet: Djot-only constructs remain enabled and
GFM table semantics do not exist.

## First cross-profile capability: fenced divs

`bdivs` is the fifth block decision. Djot enables it; `markdown_bconfig`
disables it. With divs off, a `:::` opener is complete paragraph text and
`cb_ok` excludes `CDiv`, so the generic roundtrip theorem remains true.
`with_divs` preserves block incrementality and the unrelated prefix-overlap
invariant.

## Task lists preserve syntax before gating semantics

`Line.task_marker` keeps the semantic status, the literal box character, and
the optional whitespace separator after `]`. The AST still receives only
`task_status`; the extra source evidence exists solely so another profile can
decline task semantics without inventing text.

`btasks` is the sixth block decision. Recognition remains uniform. At list
construction, Djot projects a recognized task marker to `TaskList`; the
Markdown-like profile projects the same classification to its original bullet
marker and literal item prefix. Thus `[x]` versus `[X]`, a space versus a tab,
and a bare checkbox all survive disabled fallback exactly.

The canonical side is gated at `ck_ok (LKTask checks)`: disabled task lists are
outside `cb_ok`, while the generic roundtrip theorem is unchanged. `with_tasks`
preserves every unrelated block setting and can restore task semantics on any
composed profile.

## Table flavors

`btables` continues to mean Djot tables. A future GFM recognizer will justify
replacing it with an `Off | Djot | Gfm` dialect choice. Until then,
`markdown_like_profile` keeps Djot tables off and no value claims GFM
compatibility.

## Raw blocks become code without losing source

`braw_blocks` is the seventh block decision. Fence recognition and the
verbatim `PFence` state remain shared. Only `fence_block` projects an info
string beginning with `=` to `RawBlock`; with the capability off, it instead
produces `CodeBlock` with the complete `=format` language string.

The canonical view now distinguishes `CCode` from `CRaw`. This makes its AST
projection injective enough to state the boundary directly: `CRaw` requires
raw blocks to be enabled, while a code block whose language begins with `=`
is canonical only when raw interpretation is disabled. `with_raw_blocks`
preserves every other block decision.

## Raw inline reuses literal candidate fallback

`dc_raw_inline` is independent of the delimiter rows and smart typography.
The scanner still recognizes a verbatim followed by `{=format}` through its
existing `IRaw` state. When raw inline is disabled, a successful candidate
takes the same fallback as a rejected candidate: it emits `Verbatim` and
replays the complete `{=format}` region as `Str`.

`with_raw_inline` preserves the delimiter-table admissibility conditions and
every unrelated inline setting. Canonical `CIRaw` requires the capability, so
the generic inline and document roundtrip theorems continue to describe the
profile-specific canonical fragment.
