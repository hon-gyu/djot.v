# Probe: what ordered lists actually cost

[[260809.container-uniformity]] left ordered lists as the open design
question and named the thing it expected to be hard: *"an ordered marker
needs a candidate set that later items narrow, which no `marker` value
can express. That is the next real design question, and it is bigger
than a parameter."* [[project-engineering-lessons#Probe the definitions a
theorem already constrains, too]] named the trap it expected to fire:
*"This fires next on ordered lists, which record a column **and a start
number**."*

Both predictions were checked before any code was written. One holds,
one is false, and a third cost neither of them mentions is the one that
actually lands on the uniformity chain.

Probes are `scratchpad/probe.mjs` (block events, so the `+list|style`
annotations are visible) and `scratchpad/rt.mjs` (parse → `renderDjot` →
re-parse, so canonical form and stability are visible). Both are
throwaway; nothing depends on them.

## 1. There is no start number in the block state (the predicted trap does not fire)

`getListStyles` (`djot.js/src/block.ts:9-31`) normalizes the digits out
of a marker before the container ever sees it: `3.` and `4.` both become
the style string `1.`, `j.` becomes `a.`. The block parser compares
*styles*, never numbers.

| input           | events                           | html             |
| --------------- | -------------------------------- | ---------------- |
| `1. a` / `2. b` | `+list\|1.`  `+list_item\|1.` x2 | `<ol>`           |
| `1. a` / `1. b` | identical events                 | `<ol>`           |
| `3. a` / `4. b` | identical events                 | `<ol start="3">` |

The `start` attribute comes from the *first item's marker text*,
decoded by style downstream of the container stack. So `list_state` needs
no counter, and the "column and a start number" trap has nothing to fire
on. The lesson's prediction was reasonable and wrong about where the
number lives.

Numbers need not be consecutive, and an ordered marker does not interrupt
a paragraph — `1. a` / `   1. n` is lazy paragraph text, exactly as
`- a` / `  - n` is.

## 2. The continuation rule does not depend on marker width, and our `step` already agrees

`list`'s and `list_item`'s `continue` are `this.indent >
container.extra.indent` (`block.ts:374`, `block.ts:441`), and
`extra.indent` is the column of the *marker*, not of the content. Width
never enters.

| input                   | djot.js                       |
| ----------------------- | ----------------------------- |
| `1. a` / ` b` (1 space) | one item, `a` / `b` in a para |
| `10. a` / `  b`         | one item, `<ol start="10">`   |
| `(1) a` / ` b`          | one item                      |

Our `step` tests `Nat.ltb (ls_indent ls) (off + indent_of l)`
(`Parser.v:479`), which is the same rule, and it is already
width-independent:

```coq
Compute (parse_blocks "- a
 b
").      (* one item, "a" / "b" — a 1-space continuation, not 2 *)
```

**So the `PList` branch of `step` needs no change for width.** That was
not obvious: `marker` currently carries `mk_pad`, and it would be natural
to assume the parser consults it.

## 3. Style narrowing is real, is a set intersection, and is observable at block shape

Confirmed, as [[260809.container-uniformity]] expected. The set is
carried in `container.extra.styles` and intersected on every sibling
(`block.ts:389-399`); an empty intersection closes the list and opens a
new one.

| input                      | result                                                            |
| -------------------------- | ----------------------------------------------------------------- |
| `i. a`                     | `{i., a.}`, unnarrowed; renders `type="i"` — first candidate wins |
| `ix. a` / `x. b`           | one list: `{i.}` ∩ `{i., a.}` = `{i.}`, `start="9" type="i"`      |
| `i. a` / `j. b`            | one list, narrowed to `{a.}`: `start="9" type="a"`                |
| `i. a` / `j. b` / `iii. c` | **two** lists: `{a.}` ∩ `{i.}` = ∅                                |
| `i. a` / `1. b`            | two lists                                                         |
| `1. a` / `1) b`            | two lists — delimiter is part of the style                        |

So `ls_marker : ascii` has to become a style *set*, and
`Ascii.eqb m (ls_marker ls)` becomes intersect-and-narrow, which writes
back to the state. That is a genuine change to the sibling test, but it
is lexical: invariant under both `step_fuel_shift` and `step_fuel_pad`
without argument.

The definitional probe the lessons prescribe was run anyway, on the
column that is already there, and it is clean:

```coq
Compute (snd (step "  - a" (PPara []))).      (* ls_indent := 2 *)
Compute (snd (step_at 2 "- a" (PPara []))).   (* ls_indent := 2 *)
```

## 4. The cost nobody predicted: the canonical pad is per *item*, not per list

`djot-renderer.ts:388-411` regenerates every marker as
`formatNumber(start + i, style)` and pushes a continuation prefix of
`" ".repeat(marker.length + 1)`. **The marker's width therefore changes
inside a single list**, whenever the numbering crosses a width boundary:

```
9. a
   a2      <- pad 3
10. b
    b2     <- pad 4
```

`rt.mjs` confirms this is the canonical form: the same document written
with a 3-space pad on item 2 parses identically and *renders back* with
4. Non-canonical input, in exactly the sense `cb_ok` exists to exclude.

This is where the current design breaks. `marker` is

```coq
Record marker : Type := Mk_marker { mk_style : ascii }.
Definition mk_open (m : marker) : string := String (mk_style m) " ".
Definition mk_pad  (m : marker) : nat := String.length (mk_open m).
```

— one opener and one pad for the whole list. For bullets that is right;
for ordered lists the opener and the pad are functions of the item index.

**This is the real content of "bigger than a parameter", and it is not
the style set.** The style set lives in the parser, where B2's
`Section ListMarker` has no stake. The per-item pad lives in `cb_lines`,
`Render.v` and the uniformity chain — precisely the machinery B2 just
finished generalizing over a *constant* marker.

## What this says to do

Three steps, in this order, each independently useful.

**S1 — widen the classifier.** `list_marker : string -> option (ascii *
string)` becomes `option (style_set * string)`, `KList` carries the set,
and `is_bullet` becomes `getListStyles`. `list_marker_length` (`length
rest < length l`, the descent's termination witness) survives verbatim —
a wider marker consumes strictly more. `step`'s `PList` branch changes in
exactly one place: `Ascii.eqb m (ls_marker ls)` becomes intersect, with
the narrowed set written back through `list_next`. No column moves, no
width appears. Everything in §2 says this is the smaller half.

Exit: `make shape` clears `lists.test:371, 402, 416, 430, 444` (the
`1.`, `4.`, `1)`, `(1)`, `(a)` cases) without touching `Render.v`.

**S2 — make the pad per-item, bullets first.** Turn `mk_open` / `mk_pad`
/ `mk_cont` into functions of the item index, with `bullet` the constant
function. Semantically a no-op — the B1 precedent says the diff should be
reviewable as a mechanical rename and the generated-corpus numbers should
be byte-identical. Do it *before* any ordered `cblock` exists, for the
same reason B1 was done before B2: otherwise the width change is
discovered by proof breakage inside a live feature.

**S3 — `COrdered` in the `cblock` family.** Only now, and with a
canonicality side condition that §3 makes unavoidable: a list is
canonical only if re-parsing its own rendering resolves to the *same*
style. The counterexample is a single-item alpha list starting at 9 — it
renders `i.`, which is ambiguous and resolves to roman. That AST is
unreachable by the parser (nothing produces it), so per
[[project-engineering-lessons#The clause this was missing: unrepresentable
oracle behaviour]] the answer is to exclude it in `cb_ok`, not to relax
anything. Two items rescue it (`i.` / `j.` narrows to alpha and is
stable), which is why the condition is about the list, not the style.

## The prediction that would refute this

turns out to need the pad, then `ls_indent` is not the only column the
list branch consults, §2 measured the wrong thing, and S2 has to come

### S2 is not the mechanical step this document said it was

Probed before starting it, on the strength of
[[project-engineering-lessons#Predict the falsifier at the right
granularity, or the prediction teaches nothing]] — predict the
*obligation*, not the diff.

S2 above says "semantically a no-op ... the diff should be reviewable as
a mechanical rename". The first half is true and the second is not.
`list_uniformity_gen` renders its items as

```coq
map (indent_lines (mk_open mrk) (mk_cont mrk)) itemss
```

— one marker, mapped. Per-item markers make that an *indexed* map, and
`parse_list_tail`, which inducts down `itemss`, has to carry and advance
the index. Every statement in the chain changes shape, not just spelling.
B1 was a rename; this is not the same kind of step.

**The obligation it introduces is the interesting part, and it is not
about width.** Two probes:

```coq
Compute (classify "9. a").   (* [SOrd Decimal RightPeriod], core "9"  *)
Compute (classify "10. a").  (* [SOrd Decimal RightPeriod], core "10" *)
```

Different widths, *same style set*. So width per se costs the chain
nothing — `pad_state` and `run_lines_pad_shift` were already generic in
it, as §4 of the container-uniformity note said. What the chain actually
needs is new: **every item's marker must leave the style set nonempty**,
because the sibling step now narrows. With one marker that was
vacuous; with a marker per item it is a hypothesis someone has to
discharge.

And that hypothesis is the canonicality condition S3 was going to
introduce separately:

```coq
Compute (narrow (with_starts [SOrd RomanLower RightPeriod;
                             SOrd LetterLower RightPeriod] "i")
          [SOrd LetterLower RightPeriod]).
(* [(SOrd LetterLower RightPeriod, 9)] — start recomputed under the
   style that survived *)
```

An alpha list starting at 9 renders `i.`, `j.`, ... ; the first marker
is ambiguous and only the second narrows it. Whether the rendering
round-trips is exactly the question of what the narrowing chain does to
the style set — which is the hypothesis S2 needs, not a separate `cb_ok`
clause bolted on later.

**So S2 and S3 are one step, and the plan's split was wrong.** Doing S2
"first, as a no-op, before any ordered `cblock` exists" was justified by
the B1 precedent, and the precedent does not apply: B1 removed an
ambiguity between two constants, whereas this changes what the chain
quantifies over. The right shape is a single step that generalizes the
chain from one marker to a per-item marker *with* the shared-style
hypothesis, and derives both the bullet case (all markers equal) and the
ordered case (all markers same style, first one possibly ambiguous) from
it.

### Outcome: the marker type generalized; per-item markers still open

Done in the same session. `marker` was a record holding one `ascii`; it
is now

```coq
Inductive marker :=
  | MBullet (c : ascii)
  | MOrd (core : string) (d : ordered_list_delim).
```

shaped after `list_marker`'s own branches rather than after the string it
produces, so every fact about it is a case analysis the classifier
already performs. `mk_open (MOrd "10" RightPeriod) = "10. "`, and
`mk_pad` of it is 4 — the width the renderer will need is now
*expressible*, which it was not before.

**What that cost, and it is the part the plan did not see.** Three facts
that were `reflexivity` at one bullet character became real lemmas:

- `classify (mk_open m ++ l) = KList (mk_sty m) (mk_core m) l`. At a
  bullet this was three concrete cases; in general it needs
  `marker_open_shape` (the opener starts with a character that is none
  of `>`, `#`, `` ` ``, `~`, `:`, so every recognizer ahead of
  `list_marker` rejects it) and `take_while_alnum_app` (an alphanumeric
  core comes off whole and the rest of the line survives).
- `0 < mk_pad m`. This was the literal `2`; eight sites in the chain
  depended on it computing.
- `String.length (mk_cont m) = mk_pad m`. Also formerly by computation.

**The conclusion had to move too, which the plan did not anticipate at
all.** `list_uniformity` concluded `mk (BulletList ...)`; at a general
marker it must conclude whichever list the marker names, so it now
concludes `marker_list mrk`, which is `BulletList` definitionally at a
bullet and `OrderedList` with style and start at an ordered marker. This
is the same shape as `list_block`'s match and needed the same treatment.

**Payoff.** `ordered_uniformity` is `list_uniformity` at an ordered
marker — no new proof, exactly as `star_uniformity` and `plus_uniformity`
are. `3. a` / `3. b` parses to `OrderedList Decimal RightPeriod 3`, and
`(1) a` / `(1) b` to `LeftRightParen`, both checked against the oracle.

**Still open: a marker per item.** The canonical rendering renumbers, so
a list crossing `9.` → `10.` needs a different marker (and pad) per item,
and `list_uniformity` still takes one marker for the whole list. The
hypothesis that step must discharge is now *visible and localized* rather
than hypothetical: in `run_item_sibling`, `narrow (ls_styles ls)
(mk_sty mrk)` has to stay nonempty. With one marker `narrow_mk_styles`
discharges it outright; with a marker per item it becomes the shared-style
condition, which is also the ordered-list canonicality condition. That
remains the next step, and the merge argued above still stands.

Everything else is unchanged: `make shape` 251/287, full-HTML 115/287,
generated corpus 694/796 — byte-identical to the previous commit, which
is what says the generalization did not move behaviour at a bullet.

## The canonicality condition, computed rather than argued

Before restructuring the chain for per-item markers, the question worth
answering is which ordered lists survive their own canonical rendering,
because that is the side condition `cb_ok` will carry. It is decidable
by the oracle, so `scratchpad/canon.mjs` decides it: build an
`ordered_list` AST at each style, start 1..30 and 1..4 items, render it
with `renderDjot`, parse it back, and compare.

**1200 triples, 100 failures, and every failure is alpha.**

| styles                       | failures                |
| ---------------------------- | ----------------------- |
| `1.` `1)` `(1)` (decimal)    | **none**                |
| `i.` `i)` `I.` (roman)       | **none**                |
| `a.` `a)` `(a)` `A.` (alpha) | 25 each, identical sets |

The alpha failures are at exactly these `start/count` pairs:

```
3/1 3/2  4/1  9/1  12/1 12/2  13/1  22/1  24/1  27/* 28/* 29/* 30/*
```

which is two independent causes, and the pattern confirms both exactly:

- **Ambiguity, escapable by length.** A letter that is also a roman
  digit (`c`=3, `d`=4, `i`=9, `l`=12, `m`=13, `v`=22, `x`=24) renders a
  marker `getListStyles` reads as both roman and alpha. The list is
  rescued as soon as one marker in the run is *not* a roman digit —
  `3/1` and `3/2` fail (c, d) but `3/3` passes (e arrives); `12/1` and
  `12/2` fail (l, m) but `12/3` passes (n); every other case escapes at
  the second item.
- **Wrap-around, not escapable at all.** `formatNumber` numbers alpha by
  `(num - 1) % 26`, so start 27 renders `a.` and parses back as start 1.
  Every count fails from 27 up. The renderer is lossy here; nothing on
  our side can fix it.

**What this changes.** The prediction earlier in this document — that
the condition is "exclude a single-item alpha list starting at 9" — was
right about the mechanism and much too narrow about the extent, and it
missed the wrap entirely. It also missed the sharpest fact, which is the
useful one:

> **Decimal and roman ordered lists need no canonicality side condition
> at all.**

So the roundtrip family should take ordered *decimal* lists first, with
`cb_ok` unchanged in shape — no guard, no exclusion, and the common case
covered. Alpha comes later and carries a two-part condition (`start +
count - 1 <= 26`, and at least one marker in the run not a roman digit),
which is worth stating only once alpha is actually wanted.

That also re-sizes the per-item marker step: for decimal the per-item
markers all carry the same singleton style set, so the narrowing
hypothesis the chain needs is discharged by the same argument that
`narrow_mk_styles` already makes, just applied per item rather than once.
The ambiguity machinery is only needed for alpha.

## Sizing the per-item marker step (attempted, reverted)

Tried the cheap version first and it does not work, which is worth
recording so it is not tried again.

**The idea.** The chain lives in `Section ListMarker` with `Variable mrk`.
Add a *second* variable `imk` for the facts about one item's marker, and
rename `mrk` to `imk` inside them. Rocq generalizes each statement over
exactly the variables it mentions, so at `End ListMarker` the item facts
would come out quantified over their own marker and the list facts over
`mrk` -- a per-item marker without moving a line.

**Why it fails.** Generalization happens at `End`, not before. *Inside*
the section both variables are fixed constants, so `run_item_sibling` is
a statement about `imk` specifically and the list-level lemmas -- which
are in the same section -- cannot instantiate it at `mrk`. The renaming
compiles right up to the first cross-boundary use and then cannot be
repaired without closing the section.

**What it actually costs, measured.** 103 mentions of `mrk` in the
section, but only **five lemmas and seven call sites** cross the
item/list boundary: `run_item_open`, `run_item_sibling`, `scan_loose_eq`
(these three mention the marker) and `scan_list_content_fields`,
`scan_list_content_blanks_last` (these two do not, and need nothing).
So the real shape is:

1. Close an inner `Section ItemMarker` after `run_item_sibling`, which
   means physically moving the item-level block above the list-level one
   -- the lemmas do not currently sit in dependency order.
2. The seven call sites then take an explicit marker, three of them plus
   the `marker_ok` proof.
3. `list_tail_lines` / `list_lines` / `item_ok` take a list of markers
   paired with the items, and `parse_list_tail`'s induction walks the
   pair.

Step 1 is the one with the diff, and it is a move rather than a rewrite.
Steps 2 and 3 are small once it is done. Nothing here is hard; it is
simply bigger than one sitting, and it should start from the file
reorganisation rather than from the statements.

### Outcome: decimal ordered lists are in the roundtrip

The last step landed as one change rather than the S2/S3 split this
document originally proposed, for the reason argued above.

**What went in.** `Parser.list_kind` (`LKBullet` / `LKDecimal d start`)
names the two flavours the canonical rendering produces, with `ck_first`
(the marker `item_ok` is asked for), `ck_items` (the markers the items
get), `ck_block` (the block the list closes to), and two theorems,

the bullet and decimal pairs that already existed. `CList` in `Render.v`
gained the kind; `cb_lines`, `cb_ast`, `cb_ok` and `render_block_lines`
route through `ck_items` / `ck_block`. Roman and alpha are excluded at
the type, not by a side condition -- which is what "decimal needs no
canonicality condition" buys.

**The prediction worth recording, because it was the load-bearing one.**
Written before starting: *the block layer acquires exactly one new
obligation per list case, and it is about markers rather than about
widths.* That held. The two list cases in `Roundtrip.v`
(`parse_canonical_list_end`, `parse_canonical_list_then_nonlist`) changed

term to the kernel. Render.v lost ~110 lines net while gaining the kind.
Worth stating as a rule: before writing a telescoping lemma to recover
`map` from an inlined fixpoint, check whether the fixpoint was needed --
it is needed only where the recursion goes through a *nested* list.

**Evaluation cost, measured because the datatype widened.** `Generate.v`'s
`gen_roundtrip_2` is 3.237s at this commit against 3.228s at the parent
on the same input -- unchanged, so the extra `ck_items` indirection in
`cb_lines` is free at `vm_compute`. (Checked per
[[project-engineering-lessons#`cbn` on a concrete `parse_lines` is a
build-time cliff]]; the answer here is a number, not an impression.)

**Coverage, which is the part that is not a proof.** 160 ordered
documents joined the generated corpus (`ordered_kinds` x
`itemlists (seqs leaves)` x two spacings, filtered by `cb_ok`), and all
160 match djot.js on exact HTML: 694/796 became 854/956, with the
mismatch count unchanged at 102. The starts are chosen to cross a marker
width boundary -- start 9 gives `9.` then `10.`, whose continuation pads
differ -- which is the case a single marker per list could not express
and therefore the one worth paying corpus for. `make shape` 251/287 and
full HTML 115/287 are byte-identical to the parent, which is what says
the kind did not move bullet behaviour.

**Still open.** Alpha and roman lists, which need `formatNumber` and the
two-part condition `canon.mjs` measured (`start + count - 1 <= 26`, and
at least one marker in the run not a roman digit). `render_block_lines`
returns `[]` for them today, in the same place the unimplemented
constructors do.

### Roman and alpha: the condition was over-strong, not the invariant

Probed before starting, and the probe changed the plan twice.

**First finding: roman is not a free instantiation, contrary to what
"decimal and roman need no canonicality condition" suggested.** That
sentence is about the *oracle* -- whether a rendering survives being
parsed back -- and says nothing about whether our `items_ok` can see it.
Two `Compute`s settle it:

```coq
Compute (mk_sty (MOrd "i" RightPeriod)).   (* [roman; alpha] *)
Compute (mk_sty (MOrd "ii" RightPeriod)).  (* [roman]        *)
Compute (items_ok (MOrd "i" RightPeriod)
           [(MOrd "i" RightPeriod, ["a"]); (MOrd "ii" RightPeriod, ["b"])]).
(* false -- while parse_lines ["i. a"; "ii. b"] gives OrderedList RomanLower 1 *)
```

A bare roman letter is also a single letter, so it offers two styles; a
longer numeral offers one. `items_ok` demanded the style *sets* be
equal, so it rejected a list the parser plainly accepts.

**Second finding, and the one that mattered: the over-strong thing was
that one conjunct, not the list state's invariant.** The obvious reading
of the first finding is that `ls_styles ls = mk_styles m0` has to become
a running narrowing -- the "candidate set that later items narrow" that
[[260809.container-uniformity]] called bigger than a parameter, and a
change to twelve statements. Reading the two consumers showed otherwise.
`run_item_sibling` already takes the weak hypothesis
`narrow (ls_styles ls) (mk_sty mrk) = ls_styles ls`, and
`parse_item_and_tail` used its `mk_sty m = mk_sty m0` in exactly one
place -- to derive that. The infrastructure was already stated at the
right generality; only `items_ok` was not.

**What went in.** `admits m0 m`, the boolean "every candidate the list
still offers is one this marker admits", replacing the set equality in
`items_ok`; `parse_item_and_tail`'s hypothesis weakened to the narrowing
identity it actually uses. One definition, one hypothesis, three proof
lines. `styles_eqb` / `styles_eqb_eq` / `narrow_mk_styles_agree` became
dead and were removed.

**What that reaches.** A run is covered exactly when its *first* numeral
is unambiguous, since a superset narrows to the identity -- so roman from
2 through the ambiguous `v.` is in (`roman_from_two_uniformity` is
`list_uniformity` at those markers, no proof of its own), and so is an
alpha list whose first letter is not a roman digit even when a later one
is. Left out: the run whose *first* marker is ambiguous, `i.` / `ii.`
being the shortest, recorded as a failing-by-construction pair of
examples.

**The measurement that says this was proof-side only.** `make shape`
251/287, full HTML 115/287, generated 854/956 -- all three identical to
the previous commit, which is what has to be true: `items_ok` is a
hypothesis, not a parser behaviour, so widening it cannot move a single
document. If any number had moved, the change would have been wrong.

**Still open, and now clearly two separate things.** (1) The ambiguous
first marker, which does need the running-narrowing invariant. (2) The
canonical side for roman and alpha: `roman_str` / `alpha_str` with their
inverses, and the alpha wrap condition (`start + count - 1 <= 26`).
Neither blocks the other.


# 260810: roman and alpha remaining work

What roman and alpha need

(a) Alpha codec — trivial. style_start for alpha reads one character (nat_of_ascii c - 96), so alpha_str n is a single character and the inverse is arithmetic. Roughly 20 lines.

(b) Roman codec — the genuinely hard piece. roman_value is a right-to-left subtractive scan; roman_str has to be the greedy 13-entry table, and roman_value (roman_str n) = n is an induction over greedy subtraction. There is a cheaper route: state it for n <= N and discharge by vm_compute. That is consistent with alpha, which already forces a bound into cb_ok because of the wrap past z. I would take the bounded route.

(c) The invariant weakening — I overstated this earlier and should correct it. I told you "twelve statements". The actual count is 5 lemmas, and the change is smaller than I implied, because list_block reads only the head of the style set:

| (SOrd n d, start) :: _ => mk (OrderedList (OLAttrs n d start) sp items)

So the invariant does not need to become a running narrowing. It needs to become "the head is stable", which is exactly what roman satisfies: i. has head (Roman,1), and narrowing by ii. filters to [(Roman,1)], head unchanged.

(d) Alpha's ambiguous starts need more than (c), and this is the expensive tail. An alpha list at start 9 renders i., j.. Here m0's head is (Roman,1) but narrowing by j. gives [(Alpha,9)], so the head changes. The list's resolved style is not a function of its first marker, and the conclusion of the uniformity theorem has to read the narrowed head rather than marker_list m0. That is a different theorem shape, not a weaker hypothesis.

The scoping consequence is worth noting: today's admits work already covers alpha at most starts, since a., b., e. are unambiguous. Only seven starts hit a roman-digit letter: 3, 4, 9, 12, 13, 22, 24. So (a)+(b)+(c) buys all of roman and all of alpha except seven starts, and (d) buys those seven.
