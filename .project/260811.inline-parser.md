# Plan: the inline parser

Phase 3 of [[260802.plan]], plus the inline half of [[beyond-djot]]. The
block layer is done through ordered lists and `roundtrip_doc` reaches the
parser's entry point; paragraphs are still one `Str` per line.

Three probes were run before writing any of this. One of them changes the
shape of the beyond-djot ask, and one of them says we cannot copy the
oracle's renderer.

## 0. Probes

### 0.1 `__a__` already means something in djot, and it is not strong

```
_a_         <em>a</em>
__a__       <em><em>a</em></em>
___a___     <em><em><em>a</em></em></em>
_a__b_      <em>a</em><em>b</em>
a_b_c       a<em>b</em>c
_ a_        _ a_          (literal: can_open wants nonspace after)
```

So the beyond-djot proposal: "`__` for strong as long as the strong
character differs from the emphasis character" is **not a conservative
extension**. `__a__` is a valid djot document today with a defined
meaning, and the extension changes it. That is fine, and it is exactly
what the "configurable, djot is one instance" framing is for, but it
moves the deliverable: the theorem cannot be "our parser extends djot",
it has to be "our parser is a table-indexed family, djot's table is an
inhabitant, and the extension table is another inhabitant satisfying the
same invariants". That is the Phase 4 shape arriving early, and §4 below
says why that costs almost nothing if the table is built in from step 1.

### 0.2 djot.js's *djot renderer* does not roundtrip nested emphasis

```
renderDjot(parse("__a__"))    djot.js:  _{_a_}_}     <- unbalanced
                              djoths:   _{_a_}_
reparse of djot.js's output:  <p>_<em>a</em>_}</p>   <- not the input
```

djot.js emits a spurious `}`; djoths is correct. This is a plain
upstream bug (djot.js is otherwise the authority per
[[oracle-disagreements]]), and it lands directly on our critical path:
`render_inlines` is what `roundtrip_blocks` will need to invert, and
`djot-renderer.ts` is therefore **not** a transcription source the way
`block.ts` was. The inline renderer has to be derived from our own
parser and proved, not transcribed and tested.

A second one found in step 2: `djot-renderer.ts` classifies `hard_break`
as a break tag (`:15`) but defines no handler for it, so `renderDjot`
**throws** on any document containing one. `a\` + newline + `b` cannot
be round-tripped by djot.js at all.

Worth filing upstream. Not logged in `oracle-disagreements.md` yet: that
log is scoped to corpus HTML, and this is a renderer axis it has no
column for.

### 0.3 The rendering of a delimiter is context-dependent

`a_b_c` renders as `a{_b_}c`, `_ a_` as `\_ a\_`, `_*a*_` as `_{*a*}_`.
So there is no "emit the delimiter" arm. Rendering an `Emph` is a
decision among three spellings (bare, braced, escaped) determined by what
sits on either side, which means the inline renderer is genuinely a
function of context, not a fold. This is the inline analogue of
`cb_ok`'s first-line-classifies condition, and it is where the canonical
view earns its keep.

## 1. Where the layer plugs in

The interface is already narrow, and this is the single most important
fact for sizing the work. The entire inline layer is two functions:

| function | file | callers |
| -------- | ---- | ------- |
| `para_inlines : list string -> inlines` | `Step.v:41` | 6 (`Step.v` x4, `Render.v` x2) |
| `inline_lines : inlines -> string -> list string` | `Render.v:503` | 2 (`render_block_lines`) |

and five lemmas connecting them:

- `inline_lines_para` (`Roundtrip.v:1080`): the inversion
- `para_inlines_wf`, `para_inlines_nonempty` (`Wf.v:311`)
- `para_inlines_one`, `para_inlines_cons2` (`Uniformity.v:92`): equations

Nothing else in 16k lines mentions inlines. `Roundtrip.v` reaches the
inline layer in exactly two proof cases (paragraph, heading). This was designed
for (see [[260808.roundtrip]] §"It splits blocks from inlines"), and it
is now the thing that makes the phase tractable.

**Prediction, at the obligation level** (per
[[project-engineering-lessons#Predict the falsifier at the right
granularity]]): across every step below, *no lemma about quotes, divs,
lists, fences or the line fold acquires a new hypothesis*. If one does,
the interface leaked and the step should be reconsidered before
continuing. Note what this does not claim: `cb_ok` **will** change (its
`CPara`/`CHeading` arms gain the inline obligation), and the two
`Roundtrip.v` cases **will** change. Those are the intended diff.

## 2. Architecture

### 2.1 A canonical inline view, mirroring `cblock`

`Render.v`'s recipe, "each new construct gets a `cblock` constructor, a
canonical rendering, and a `cb_ok` obligation", applies verbatim one
level down. New file `theories/Inline.v`:

```coq
Inductive cinline : Type := ...
Fixpoint ci_text (ci : cinline) : string.        (* the source *)
Fixpoint ci_ast  (ci : cinline) : node inline.   (* the AST *)
Fixpoint ci_ok   (ci : cinline) : bool.          (* canonicality *)
```

and `CPara` / `CHeading` hold `list (list cinline)`: one `list cinline`
per source line, so softbreaks stay where they are (the block layer owns
line structure; the inline layer owns within-line structure). The
inline roundtrip is then `parse_inlines (map ci_line ciss) = ...`, and
`roundtrip_blocks` consumes it as a lemma exactly where it consumes
`inline_lines_para` today.

The rejected alternative was to keep `CPara (ls : list string)` and add
`cb_ok` the boolean side condition `inline_lines (parse_inlines ls) == ls`.
It is one line, it needs no new inductive, and it is nearly vacuous: it
says "lines that roundtrip, roundtrip", `Generate.v` cannot enumerate
inhabitants of it structurally, and it proves nothing about the parser.

**The one signature decision step 1 must not get wrong.** By §0.3 a
`cinline`'s source text depends on its neighbours, so `ci_text : cinline
-> string` lifted to a line by `map`/`concat` is the wrong shape, and at
step 1, where the only constructor is `CIStr`, it is indistinguishable
from the right one. The line-level function is therefore written as a
**fold from the start**:

```coq
Fixpoint ci_line (cis : list cinline) : string.   (* not: concat (map ci_text cis) *)
```

A fold has somewhere to carry context; `map` does not. This costs
nothing at step 1 and is the difference between step 4 adding an
accumulator and step 4 rewriting the view. It is the same trap as
`PAttr` recording a line-local column
([[project-engineering-lessons#Probe the definitions a theorem already
constrains, too]]): invisible in the behaviour of the constructor that
motivated it, structural to repair later.

Which way the context-dependence is then discharged (an accumulator in
`ci_line`, a `braced : bool` field recorded in the constructor, or always
emitting the brace form) is deliberately **left open until step 4**, and
§5 says how to settle it. All three are compatible with a fold; only the
`map` version forecloses them.

### 2.2 A scope stack, not djot.js's splice-based match list

djot.js's `feed` builds a flat `Event[]` and then **mutates it
retroactively**: `addMatch(..., matchIndex)` splices over a placeholder
(`inline.ts:594`), `strMatches` downgrades a range to `str`
(`inline.ts:738`), `clearOpeners` discards openers spanned by a
completed match (`inline.ts:716`), and `reparseAttributes` re-feeds
already-consumed slices (`inline.ts:637`).

Only the last of those is backtracking, per the definition in
[[260802.plan]] under Non-goals: the first three re-annotate events
without re-reading a character. So the reason to prefer a scope stack is
**provability, not conformance**. It is not repairing a defect in the
oracle's algorithm, and the reformulation must preserve the retroactive
behaviour rather than eliminate it.

The equivalent formulation that is provable is a shift-reduce state: a
stack of open scopes each carrying its accumulated content. Closing a
delimiter pops; *abandoning* an opener flattens its scope into its parent
as literal text, which is what `clearOpeners` plus the default-match
placeholder amount to. This is the same move `Step.v` already makes for
blocks (`pstate` carries a container's accumulated lines rather than
patching an emitted tree), so the file has a precedent and the proofs
have a familiar shape.

**This equivalence is a claim about djot.js and must be probed, not
assumed.** It has been, ahead of step 4 rather than after it:
[[artifacts/260812.scopestack-probe]] leaves djot.js's matchers running
unmodified and replaces only `matches`, with an array that mirrors every
mutation into a scope stack; at `getMatches` the flattened stack is
compared to the flat array by object identity. Result below.

**The equivalence holds, and the stack needs four dispositions rather
than the two named above.** Zero order mismatches over the 293-document
corpus and ~580k generated strings (every string of length <= 6 over
seven delimiter-dense alphabets: emphasis, braces, verbatim and escapes,
math, smart quotes, brackets, image markers). What the probe added:

| disposition | djot.js | where |
| ----------- | ------- | ----- |
| close | `addMatch(..., matchIndex)` over the placeholder | everywhere |
| abandon: flatten placeholder + content into the parent | `clearOpeners` | everywhere |
| **discard**: drop the frame *and its content* | `matches.pop()` back to the opener | `]` when the opener is `[^` |
| **close below the top** | `clearOpeners` called *after* the close | link destination, span |

The last two are the finding, and both are confined to brackets:

- *Discard* is a third disposition, not a special case of the other two.
  The footnote-reference branch (`inline.ts:363-372`) pops every match
  back to the opener and relabels the opener's own placeholder, so the
  content of any frame opened inside is not flattened into the parent —
  it is destroyed. `[^a]` produces no superscript event even though `^`
  opened one. A stack model with only close and abandon cannot express
  this, and the probe found it as a pop into an empty frame.
- *Close below the top* means `close` may not assume it is closing the
  topmost frame: the destination and span branches emit the `+linktext` /
  `+span` over the placeholder before clearing the openers inside it, so
  `[x_y](x_y)` closes a frame with an open `_` frame above it. Closing
  therefore has to abandon what is above it first. Order came out
  identical once it does.

**For step 4 this is a clean pass**: on every alphabet without brackets,
zero anomalies of any kind, so the two-disposition stack is exactly right
for the delimiter family. The other two are step 6 obligations, and
worth carrying into its design now that they are named. Neither re-reads
input, so neither disturbs §2.4.

### 2.3 The matcher table, and where the branch factor goes

[[project-engineering-lessons#A hanging `Qed` under instant tactics]]
predicted this step by name: *"it fires next on the inline parser, which
will want exactly this shape for its delimiter table."* The rule from
that lesson is binding here: **one recursive call, with a table lookup
deciding what to do**, because the scanner will have on the order of
twenty dispatch cases and inlining them into the recursion makes every
general lemma about the scanner unprovable while every `Compute` stays
fast.

djot.js has already done the factoring for us: `betweenMatched(c,
annotation, defaultmatch, opentest)` (`inline.ts:103`) is one function
instantiated at `_ * ^ ~ = + - " '`. So the table is not a speculative
generalization; it is a transcription of a parameterization the oracle
ships. Per [[project-engineering-lessons#Check whether a proof uses the
structure before pricing its removal]], the cost of a table entry's extra
fields is the number of proof lines that *inspect* a delimiter rather
than carry it: expected to be the `can_open`/`can_close` tests and
nothing else.

### 2.4 No-backtracking: state it over re-reading, not over the state shape

[[260802.plan]] under Non-goals fixes the sense: what is forbidden is
tokenizing a region twice under different interpretations. The stricter
"scanner position strictly increases" is *not* the target, and reaching
for it is a live trap here, because it condemns the opener stack's
retroactive annotation along with the real offender, and would push the
design toward eliminating behaviour that is perfectly legitimate.

Structural recursion on the remaining input suffix still gives the
strict property for free wherever it applies, and it is worth taking for
free: it is a sufficient condition, locked in at step 1 while it costs
nothing, so every later matcher inherits it. What must not happen is
*stating the theorem* in that form.

The exception is real and should be named now rather than discovered:
`reparseAttributes` re-feeds a region already consumed. So the theorem to
state is *"the scan without attribute reparse is single-pass, and reparse
re-enters on a strictly shorter region with attributes disabled"*: a
second, decreasing measure. Stating it as "position strictly increases"
over the whole parser would be false, and per
[[project-engineering-lessons#Probe a theorem's shape]] that is the kind
of thing found after 200 lines of proof if it is not settled first.

## 3. Steps

Ordered by what the roundtrip needs, not by corpus payoff. Each step
names the obligation whose failure would change the plan.

**1. The canonical view, at today's behaviour.** `theories/Inline.v` with
one constructor (`CIStr`); `para_inlines` / `inline_lines` re-expressed
through it; `CPara` / `CHeading` widened. A pure refactor.
*Falsifier:* `make test` and `make generated` byte-identical, `make deep`
still passes, and no lemma outside the paragraph/heading cases of
`Roundtrip.v` and the `CPara`/`CHeading` arms of `cb_ok` changes. Also
where the scanner's structural recursion and its position theorem get
fixed, while both are trivial.

**2. Escapes.** `\` before punctuation. Smallest real construct, and the
one that makes the renderer *total*: without it, `ci_ok` on a `CIStr`
has to exclude every delimiter character, and the canonical set is
uselessly small. Do it before anything it protects.

**3. Verbatim.** Backtick spans, and with them `$`/`$$` math, which share
their machinery. Deliberately ahead of emphasis, and the reason matters
because the obvious one is wrong.

Verbatim is not a `betweenMatched` instance, where `betweenMatched`
(`inline.ts:103`) is the table djot.js already ships: nine rows, `~ ^ _ *
+ = ' "` and `-`. Four structural reasons, all checked against the
source and the oracle:

- *It is a mode, not a row.* `feed` tests `this.verbatim > 0` **before**
  dispatching to `matchers`, so an open verbatim suppresses the whole
  table: `` `_a_` `` is `<code>_a_</code>`. No row can say "while I am
  open, no other row fires".
- *It closes by run length, not by identity.* The closer must be a run of
  exactly N backticks, so ``` ``a`b`` ``` keeps the inner one as content.
  Every other djot delimiter matches by identity. This is the single
  exception to the "no run arithmetic anywhere" property that
  [[extension-decisions]] records as what djot bought by banning doubled
  delimiters, which makes it worth isolating rather than blending in.
- *Its content is flat.* `Verbatim (s : string)`, not `list cinline`: no
  recursion, and a `ci_ok` of a different shape from every container.
- *Three constructs share the mode.* `` $`x` `` and `` $$`x` `` reuse it
  through `verbatimType`, popping the `$` matches retroactively.

None of that means the *final* table cannot cover it. [[beyond-djot]]
asks for a general inline-container notion where delimiters and
precedence are user-specified, and a table carrying "nests / suppresses
others / matches by length" plausibly subsumes verbatim. That is an open
design question, and step 4 is where it gets answered.

**Which is the actual reason to do verbatim first.** It is the instance
*least* like emphasis. Built first, step 4 designs the table's field set
against the two most different cases at once; built after, the fields fit
emphasis and verbatim is retrofitted into them. That is
[[project-engineering-lessons#Check whether a proof uses the structure
before pricing its removal]] applied before the generalization exists
rather than after.

It also forces the "content that would close me" question. The block
layer answered that by *exclusion* (`cb_ok` forbids a code block whose
content contains the fence); the inline layer must answer it by *widening
the fence* (`` `` ` `` `` renders at width 2), which is the first place
the renderer computes rather than escapes.

**4. The delimiter table and the emphasis family.** `_ * ^ ~`, then the
braced `{= =}` `{+ +}` `{- -}` and smart quotes, which come free once the
table exists (all nine are `betweenMatched` rows already). The `{...}`
explicit-marker rendering from §0.3 lands here.

This step owns the question step 3 leaves open: whether the table
subsumes verbatim, or whether verbatim stays a mode alongside it. Decide
it with both constructs already written rather than by anticipation, and
if the answer goes beyond what djot does, it is an
[[extension-decisions]] entry.

*First* deliverable of this step is the §2.2 equivalence probe against
djot.js on the corpus, before any proof.
*Falsifier:* adding the second through eighth table entries adds no new
lemma: only rows. If entry two needs a lemma, the table's fields are
wrong and it is cheaper to find out at entry two than at entry eight.
`--shape` mode in the harness should be deletable at the end of this
step; that is the measurable milestone.

**5. No-backtracking and locality, stated and proved.** On the step-4
scanner, before brackets bring the reparse exception in. Locality is
about *classification*: the tree shape is a function of the inline text
alone, and the reference/note maps only fill in targets. The plan doc
already flags getting this scope wrong as a way to spend a long time
proving a falsehood.

**6. Brackets.** Links, images, spans, footnote references, autolinks,
and with them the attribute reparse, the `destination` mode, and
`pendingSpan`'s retroactive downgrade. The genuinely hard step; the
locality statement from step 5 becomes load-bearing here because this is
where the reference map enters. Expect this to be as large as steps 1-5
combined.

**7. The config knob and the beyond-djot table.** §4.

Steps 1-3 are small and mostly mechanical. Step 4 is the design. Step 6
is the volume.

## 4. Beyond djot: what the table buys, and what it still owes

The table from §2.3 is needed for djot alone. Making it a *parameter*
rather than a constant is the whole of the extension mechanism, and by
§0.1 it has to be a parameter anyway, because the extension is not
conservative.

What must be proved for the family, and is the actual research content:

**Conflict-freeness is the side condition.** With multi-character
delimiters, a run like `___` must resolve, and `____` must too (djot
already excludes empty emphasis: `opener.endpos !== pos - 1`,
`inline.ts:141`, so `__` `__` is not nested-empty but something else).
The user's proposed rule, *strong character differs from emphasis
character*, is a **sufficient condition** for a table whose delimiters
are prefix-free per starting character. That is the theorem to aim at:
`delims_conflict_free T -> ` (scan deterministic, renderer inverts it),
with djot's table and the `__`/`*` table both instances. The proposed
rule then becomes a checked corollary rather than a design assumption.

**There is no oracle here.** By construction: this is behaviour djot
does not have. So [[project-engineering-lessons#Ask the oracle]] does not
apply, and its replacement is [[extension-decisions]]: djot's baseline
pinned first, then every decision pinned by an `Example` rather than by
prose. Opened with the baseline table and entry `E1`; the `___` and
`____` readings are its open sub-questions, and `____` is flagged to
check first because it is the case most likely to show that djot's
empty-emphasis exclusion does not generalize to multi-character
delimiters.

**Not in this plan.** Setext headings and optional-blank-before-sublist
are block-layer asks from [[beyond-djot]] and belong with the block
parser. Link references are listed as still-thinking and are step 6's
business at the earliest.

## 5. What could go wrong

- **Step 4's equivalence probe fails**, i.e. the scope stack and
  djot.js's splice-based mutation genuinely differ somewhere. Then §2.2
  is wrong and the choice is: match the oracle with a harder formulation,
  or diverge and log it. Finding this at step 4 costs a probe; finding it
  at step 6 costs the phase.
- **`ci_ok` turns out to be non-compositional**: the context-dependence
  from §0.3 means a `cinline`'s canonicality may depend on its
  *neighbours*, which `forallb ci_ok` cannot express. This is the one
  place the `cblock` recipe may not transfer cleanly. §2.1 keeps all
  three repairs open; the way to choose is to notice that the roundtrip
  does **not** require a minimal rendering. `_a_` and `{_a_}` both parse
  to `Emph [Str "a"]`, so *any* always-safe spelling satisfies
  `parse (render d) = d`, and the brace form is always safe: that is
  what djot has it for. So the cheap path is: take the brace form as
  canonical, get the theorem, then narrow to the bare form as a
  *refinement* with its own proof. Worth resisting the urge to do the
  pretty version first; the block layer already made this trade the other
  way (`CCode` fixes the fence at three and `cb_ok` excludes content that
  would close it early) and it is the same trade.
- **Step 6 is unbounded.** If it is, steps 1-5 stand alone as a result
  and the phase can be declared at "inline emphasis and verbatim, proved;
  brackets pending", which is a real checkpoint.

## 6. Progress

### Step 1, first half: landed

`theories/Inline.v` exists. It holds the canonical view (`cinline`,
`ci_line`, `ci_ast`, `ci_ok`, `cis_ok`, `ci_para`), the pass
(`parse_inline_line`, `para_inlines`), the renderer (`inline_lines`), and
both bridge theorems:

- `para_inlines_ci_para`: parsing a canonical paragraph's text gives its
  inlines, given `cis_ok` per line and `para_ok`'s trailing-whitespace
  conjunct.
- `inline_lines_ci`: rendering those inlines gives back exactly the
  canonical lines.

`para_inlines` and `inline_lines` moved out of `Step.v` and `Render.v`
unchanged. Behaviour preservation is *definitional*, not tested:
`para_inlines_one` and `para_inlines_cons2` still hold by `reflexivity`,
which is what says the new spelling is the same term. Confirmed against
the falsifier: `make shape` 251/287, full HTML 115/287, generated
1238/1340, all three byte-identical to the recorded baseline, and no
proof anywhere else changed (three files gained `Inline` in their
`Require` line, and that is the whole diff outside the new file).

`ci_line` threads `option ascii` (the byte to the left), settled per §2.1
and justified by `inline.ts:110-112` rather than by hedging: djot's
`can_open` / `can_close` each read exactly one neighbouring character, so
one byte on each side is the whole of the available context.

### Step 1, second half: landed

`CPara` and `CHeading` now hold `list (list cinline)`. `cb_lines` goes
through `ci_line`, `cb_ast` through `ci_para`, and `cb_ok` splits into a
block obligation on the rendered lines (`para_ok` / `heading_ok`,
unchanged) and an inline one per line (`cis_ok`). The two `Roundtrip.v`
cases now rest on `para_inlines_ci_para` and `inline_lines_ci`, reached
through two named bridge lemmas (`cb_ast_para_of_lines`,
`cb_ast_heading_of_lines`) so that the seam has a name rather than being
inlined into a tactic block.

**The §1 prediction held.** No lemma about quotes, divs, lists, fences or
the line fold acquired a hypothesis, or changed at all: the diff outside
the paragraph and heading cases is the `cpara` / `cheading` rewriting of
examples. That is the measurement the prediction was for, and it is what

Behaviour unchanged again, on every check available: `make shape`
251/287, full HTML 115/287, generated 1238/1340, `make probe` clean, and

last one is the sharpest of the five: it says widening `cb_ok` with the

Six proof cases changed, in two shapes. Cases that mention only

`cpara` / `cheading` are the plain-text smart constructors that absorbed

faithful.

### Step 2, escapes: landed

**Escapes add no `cinline` constructor**, which was not the plan's
assumption. `\*` and a bare `*` where nothing opens both parse to
`Str "*"`, so the AST cannot tell them apart. An escape is the *spelling*
a `CIStr` needs to survive reparsing, so step 2 is a pair of string
functions (`escape_str` / `unescape`) and one theorem, `unescape_escape`.

`needs_escape` is the growth point: today just the backslash, and every
construct that claims a delimiter adds its character. Two named
obligations keep it sound, `needs_escape_punct` (an escaped character
must be one the decoder accepts) and `needs_escape_backslash` (the escape
character escapes itself). A later construct re-proves those two and
nothing else.

Corpus 115 -> 119 of 287; shape and generated unchanged, as expected
since escapes touch neither block shape nor the generator's
backslash-free content. `make deep` green, `accepted_counts` unchanged.
All five remaining `escapes.test` failures are hard break (4) and
non-breaking space (1), the two readings deliberately left out: both are
distinct AST nodes rather than escapes, and neither can arise from a
canonical rendering, since `escape_str` never emits a bare backslash.

**The prediction failed, in two files, and that is the useful part.**
"Step 2 changes no file except `Inline.v`" was wrong:

- `Render.v`: `cb_lines_cpara` read `cb_lines (cpara ls) = ls`, which
  escapes falsify. Now `= map escape_str ls`, unconditionally true and
  still reading as `= ls` for every backslash-free example. The lemma was
  written in step 1 with no consumer, precisely as a drift detector, and
  it detected drift on the next step.
- `Wf.v`: `para_inlines_wf` needed `unescape_nonempty`, because a `Str`
  must be nonempty and the parser now decodes before building it.

So the block/inline interface is **not** the three names `ci_line`,
`ci_para`, `cis_ok`. It is those three plus two properties other files
consume: that a plain-text line renders to itself, and that parsing
preserves nonemptiness. Both repairs were one lemma, so the seam is in
the right place; but the honest statement of what a later construct must
check is the properties, not the names. Steps 3 and 4 should predict
against that list rather than against "no file changes".

### Step 3a, the scanner and verbatim parsing: landed

Split from step 3b (verbatim in the *canonical view*) partway through,
once the shape of 3b's proof became clear. 3a is the parser half: the
scanner exists, verbatim parses, and the corpus responds. 3b adds
`CIVerb` to `cinline` so the roundtrip covers it.

**The scanner is character-at-a-time and structurally recursive** on the
remaining input. What that buys is termination and a flat cost model, and
it happens to also give "never re-reads a character".

That last property is **stronger than Phase 3 wants, and must not be
treated as the goal** (§2.4, as corrected): it is the exact over-strict
reading that would condemn the opener stack's retroactive annotation.
Recorded here because the trap is live at step 4 and this scanner is what
step 4 extends. `istep` today only ever appends to `out`, so nothing yet
depends on the stronger property; when the delimiter table needs to

allow it, and that is a legitimate change rather than a defect to design

Four states: `IText` (with a pending-backslash flag), `IOpen`

and it is what lets `` ` `` ` `` hold two backticks inside a one-backtick

### Step 3b, verbatim in the canonical view: landed

`CIVerb (s : string)` now closes the parser/renderer/proof loop, with:

- `verb_ticks s` = the least positive integer that is *not* a backtick
  run length in `s` (djot.js `verbatimDelim`, djot-renderer.ts:27, which
  starts at 1 and increments while the length occurs). Verified against
  the oracle: `"a"` -> 1, `` "`" `` -> 2, ``` "``" ``` -> 1, ``` "` ``" ```
  -> 3.
- `pad_verb` / `trim_verb`: one space at each end, but only against a
  backtick (`trimVerbatim`, parse.ts:57). `` ` a ` `` really is `" a "`.
- `ci_ok (CIVerb s)` must exclude content starting `" `"` or ending
  `` "` " ``, since `trim_verb (pad_verb s)` loses those. That is
  *accuracy, not compromise*: `trimVerbatim` never outputs such a string,
  so they are outside the parser's image.
- `cis_ok` must exclude **adjacent** `CIVerb`, for the same reason
  `no_adjacent_lists` exists at the block level: two renderings
  concatenate into one longer run, which reparses as a single span. Also
  unreachable for the parser, so also accuracy. `no_adjacent_ci_str`
  generalizes to a pairwise `ci_sep_ok`.

The proof has exactly the two-state shape predicted here:

### Step 4b, the delimiter table and the scope stack: landed (parser side)

Six rows -- `_ * ^ ~` unbraced, `= +` braced-only -- through one lookup
and one recursive call, per the branch-factor rule. The hyphen and the
two quote characters are left out: each carries a *second* construct on
the same character (smart dashes, smart quotes), and adding a row is
cheap where adding a construct is not.

The scope stack is as §2.2 predicted, and the probe's four dispositions
came out exactly where it said: close and abandon are both here, discard
and closing-below-the-top are not reachable from this table. Three
things the probe did not cover, all found while writing it:

- **A pending delimiter needs the byte after it**, so `IDelim` is a
  state, like `IOpen` for a backtick run. `can_close` is decided from the
  byte before, `can_open` from the byte after, and a `}` immediately
  after forces the close. `{` needs the same treatment (`IBrace`), and a
  *marked* delimiter needs no lookahead at all -- djot.js forces
  `can_open` and blocks `can_close` for it, so `{_` opens on sight.
- **Abandoning has to merge its seams.** An abandoned opener decays to a
  `Str` of its own source text, which lands between two runs that may
  themselves end and start with `Str`. `no_adjacent_str` is not a
  tidiness convention -- it is what the renderer inverts -- so `oapp`
  merges one seam and `osnoc` the other. That merge is attribute-aware,
  because `plain_str` is: a `Str` carrying attributes is a node in its
  own right.
- **The marking is part of the opener key.** `{_a_` does not close and
  `_a_}` does not either, both decaying to text. This is what makes the
  braced form a *context-free* spelling, which is why it is the one the
  canonical view will use.

### Next: step 4c, the delimiter in the canonical view

The parser reads the family; the renderer does not write it yet, so
`cinline` still has no delimiter constructor and `needs_escape` claims
the six characters and the two braces to keep `CIStr` text literal.
`CIDelim (k : dstyle) (kids : list cinline)` next, with the braced
spelling as its canonical source -- it is the only spelling that is a
function of the constructor alone, and §0.3's three-way choice is then an
optimisation to prove later, against this as the reference.

Started and backed out rather than left half-done; the tree is at the
parser-side commit. What the attempt established, so the next run does
not rediscover it:

**The nesting is cheap; the composition is not.** `cinline` becomes a
nested inductive through `list cinline`, so `ci_src`, `ci_ast` and
`ci_ok` each inline their own list recursion the way `Wf.wf_inline`
does. Each then needs one equation lemma to fold the anonymous `fix`
back into the named list function (`ci_text`, `ci_inlines`, `cis_ok`),
proved by `cbn` followed by an `assert` that states the `fix` verbatim
and an induction. That is mechanical and about forty lines.

**Drop `ci_text`'s `prev` parameter while doing it.** It exists to let a
delimiter's spelling depend on its neighbours, and the braced spelling
does not, so `ci_text` becomes a plain fold and `ci_text_prev` goes
away. `str_last` stays -- the *scanner* needs it for `can_close`. Put
`one` above the table, since `ci_src` needs it.

**The real work is restating `iscan_cis` in a composable form.** Today
it is stated over a stack-free `OState out []` and ends the scan; a
`CIDelim` needs the induction hypothesis to apply *inside* a pushed
scope and to hand the closer to the inner call. The shape that does
both:

```coq
Lemma iscan_cis_app :
  forall cis rest txt prev o,
    cis_ok cis = true -> text_sep_ok txt cis = true ->
    starts_tick rest = false ->
    exists p,
      iscan_str (ci_text cis ++ rest) (IText false txt prev o)
      = iscan_str rest
          (IText false EmptyString p
             (oemit_all (ci_inlines cis) (flush_text txt o))).
```

Three things make it work, each checked before the attempt was backed
out. The `starts_tick rest = false` side condition is what lets a run
ending in a `CIVerb` compose: the pending closing run is resolved by the
next byte, and a backtick would lengthen it instead -- the closer
`dchar k` is never a backtick, so it discharges by computation. The
existential `p` is sound because the *closer* never consults it: `_}`
sets `marker`, and `idelim_resolve` ignores `canclose` when `marker` is
set. And the `CIDelim` case then runs `{` -> `IBrace`, `dchar` ->
`ibrace_step` pushes the frame, IH on `kids` with `rest` the closer,
then `dchar` + `}` -> `oclose`, whose `oclose_go` finds the frame at the
top with `content = oapp [] (fr_out f)` and `List.rev (List.rev _)`
cancelling to `ci_inlines kids`.

`oemit_all` (emit a list of nodes in order into an `ostate`) is the one
new definition, and it needs lemmas relating it to `opush` and `oclose`.
`inline_lines` gains a delimiter case, and `iscan_cis_closed` gains one
that follows from the frame being popped.
