# Plan: definition lists

Everything in §1 was measured against djot.js on 2026-08-22, djoths
where it says so.  Nothing is read off the prose spec.

## 0. What this construct is

**A definition list is not a construct.**  It is an ordinary list whose
marker style happens to be `:`: `getListStyles` returns `[":"]` for it
alongside `-`, `*`, `+` (`block.ts:9-11`), the same `list`/`list_item`
containers open and continue, and the only thing that distinguishes it
is one arm at `-list` (`parse.ts:824`) and one at `-list_item`
(`parse.ts:883`).

That is the whole shape of this step, and it is why the step is small.
Nothing new opens, continues or closes; a marker character joins a set,
and the fold a list already runs at close gains an arm.  Two consequences
worth naming before they look like coincidences:

- **The tightness quirk is free.**  A blank line inside a definition
  arms the *definition list* rather than the bullet list enclosing it
  (§1.4), because the blankline handler only reaches the tip container
  or its parent and a `dl` is a list.  Our own rule already arms the
  innermost list, so this reproduces without a line.  A separate
  `PDefList` state would have had to reproduce it by hand.
- **The term rule is a fold over what the item already emitted**, not a
  revision of it, exactly as the table's header rule was
  ([[260821.tables]] §2.2).  No state ever revises an emission.

## 1. What the oracle does

### 1.1 The marker

`:` is in `pattListMarker` (`block.ts:59`) and needs one space, tab, or
end of line after it.

| line | verdict |
| --- | --- |
| `: a`, `:` + tab + `a`, `:   a` | definition list |
| `:` alone, `: ` | a list with one empty item |
| `:a` | paragraph |
| `:: a` | paragraph -- `getListStyles "::"` is empty |
| `::: a`, `:::`, `:::: a` | div |

`div_open` already precedes `list_marker` in our `classify`, so the last
row costs nothing.

Every other property is the list machinery we have: `:` does not
interrupt a paragraph (`p` / `: a` is one paragraph); `: a` after `- b`
starts a *separate* list, since the styles do not intersect;
continuation is `indent > marker indent`, so one space suffices; a `:`
list nests in a quote or an item with no special handling; `{#i}` on the
line above attaches to the `<dl>`.

### 1.2 Term and definition

At `-list_item`, if the item's first child is a paragraph its *inlines*
become the term and the paragraph is dropped; otherwise the term is
empty and nothing is dropped (`parse.ts:883-900`).

| input | result |
| --- | --- |
| `: a` / blank / `  d` | `dt a`, `dd` holding `<p>d</p>` |
| `: a` / `  d` | one paragraph, so `dt a<br>d` and an empty `dd` |
| `: # h` / blank / `  d` | empty `dt`, heading and paragraph both in `dd` |
| `:` / blank / `  d` | **`dt d`** -- the term is the first paragraph wherever it starts |
| `: {#i}` / `  t` | `dt t`: the term takes inlines, so the attribute is dropped |
| `:` | one item, empty term, empty definition |

The fourth row is the one that constrains the canonical view (§4.1).

### 1.3 Tightness is not a property of a `dl`

djot.js's `definition_list` node carries **no `tight` field**, where
`bullet_list`, `task_list` and `ordered_list` all do
(`parse.ts:824-857`).  The HTML renderer's `tight` is rendering state
that a node overrides only if it *has* the field (`html.ts:140-148`), so
a `dd` inherits the tightness in force:

- at top level, loose: `: a` / blank / `  d` gives `<dd>\n<p>d</p>\n</dd>`;
- inside a tight bullet item, tight: `- : t` / blank / `    d` / `- x`
  gives `<dd>\nd\n</dd>`, and the outer list stays tight.

**djoths disagrees**, and on the commonest shape of all: it computes a
spacing for the `dl` and renders the first case as `<dd>\nd\n</dd>`.
With two items separated by a blank the two agree.  djot.js is the
authority; this wants an `oracle-disagreements.md` entry.

### 1.4 A blank inside a definition does not loosen the list outside it

`- : t` / blank / `    d` / `- x` keeps the *bullet* list tight, where
`- a` / blank / `  c` / `- b` does not.  The blankline handler looks for
a container with a `tight` field at the tip or one below it
(`parse.ts:1197-1205`); inside a definition it finds the `dl`, sets the
flag there, and `-list` then discards it.  §0 says why we get this free.

## 2. The change

### 2.1 `sp` stays on `DefinitionList`, and the reason is the roundtrip

`Ast.v` has `DefinitionList (sp : list_spacing) items` transcribed from
djoths.  §1.3 says no rendering may read it: `Html.v` must render a `dd`
at the *incoming* `tight`, so the field is invisible in HTML and the
corpus can never catch a wrong value.

The reflex is to delete it.  That is wrong, and the reason is
[[project-engineering-lessons#Probe the definitions a theorem already
constrains, too]] one level up, the `cblock` list: the canonical view
spells a list as `CList k sp items`, and `render_cb_lines` says the
renderer recovers `cb_lines` from `cb_ast`.  Drop `sp` and a `CList
LKDef Loose items` and a `CList LKDef Tight items` render to different
lines and the same AST -- `cb_ast` non-injective, `render_cb_lines`
false, which is exactly the wall the source-shaped `CTable` hit.

So the field is not unverifiable after all.  It is unobservable in HTML
and pinned by the roundtrip, which is a sharper statement than either
oracle makes, and it is what lets a definition list be a plain
`list_kind` rather than a fourth kind of thing.

### 2.2 The parser

1. `Line.is_bullet` gains `:`.  `list_marker ": a"` then yields
   `[SBullet ":"]`, and `:: a` still fails, since the character after
   the marker is not whitespace.
2. `Step.list_block` and its mirror `Marker.styles_list` gain an arm:
   a style set headed by `SBullet ":"` closes to
   `DefinitionList sp (def_items items)`.
3. `def_items : list blocks -> list (inlines * blocks)` is §1.2's rule,
   a `map` of a two-case match on the head block.

**Obligation prediction.**  No statement acquires a new hypothesis, with
one exception named below.  `is_bullet_cases` gains a fourth disjunct
(three users).  `supported` gains a `DefinitionList` arm and
`supported_list_block` *stays an equality*, because `supported (Para _)`
is `true` and dropping a leading paragraph therefore changes nothing.

The exception is `wf_list_block`, which is an equality today and cannot
stay one: an item `[Para []]` is ill-formed as a bullet item and
well-formed as a definition, since `wf_def_items` asks nothing of the
term's nonemptiness.  It becomes an implication in the direction its one
user needs.  That is the whole cost, and it is [[project-engineering-
lessons#Check whether a proof uses the structure before pricing its
removal]]: one user, `rewrite` becomes `apply`.

### 2.3 `Html.v`

`Html.v:311` is a `TODO Phase 1` stub.  `<dl>`, then per item `<dt>`
inline `</dt>` and `<dd>` newline blocks `</dd>`, rendered at the
incoming `tight` and ignoring `sp` (§1.3).  `render_block_foot` needs
the same arm threading the counter, which is the bug the table step
found on the same line: a footnote reference inside a definition would
otherwise be dropped.

### 2.4 `Document.v` is real work here, unlike the table's

A table holds inlines, so [[260821.tables]] §5 was a comment.  A
definition holds *blocks*, so every pass that walks the tree needs an
arm: `assign_ids`, `collect_notes`, `undo_pass_block`, `notes_free`,
`pristine_block` -- five, each with an equation lemma, plus the
`hdlist` case of `block_ind2`.  Priced as its own step.

## 4. The canonical view, before proposing it

`ck_block`, `ck_items`, `ck_first`, `ck_ok` is the four-piece interface
a `list_kind` implements (`OrderedList.v:1304`), and `LKDef` fills it
in: `ck_first` is `MBullet ":"`, `ck_items` is `same_marker` at that
marker, `ck_block sp items` is `DefinitionList sp (def_items items)`,
and `ck_ok` is `true` -- there is no numbering and so no range.

Two things to probe before writing any of it.

### 4.1 The unrepresentable item

§1.2's fourth row says an item with an **empty term whose definition
begins with a paragraph** cannot be written down: whatever paragraph
comes first becomes the term.  No spelling escapes it -- an attribute
line in front attaches to that paragraph and is then dropped with it.
So `ck_ok` alone is not enough and `cb_ok`'s list case needs a condition
on item *contents* for the first time.  Probe whether it is cheaper to
state as "every `LKDef` item's first block is a paragraph", which is
what a canonical rendering would produce anyway.

### 4.2 What `para_ok` loses

`:` is not in `Inline.needs_escape` and should not join it -- it is not
a delimiter and the scanner does not dispatch on it -- so a canonical
paragraph line beginning `: ` renders unescaped and reparses as a list.
`para_ok`'s `is_text` already rejects it once `classify` calls it
`KList`, so this is a shrink in the canonical set and not a soundness
hole.  It is the same cost `-`, `*` and `+` already pay.

## 5. Open questions

- Whether `def_items` should be shared between `Step.v` and
  `OrderedList.v`'s `ck_block` or spelled twice.  Sharing means the
  canonical view and the parser cannot drift; it also means `Step.v`
  depends on a definition that belongs to the roundtrip layer.  Decide
  by where it reads better once step 1 is written.
- Task lists are the same shape (`- [ ]`, three corpus cases) and share

## 6. Progress

All four steps landed on 2026-08-22.

### Steps 1 and 2: the parser, and the passes that walk it

`Line.is_bullet` claims `:`, and that is the whole of the recognizer:
`list_marker ": a"` yields `[SBullet ":"]`, `":: a"` stays `KText`
because the character after the marker is not whitespace, and `"::: a"`
is a div because `classify` tests `div_open` first.  `Step.list_block`
and `Marker.styles_list` gained one arm apiece, spelled as a test on the
character rather than as a pattern so a proof holding an unknown bullet
cases on it in one step, and `Ast.def_item` is the split.

**One obligation the plan predicted, and one it did not.**
`is_bullet_cases` gained its fourth disjunct (three users, one line
each) and `wf_list_block` became the implication §2.2 said it would --
one user, `rewrite` to `apply`.  `supported_list_block` stayed an
equation, also as predicted.  What was missed is
`Line.marker_open_shape`, which proves `div_open (mk_open m ++ l) =
None` from "the first character is not a colon"; with `:` a bullet that
premise is false and the conclusion still true, so the conjunct became
`div_open (String c r) = None` outright and `div_open_not_colon` supplies
it for the alphanumeric cases.  That is
[[project-engineering-lessons#Check whether a proof uses the structure
before pricing its removal]] read backwards: the proof used the
character, not the fact.

`Document.v` was the larger half and exactly the five passes §2.4
listed, plus `block_ind2`, which gained a fourth predicate `D` -- a
definition list holds a list of *pairs*, which is not `R`'s type, and
the term half contributes no hypothesis.  Six `induction ... using
block_ind2` sites each took a `(D := ...)` and two cases.  Without it
`: # h` renders a heading with no auto-identifier, which is what the
step is for.

**Measured.**  Corpus **269 -> 275/287**, `--shape` **281 -> 287/287**:
block structure is now complete, and all twelve remaining exact-HTML
mismatches are inline (attributes 6, headings 1, links 2) or task lists
(3).  `definition_lists.test` is 6 of 6.

### Step 3: the canonical view, at the cost of a `list_kind`

`LKDef` fills the four-piece interface and the two uniformity theorems
took three lines each, because `list_uniformity_same` already quantifies
over the marker and `marker_list colon` *is* the `DefinitionList` arm of
`styles_list` -- the same arm the parser goes through.  §4.1's worry did
not materialize: it was about a `list (inlines * blocks)` representation,
and `ck_block LKDef sp items = DefinitionList sp (def_items items)`
makes the view's image the representable set by construction, so the
unrepresentable item cannot be spelled rather than having to be excluded.

Two conditions were needed, and the generated corpus found the second
one rather than the plan:

- `render_ck_list` gained `ck_render_ok`, since `def_item` drops a
  leading paragraph and an *empty* one would lose a line.  Nothing
  canonical spells one (`ci_para_nonempty`), so it is a hypothesis
  discharged from `cb_ok` rather than a clause in it.
- **`def_split` steps over reference and footnote definitions.**  Both
  oracles read `: [r]: u` / blank / `t` as having the term `t`: djot.js
  has already moved both kinds out of the tree before `-list_item` runs,
  so neither can be `children[0]`.  We keep them as blocks, so the search
  has to skip them -- and then the term sits behind the definition in
  the source and in front of it in the rendering, two spellings of one
  AST.  `cb_ok` picks the renderer's, which is the one new clause
  (`ck_content_ok`).  Three generated mismatches found this; there is no
  corpus case for it.

**Measured.**  The generated corpus grows 4612 -> 4742 with zero
mismatches, and the roundtrip is 31272 documents at depth 3, also zero.
Both denominators moved for a second reason worth recording: a canonical
paragraph line may no longer begin `: `, which is the same cost `-`, `*`
and `+` already pay and the reason the depth-3 pool shrank from 34496
before this step.
