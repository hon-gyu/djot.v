Background: what "tight" means

A djot list is tight or loose. The distinction is purely a rendering one, and it shows up in the HTML as whether item contents are wrapped in <p>:

tight → no <p>loose → <p>
<li>
a
</li>
 
<li>
<p>a</p>
</li>

The syntax reference states the rule:

A list is classed as tight if it does not contain blank lines between items, or between blocks inside an item. Blank lines at the start or end of a list do not count against tightness.

Why this reads as a bug, not a design choice

Three controls, each one line away from the witness. If djot.js were applying some principled rule like "a blank line before a container belongs to that container", all three would behave the same way. They do not.

Identical, and loose. Same blank line, same position; only the block type in the second item changed. A heading or a code block behaves the same way. Only a nested list suppresses the looseness.

Control 2: add an earlier blank → djot.js says loose

- a

- b

- - n

Both engines return loose here (a and b both get <p>). So djot.js is not blanket-ignoring blank lines in this document. It is specifically swallowing the one blank immediately before the list-opening item. The bug is local to that adjacency.

Control 3: the intra-item case, which is not the bug

- a

  - b

Here the nested list is indented inside the same item, so the blank line falls between two blocks of one item. Both engines, and we, call this tight:

Against the syntax reference alone this looks like an unexplained deviation, since the prose says a blank between blocks inside an item makes the list loose. The djot repo's own rationale (README, Rationale) states it outright: a sublist "must always be preceded by a blank line", and "(This blank line doesn't count against 'tightness.')". It is a consequence of goal 7, which forbids block elements from interrupting paragraphs and so forces the blank in the first place. Control 3 is decided, with a reason, not a gap.

The mechanism, and where the justification runs out

djot.js emits a blankline match and then excludes a following +list event from "spending" it. That exclusion is what makes Control 3 come out tight, which is intended. The same code path fires at a sibling boundary, and that is the leak.

The exemption in Control 3 reaches exactly as far as the requirement that creates it: the blank is mandatory there. Nothing requires a blank before a sibling item. Drop it from the witness and the document still parses:

So djot.js is extending an exemption to a position where its justification does not reach: the blank is optional there, which makes it a deliberate authoring signal, and djot.js discards it.

Which source settles what

The engines and the syntax reference record what the language is. The rationale records what it is for, and that is what turns "djot.js differs" into "djot.js is wrong" here. It is not a spec, though, and the two rationale sources are not equal: the repo README is the project's own, while Beyond Markdown is a 2017 essay predating djot whose tightness rule (:254, "tight if it contains at least one pair of items with no blank line between") was dropped. Both engines contradict that essay on its own worked example. Cite the rationale for principles, never for behaviour.

Corroborating: zero of djot.js's 26 test files contain an item, a blank line, and then an item beginning with a nested marker. The shape is untested upstream, so nothing pins the behaviour.

Verdict

Recorded as djotjs-bug. We keep our behaviour: it matches the prose and it matches djoths. This overrides the log's standing default of treating djot.js as the authority. That default exists because djoths lags on syntax changes, which is not a reason djot.js cannot have a plain bug.
