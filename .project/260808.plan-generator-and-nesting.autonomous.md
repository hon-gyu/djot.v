## What the probes already established

All of this is machine-checked, from `Compute`/`reflexivity` runs against
`main` (`7ed0faa`) as of 2026-08-08. It is the evidence the plan rested
on. Findings 1 and 3 stand; finding 2 is now historical.

**1. The parser is already correct on nested lists.** These all satisfy
`parse_blocks (render (cb_lines c)) = [cb_ast c]` *by `reflexivity`
today*:

| shape                           | rendering                 | spacing |
| ------------------------------- | ------------------------- | ------- |
| nested list first in its item   | `- - b` / `  - c`         | Tight   |
| nested list after a paragraph   | `- a` / `  ` / `  - b`    | Tight   |
| three deep                      | `- - - x` / `    - y`     | Tight   |
| nested inside a quote           | `> - - b` / `>   - c`     | Tight   |
| two items each holding a list   | `- - b` / `- - c`         | Tight   |
| list then paragraph in one item | `- - b` / `  ` / `  tail` | **Loose** |

So **nested-list support is entirely a predicate-and-proof job**. No
parser change is needed; the column-offset fix (`954bcd1`) already did it.

*Correction (2026-08-09):* the last row was originally recorded without a
spacing column, which read as a claim that the `Tight` spelling
roundtrips. It does not -- the parser returns the outer list `Loose`,
because the blank belonging to the inner list is a blank inside the outer
item too. `Loose` is the spelling that roundtrips, and `cb_ok` accepts
that one and rejects `Tight`. Adding the column is the fix; nothing else
in the table changed.

**2. `cb_ok` rejects every one of them**, solely because
`list_content_safe` returns `false` for `CList`. *Historical:* the
predicate no longer exists. All six shapes are accepted today (the last
at `Loose`).

**3. `item_forces_loose` is too coarse, and this is a real bug.** It
declares that any item with more than one block forces the list loose. But
for `- a` / blank / `  - b`, djot.js and djoths both report the outer list
**tight**, and so does our parser — because `Parser.list_content` encodes
djot.js's rule that a `+list` event does not spend the blank into
looseness. The renderer-side predicate does not mirror it.

*Fixed* in `dc13c4b`: `item_forces_loose` is now `lines_loose` over the
item's own rendered lines, so it reads the same rule off the same lines
the parser scans. See `oracle-disagreements.md`.

## Item 1 — the cblock generator

Phase 1 item 4 of `260802.plan.autonomous.md`, never done: *"Test the
renderer differentially too: render random `wf_block` inhabitants, feed to
both oracles, check they parse back to the same tree."*

Two layers, and the first is far cheaper than the second.

### 1a. In-Rocq self-consistency — **done**

For a canonical block, the roundtrip is *decidable by computation*: the
parser is executable and `cb_ast` is a closed term, so both sides are
closed and `vm_compute; reflexivity` closes the goal. No extraction, no
oracles, no harness.

Delivered as `theories/Generate.v`: `enum_cblock` over a tiny alphabet
(5, 110, 2315, 48620 inhabitants at depths 0–3), with `gen_roundtrip_1`
through `gen_roundtrip_3` checking every `cb_ok`-accepted inhabitant.

Two notes against the original sketch:

- **No decidable equality on `block` was needed.** The plan flagged this
  as what decides the cost. It does not arise: `map rt_lhs accepted =
  map rt_rhs accepted` is a `Prop` equality between two closed terms,
  decided by conversion.
- Its value is not the accepted-side check, which `roundtrip_blocks`
  already implies. It is that relaxing `cb_ok` re-scopes the check
  automatically, so a proposed relaxation is testable for soundness in
  seconds, before any proof work. That is exactly how the `cb_ok`
  restatement in item 2 was cleared: 671 accepted at depth 2 and 7151 at
  depth 3, every one verified to roundtrip, *before* the predicate was
  touched.

### 1b. Differential against the oracles — **open**

This is the only live item in this document.

- Extract `enum_cblock` and `cb_lines` alongside `convert`, and add a
  `--generated` mode to `harness/main.exe` that renders each enumerated
  cblock, runs it through djot.js and djoths, and diffs with the existing
  `--shape` projection.
- Any disagreement is adjudicated into `oracle-disagreements.md` exactly
  as corpus disagreements are.

**What decides the cost**: extraction of an inductive-heavy generator, and
whether the enumeration is small enough to run in a test loop. Bound the
depth hard; the point is coverage of *shapes*, not volume.

**Why it matters more now**: 1a checks the parser against *our own*
renderer, so it cannot catch a rule we got wrong in both. Every shape
admitted by the item-2 work — 6616 newly accepted blocks at depth 3,
nested lists among them — is currently unchecked against any external
oracle. `--shape` drops inline content, so name what it drops before
trusting it (see `project-engineering-lessons.md`).

**Exit criterion**: `enum_cblock 3` runs in `make test` (or a new `make
generated`) with zero unexplained diffs.

## Item 2 — nested lists in the roundtrip — **done**

Phase 1's remaining exit criterion.

### Step 1 — fix `item_forces_loose` — **done as written**

Landed in `dc13c4b`, by the simpler route: rather than case-analysing
block boundaries, define the predicate as `lines_loose false false` over
the item's own rendered lines. Same rule, read off the same lines the
parser scans, so there is no second encoding to keep in sync.

### Step 2 — relax `list_content_safe` — **superseded**

The predicate was **deleted**, not relaxed. `cb_ok`'s list case now asks
for `Parser.item_ok` on the item's rendering — which is
`list_uniformity`'s own hypothesis — plus a per-item `no_adjacent_lists`
(which `list_content_safe` had been supplying for free by banning nested
lists outright). `item_marker_ok` and `item_first_line` went with it:
`item_ok`'s first conjunct is exactly `item_marker_ok`.

Recorded because the intermediate recommendation was wrong and the way it
was wrong is instructive: an earlier session proposed defining
`list_content_safe` *as* `run_pad_safe` on the block's lines. That breaks
`list_content_safe_quote`, because `pad_safe` stops at `PQuote` — a
quoted code block is pad-safe while the bare code block is not — so the
predicate stops decomposing over a quote. The move that worked was to
delete the structural predicate and put the lemma's actual hypothesis
where it had stood.

`CCode` is still excluded from an item, but *computationally* rather than
structurally: fence content is verbatim and keeps the ambient indent,
which `run_pad_safe` (`item_ok`'s third conjunct) detects. A fence inside
a quote inside an item is therefore admitted, while a bare fence in an
item is not.

### Step 3 — generalize the nine `LSt 0` statements — **not needed**

All nine lemmas were deleted along with the canonical-list section of
`Roundtrip.v`. They existed to reason about a list's internals at the
`cblock` layer; `list_uniformity` does that once, over line lists, at
every depth. Nothing generalizes `LSt 0` because nothing states it any
more outside `Parser.v`'s own list run.

### Step 4 — the new opening path — **dissolved, not solved**

The obligation was: `- - b` opens the outer list and then descends into
the residue `- b`, two `step_list_open`s on one line, where the flat case
has one.

It never arises. `Parser.step_item_open` states that opening an item on
`bullet_open ++ l0` yields a `PList` whose inner state is
`step l0 (PPara [])` padded by 2 — whatever `l0` is. If `l0` is itself a
marker line, the inner state is the inner list, by the same equation that
handles any other content. There is no case split on what the item's
first line classifies as, and `item_ok`'s only demand there is that
`bullet_open ++ l0` is not a thematic break.

This is the step the plan called "the only genuinely new proof
obligation, and the one to scope carefully". It cost nothing, because the
line-level statement never had to distinguish the case.

### Step 5 — retire the exclusions — **done**

The build said, on 2026-08-09. `safe_cblock_no_columns` went with the
`Roundtrip.v` section; `no_columns`, `no_columns_pad_state`,
`pad_state_no_columns` and `step_pad_flat` were then unreachable and are
deleted. What replaced them is `run_lines_pad_shift` / `pad_state`: the
pad is stated as a *shift* of the state rather than as a no-op, which is
what makes it hold when the item's content does open a list.

### Exit criterion — met

`cb_ok` accepts every shape in the table above (the last at `Loose`, per
the correction), and `roundtrip_doc` covers them.
`Roundtrip.nested_list_roundtrip` and
`Roundtrip.nested_list_after_para_roundtrip` pin two of them; the
generator covers 7151 shapes at depth 3.

The criterion's last clause — "`list_content_safe` excludes `CCode` and
nothing else" — is void: there is no such predicate.
