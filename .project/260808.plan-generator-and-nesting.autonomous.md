# Plan: the cblock generator, and nested lists in the roundtrip

Two items, in this order. The generator first, because it is cheap, it is
the tool that de-risks the second, and it has already found three things
while this plan was being written.

---

## What the probes already established

All of this is machine-checked, from `Compute`/`reflexivity` runs against
the current `main` (`7ed0faa`). It is the evidence the plan rests on.

**1. The parser is already correct on nested lists.** These all satisfy
`parse_blocks (render (cb_lines c)) = [cb_ast c]` *by `reflexivity`
today*:

| shape                           | rendering                 |
| ------------------------------- | ------------------------- |
| nested list first in its item   | `- - b` / `  - c`         |
| nested list after a paragraph   | `- a` / `  ` / `  - b`    |
| three deep                      | `- - - x` / `    - y`     |
| nested inside a quote           | `> - - b` / `>   - c`     |
| two items each holding a list   | `- - b` / `- - c`         |
| list then paragraph in one item | `- - b` / `  ` / `  tail` |

So **nested-list support is entirely a predicate-and-proof job**. No
parser change is needed; the column-offset fix (`954bcd1`) already did it.

**2. `cb_ok` rejects every one of them**, solely because
`list_content_safe` returns `false` for `CList`. That is the predicate to
relax.

**3. `item_forces_loose` is too coarse, and this is a real bug.** It
declares that any item with more than one block forces the list loose. But
for `- a` / blank / `  - b`, djot.js and djoths both report the outer list
**tight**, and so does our parser — because `Parser.list_content` encodes
djot.js's rule that a `+list` event does not spend the blank into
looseness. The renderer-side predicate does not mirror that. Consequence:
`cb_ok (CList Tight [[P "a"; CList …]])` is `false` although `Tight` is
exactly what parses back.

This one would otherwise have been found somewhere deep inside the
tail-induction proof. It is listed as its own step below.

## Item 1 — the cblock generator

Phase 1 item 4 of `260802.plan.autonomous.md`, never done: *"Test the
renderer differentially too: render random `wf_block` inhabitants, feed to
both oracles, check they parse back to the same tree."*

Two layers, and the first is far cheaper than the second.

### 1a. In-Rocq self-consistency (do this first)

For a canonical block, the roundtrip is *decidable by computation*: the
parser is executable and `cb_ast` is a closed term, so `parse_blocks
(concat nl (cb_lines c)) = [cb_ast c]` closes by `reflexivity`. No
extraction, no oracles, no harness.

- Write `Fixpoint enum_cblock (depth : nat) : list cblock` over a fixed
  tiny alphabet (say para text drawn from `["a"; "b"]`, one heading level,
  both spacings, item counts 1 and 2). Keep it in a new
  `theories/Generate.v` so `Roundtrip.v` does not grow.
- Check `forallb (fun c => cb_ok c ==> rt_decide c) (enum_cblock 3)`,
  where `rt_decide` compares with a derived `block` equality. Needs a
  decidable equality on `block`/`inline` — mechanical, or reuse the
  skeleton trick from `harness/main.ml` and compare rendered shapes.
- Run it as an `Example … reflexivity`. It becomes a regression test that
  costs nothing to keep and fails loudly.

**What decides the cost**: whether a decidable equality on `block` already
exists. If not, `Scheme Equality` or a hand-rolled `block_eqb` is the only
real work. Everything else is enumeration.

**Why this first**: it catches parser-vs-renderer disagreement, which is
the class the nested-list bug and `item_forces_loose` both belong to. It
would have found both.

### 1b. Differential against the oracles

- Extract `enum_cblock` and `cb_lines` alongside `convert`, and add a
  `--generated` mode to `harness/main.exe` that renders each enumerated
  cblock, runs it through djot.js and djoths, and diffs with the existing
  `--shape` projection.
- Any disagreement is adjudicated into `oracle-disagreements.md` exactly
  as corpus disagreements are.

**What decides the cost**: extraction of an inductive-heavy generator, and
whether the enumeration is small enough to run in a test loop. Bound the
depth hard; the point is coverage of *shapes*, not volume.

**Exit criterion**: `enum_cblock 3` runs in `make test` (or a new `make
generated`) with zero unexplained diffs.

## Item 2 — nested lists in the roundtrip

Phase 1's remaining exit criterion. Order matters: steps 1 and 2 are
independent of the proofs and should land first, because they change what
the proofs must say.

### Step 1 — fix `item_forces_loose`

Mirror `Parser.list_content`'s rule: a blank line inside an item loosens
the list *unless* the next event is a nested list opening. Concretely, an
item forces loose when it contains a blank-separated block boundary whose
following block is not a `CList`.

Verify against the oracles first (`- a` / blank / `  - b` is tight; `- - b`
/ blank / `  tail` is loose — both already checked). Then re-run the
existing `Example`s in `Render.v`; the tight/loose corpus cases are the
regression guard.

This is a `Render.v`-only change plus whatever `cb_ok_lines_ok` needs.

### Step 2 — relax `list_content_safe`

`CList => false` becomes `CList sp items => forallb (forallb
list_content_safe) items`. `CCode => false` stays: fence content is
verbatim and keeps the ambient indent, which is the one genuine gap and is
unrelated to this work.

### Step 3 — generalize the nine `LSt 0` statements

Only **nine** lemma *statements* hardcode `LSt 0`; the other 28
occurrences are inside proofs and follow. They are:

```
run_first_list_item          run_first_canonical_item
scan_item_forces_loose       scan_list_content_loose_ext
parse_canonical_list_tail_tight / _loose
run_canonical_list_tail_tight  / _loose
parse_list_current_then_nonlist
```

Generalize `LSt 0` to `LSt k`. `step_fuel_shift` is what makes this go
through: a nested list at column `k` is the column-0 run shifted by `k`,
and no routing decision changes.

### Step 4 — the new opening path

This is the only genuinely new proof obligation, and the one to scope
carefully.

`safe_cblock_first` and `run_first_list_item` both assume the item's first
line does **not** classify as a list marker. That is false exactly when
the item begins with a nested list: `- - b` opens the outer list and then
descends into the residue `- b`, which opens the inner one. Two
`step_list_open`s on one line, where today there is one.

`safe_cblock_first`'s statement will need to split on whether the first
block is a `CList`, and the item-opening lemmas need the second branch.
`step_at_idle` plus `step_list_open`'s existing `pad_state (consumed l
rest)` form should carry it — the machinery exists, the case does not.

**What decides the cost**: whether the marker-line case can reuse
`run_first_list_item` with a different first-line lemma, or needs its own
induction. Probe it with a `Compute` on the two-marker line before
committing to either.

### Step 5 — retire the exclusions

`no_columns`, `step_pad_flat` and `safe_cblock_no_columns` exist only
because flat items never open a list. Once nested items do, those three
either gain a `pad_state` form or are replaced by `step_fuel_shift`
directly. Do not delete them speculatively; let the build say.

### Exit criterion

`cb_ok` accepts every shape in the table at the top of this document, and
`roundtrip_doc` covers them. `list_content_safe` excludes `CCode` and
nothing else.

## Sequencing

1. **1a** (in-Rocq generator) — cheapest, and it is the regression net for
   everything after.
2. **2 step 1** (`item_forces_loose`) — a real bug, independent of the
   rest, and the generator will confirm the fix.
3. **2 steps 2–5** (nested lists).
4. **1b** (oracle-differential generator) — after nesting, so the
   generated corpus exercises the newly admitted shapes.

Do not start step 4 before step 3: the new opening path is much easier to
state once the list lemmas are already column-generic.
