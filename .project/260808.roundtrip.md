# The roundtrip property

What it says, why this project proves it, what it does not buy, and which
variants of it exist. 

---

## 1. What it is

Print a document, parse the printed text, and you get the document back.

```
parse (render x) = x
```

Two programs written independently (the parser, the renderer) composed
into the identity. Nothing normalizes the comparison away: it is
structural equality on the AST.

The statement as written is **false**, and necessarily so. It has to be
restricted to a subset of documents:

```
accepted x  ->  parse (render x) = x
```

Most of the engineering is in `accepted`. Choosing it well is the whole
game, and the choice is not free: too permissive and the theorem is
false, too restrictive and the theorem covers nothing.

### Why the unrestricted form fails

Not a technicality. Whole families of ASTs have no printing that
survives a reparse:

| AST                                                                       | what goes wrong                                             |
| ------------------------------------------------------------------------- | ----------------------------------------------------------- |
| paragraph whose text is `- a`                                             | prints to a line that reparses as a list                    |
| paragraph whose last line ends in spaces                                  | parser strips trailing space, so nothing produces it        |
| code block containing a line of three backticks                           | the fence closes early                                      |
| two adjacent lists                                                        | the blank line between them merges both into one loose list |
| any node carrying a position or attribute the parser would not emit there | unreachable by construction                                 |

The first four are ambiguity: the printing is not injective, so the
parse cannot recover the input. The last is reachability: the AST type
can express things no source string denotes.

So a roundtrip theorem is always a theorem about a *fragment*, and the
interesting content is which fragment.

## 2. What it is for

### 2.1 It is the repaired completeness half

There is already a soundness theorem about the parser's image
(`theories/Wf.v`, `wf_parse`): everything the parser produces satisfies
a checkable well-formedness predicate. That is the easy direction.

The converse is the interesting one, and it is **refuted**
(`theories/Wf.v`, `wf_complete_false`): there are well-formed ASTs no
input produces. The witness is a `Section` node, which is well-formed by
every condition the predicate imposes but is only ever created by the
whole-document pass that runs after parsing.

So the parser's image cannot be characterized by a predicate over the
AST alone. Roundtrip is what replaces the refuted statement: instead of
"every well-formed AST is reachable," it says "here is a family of ASTs
that provably are reachable, each exhibited with the source that
produces it." The two together bound the parser's image from above and
below.

This is the primary reason. The rest are real but secondary.

### 2.2 A specification without writing a second parser

"The parser is correct" is not a statement until there is an independent
account of correct. The renderer is that account. It is a separate
program with separate reasoning, and the theorem forces the two to
agree. Drift between them cannot hide: it shows up as a goal that will
not close.

This is the same shape as differential testing against another
implementation, with a proof instead of samples, and with an oracle we
own.

### 2.3 An extension discipline

Every construct added to the parser owes a canonical printing and an
acceptance obligation, or the theorem stops covering it. Coverage cannot
rot silently, because the fragment is stated and checked rather than
assumed.

### 2.4 It is the instrument for the project's actual question

The framing question (`reference/Formalizing djot in Rocq.v2.md`) is not
"does djot have nice properties" but **how far can djot be extended
before they break**. The working complaint is that djot bought its
properties with blunt instruments: no indented code blocks, rigid list
indentation rules, no raw HTML.

Under that goal roundtrip is the right tool, because it fails *locally
and loudly*. Relax a syntax restriction and one of two things happens:
the acceptance predicate grows a new exclusion, which names exactly what
the relaxation costs, or the proof breaks at the case that no longer
holds. A vague design claim about ambiguity becomes something the build
checks.

## 3. What it does not buy

Roundtrip is a **meta-property**: a property of the parser that needs no
external specification. It says the parser and renderer are consistent
with each other. It says nothing about whether either matches djot.

A parser that consistently swapped emphasis and strong, paired with a
renderer that swapped them back, would satisfy the roundtrip perfectly.

Conformance is a separate obligation, and differential testing against
djot.js and djoths is how it is discharged. The two are complements, not
substitutes. Semantic questions about djot's behaviour are settled by
running the oracles, never by argument (see
`project-engineering-lessons.md`).

### Is roundtrip a property djot claims?

**No.** Worth stating plainly, because it is easy to assume otherwise.

`reference/beyond-markdown.md` organizes djot's rationale as six fixes:
emphasis delimiters, reference-link locality, removal of indented code
blocks, list and blank-line rules, raw HTML, and uniform attributes.
Every one is a claim about syntax design. Neither that document nor
`reference/djot-syntax-reference.md` mentions roundtripping,
losslessness, or idempotence.

Of the properties this project targets, three do have that pedigree and
are quoted commitments from the prose spec:

- **uniformity**: "the contents of a list item should have the same
  meaning they would have outside the list item"
- **no-backtracking**: blocks "can be parsed line by line with no
  backtracking"
- **locality**: "the parsing of the link is 'local' and does not depend
  on whether the label is defined"

Roundtrip has no such quote. djot supports djot-to-djot conversion as a
feature, but never promises it as a law. It is our chosen proxy for the
ambiguity claims djot does make, and it is a good proxy precisely
because it is mechanically checkable where "unambiguous" is not.

## 4. Variants

Four statements in the family. They are not equivalent, and only one of
them is currently a theorem here.

### 4.1 AST-side: `parse (render x) = x`

The one described above, restricted to an accepted fragment. Strongest
of the four, and the one being proved.

Reading: the printer loses no information the AST carries.

### 4.2 String-side: `render (parse s) = s`

**False for every interesting `s`, and unfixably so.** Parsing is lossy
by design; the AST records what a document means, not how it was
spelled. Counterexamples are everywhere:

- `-   a` versus `- a` (indentation past the marker is not recorded)
- `***` versus `* * * *` (thematic-break spellings collapse)
- `~~~` versus triple-backtick fences, and any fence longer than three
- tabs, CRLF, trailing blank lines
- escapes that were not required (`\-` mid-paragraph)

Restricted to strings already in the printer's image it becomes true,
but then it is not a new theorem: injectivity of the printer plus 4.1
gives it as a corollary.

### 4.3 Normalization: `parse (render (parse s)) = parse s`

**Reformatting never changes meaning.** Equivalently, `render . parse` is
idempotent: normalizing twice is normalizing once.

This is the genuinely useful dual of 4.1, and the property a djot
formatter needs. It is also the one a user of the library would most
likely want.

It is not free from 4.1. It needs every `parse s` to land in the
accepted fragment, and today that fails, because the printer only emits
three-backtick fences and so cannot print a code block whose content
contains three backticks. That is a hole in the printer, not a false
theorem, but it must be closed before 4.3 is even well-posed.

### 4.4 Relational: the printer as a relation

Where several printings are legitimately valid, fix the format as a
*relation* over all valid encodings and prove the parser inverts it
(the Narcissus framing, `reference/Formalizing djot in Rocq.v2.md` §8.3).

More general than 4.1, and the escape hatch for constructs with no
defensible canonical spelling. Not needed yet: so far every construct
has had one obvious printing, and picking it keeps the theorem an
equality rather than a membership.

### Relations at a glance

```
4.1  parse (render x) = x                on accepted ASTs      proved
4.2  render (parse s) = s                 on canonical strings  corollary of 4.1
4.3  parse (render (parse s)) = parse s   all strings           blocked on printer gaps
4.4  parse inverts a format relation      all strings           not needed yet
```

### 5.1 Why a restricted document type rather than the AST

The accepted fragment is not carved out as a predicate over the AST. It
is a separate inductive, `cblock` (`theories/Render.v`), with one
constructor per construct the roundtrip covers: paragraph, thematic
break, code block, heading, quote, bullet list. Four functions relate
it to everything else:

|              |                                                          |
| ------------ | -------------------------------------------------------- |
| `cb_lines`   | the canonical source lines                               |
| `cb_ast`     | the AST those lines are claimed to mean                  |
| `cb_ok`      | decidable acceptance                                     |
| `cblocks_ok` | acceptance for a sequence, adding cross-block conditions |

Three reasons for the separate type, in order of importance:

**It splits blocks from inlines.** A `CPara` holds *source lines*, plain
strings. The AST's paragraph holds parsed inlines. `cb_ast` is where
inline parsing happens (`CPara ls -> Para (para_inlines ls)`). So the
block-layer theorem claims only that the parser groups these lines into
these blocks and hands *these exact strings* to the inline parser. It
makes no claim about inlines at all. Stated over the AST directly, no
such split is available and every block lemma would drag the inline
grammar in with it.

**It removes the canonicalization quotient.** Printing an AST requires
choices, and blank-line ownership at block boundaries is genuinely
ambiguous. An earlier QCheck attempt handled this with a
canonicalization step carrying a 30-line comment explaining the
ambiguity. Recording the choice in the type instead makes the theorem an
exact equality with no quotient (`theories/Roundtrip.v` header states
this).

**It is enumerable.** Because a paragraph is a list of strings over a
small alphabet, the type can be exhaustively generated to a bounded
depth. The AST cannot be, usefully. This is what the generator work
(`260808.plan-generator-and-nesting.autonomous.md`) depends on.

The restricted type is scaffolding for the block layer, not the
destination. The eventual statement is over the AST.

### 5.2 The generator

`theories/Generate.v` enumerates `cblock` exhaustively over a tiny
alphabet (5, 110, 2315, 48620 inhabitants at depths 0 to 3) and decides
the roundtrip on every `cb_ok`-accepted one by `vm_compute; reflexivity`.
No decidable equality on `block` is needed, because both sides are
closed terms.

Its value is not the accepted-side check, which `roundtrip_blocks`
already implies. It is that relaxing `cb_ok` re-scopes the check
automatically, so a proposed relaxation can be tested for soundness in
seconds, before any proof work. The two boundary examples in that file
were found exactly that way.

### 5.3 What is proved

- `roundtrip_blocks` (`theories/Roundtrip.v`): the block-sequence
  roundtrip under `cblocks_ok`.
- `roundtrip_doc`: the same at the parser's entry point, modulo
  `undo_pass`, which strips the section-and-identifier post-pass. Its
  correctness is `pass_erase` (`theories/Document.v`), guarded by
  `pristine`. This is the only normalization in the statement, and it
  exists because the parser adds structure no input asked for.
- `list_uniformity` (`theories/Parser.v`): a bullet list's rendering
  parses back to a `BulletList` whose items are the items' own lines
  parsed at top level, and whose spacing is `list_spacing_of` over those
  same lines. The list analogue of `quote_uniformity`, and the property
  *Beyond Markdown* names as a design principle. Stated over line lists
  only: no `cblock`, no acceptance predicate, and nothing about nesting
  depth. `list_uniformity_gen` leaves the list's ending open;
  `list_uniformity` and `list_uniformity_tail` are the two endings.

  The spacing clause has two halves and both are scans that carry the
  item's own parse state, because a blank belongs to the innermost list
  open where it falls: `item_loose` (via `lines_loose`) for blanks
  inside an item, `seps_loosen` (via `ends_open_list`) for the blanks
  between items. The second half was wrong until 2026-08-09 --- it
  assumed a separator always loosens --- which put ASTs no djot source
  denotes inside the fragment. See `oracle-disagreements.md`, "a blank
  at the end of a nested list".
- `parse_lines_pad_invisible` (`theories/Parser.v`): a blank pad in front
  of every line of a run from idle changes nothing, provided no fence is
  open directly (`run_pad_safe`). It is what `list_uniformity` uses to
  discharge the item's continuation pad.

### 5.4 Known gaps in the fragment

- **Nested lists are in.** `cb_ok`'s list case now asks for exactly
  `list_uniformity`'s hypothesis -- `item_ok` on the item's rendering --
  plus a per-item `no_adjacent_lists`. `list_content_safe`,
  `item_marker_ok` and `item_first_line` are gone, and with them the
  padded-block layer (`parse_cblock_pad`, `parse_safe_cblocks_pad`) and
  the whole hand-rolled canonical-list section: `theories/Roundtrip.v`
  went from 2918 lines to 1283. The fragment went from 150 to 671
  accepted shapes at depth 2, and 535 to 7151 at depth 3, every one of
  them checked to roundtrip by full AST equality.

  Recorded because it was wrong on the way in: the earlier
  recommendation was to define `list_content_safe` *as* `run_pad_safe`
  on the block's lines. That breaks `list_content_safe_quote` outright,
  because `pad_safe` stops at `PQuote` -- a quoted code block is
  pad-safe while the bare code block is not -- so the predicate stops
  decomposing over a quote. The move that worked was not to redefine the
  structural predicate but to delete it, and put the *lemma's* actual
  hypothesis in `cb_ok` where the predicate had been.
- **Code blocks in list items.** No longer a blanket exclusion. Whether a
  fence survives the item's indent is now *computed* by `run_pad_safe`
  (`item_ok`'s third conjunct) rather than declared, so a fence inside a
  quote inside an item is admitted while a bare fence in an item is not.
  A fence in an item is still genuinely unrepresentable, and is still
  the reason 4.3 is not well-posed.
- **Adjacent lists** and **paragraphs that classify as other
  constructs** are permanent exclusions, not gaps. They are the
  ambiguities from section 1.
