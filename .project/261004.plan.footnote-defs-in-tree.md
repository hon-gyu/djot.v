# Plan: footnote definitions stay in the tree

## Why

The document pass treats the two kinds of definition differently.

- A reference definition stays in `doc_blocks` as a `RefDef` block, and
  `Refs.of_list` builds `doc_references` beside it.
- A footnote definition is removed. `Notes.of_list` returns the blocks
  without it and puts its body in `doc_footnotes`.

Nothing needs the removal. `Html.v` gives a `FootnoteDef` no output and
finds a note's body through the map, so a definition left in place
renders the same. The removal follows the shape of djot.js's AST, where
footnotes are on the document and not among its children.

What the removal costs today:

- A definition's place, its position, its attributes and any earlier
  definition of the same label are not in the document. The OCaml
  wrapper keeps the blocks as parsed (`Doc.parsed`) and a list collected
  from them (`Doc.footnote_defs`) to get them back.
- `Render.doc_source_blocks` appends the definitions after the blocks,
  which is the first round-trip exception `Doc.to_string` documents.
- `Pristine.of_list` has to exclude footnote definitions, so `pass_erase`
  and `roundtrip_doc` say nothing about documents with footnotes.
- `Document.v` carries the `notes_free` family and the lemmas over it (about 400 lines) only to
  show that the pass removes nothing from pristine input.
- `Mapper.map_doc` maps the blocks and the map separately, and leaves
  `Doc.footnote_defs` unmapped. `Folder.fold_doc` visits the blocks and
  then the map.
- `Stream` returns blocks that differ from `Doc.blocks` in two ways, and
  this is one of them.

## Decisions

### D1. The notes pass collects and does not remove

`Notes.of_list : blocks -> note_map -> note_map`, with the shape of
`Refs.of_list`. `doc_pass` becomes

```coq
{| doc_blocks := sectionize bs'
 ; doc_footnotes := Notes.of_list bs' []
 ; ... |}
```

`FootnoteDef` keeps its children. The comment on the constructor in
`Ast.v` already says "the block stays"; this makes it true.

### D2. A map entry is the definition's body as it is in the tree

Today a body is stored with the definitions nested in it removed. After
the change a definition written inside another stays in its parent's
body, and the nested one has its own entry as before. The HTML is the
same either way, since a nested `FootnoteDef` renders to nothing.

A key whose block is a footnote definition is dropped today along with
the definition. It stays, with the definition under it.

Entry order and the last-definition-wins rule (`alist_set` on the
normalized label) do not change.

### D3. Sections wrap definitions like any other block

`sectionize` runs on all the blocks, so a definition written under a
heading is inside that heading's section. `Undo.pass` already handles
`FootnoteDef`, and takes the wrapper back off.

### D4. Keep `doc_footnotes` as a field

The alternative is to drop the field and compute the map from
`doc_blocks` when asked. That cannot disagree with the tree, but every
HTML render and every lookup would walk the document. Keep the field,
and state the agreement as a lemma:

```coq
Lemma doc_footnotes_of_blocks :
  forall bs, doc_footnotes (doc_pass bs) = Notes.of_list (doc_blocks (doc_pass bs)) [].
```

This needs `Notes.of_list` to descend into `Section`, as
`Refs.of_block` does and today's `Notes.of_block` does not, and to be
unaffected by `sectionize`, which only wraps.

## What falls out

- `Pristine.of_block` accepts `FootnoteDef`, so `pass_erase` and
  `roundtrip_doc` cover documents with footnotes.
- `notes_free_*`, `collect_notes_pristine_block`,
  `collect_notes_list_pristine`, `pristine_notes_free` and
  `assign_ids_notes_free` are deleted. `pass_erase` no longer has a notes
  step.
- `doc_source_blocks` loses its `++ map ... (doc_footnotes d)`, and the
  "footnote definitions come after the blocks" exception goes from
  `Doc.to_string`.
- In the wrapper, `Doc.t` loses `parsed` and `footnote_defs`.
  `Doc.footnote_defs` becomes a fold over `Doc.blocks`, or goes if
  nothing uses it. `For_testing.parsed` goes with the field unless a
  test needs the unsectioned blocks, in which case it is `Undo.pass`.
- `Mapper.map_doc` maps the blocks and derives the map again from the
  result. `Folder.fold_doc` visits the blocks only.
- `Stream` blocks differ from `Doc.blocks` by sections alone.

## A consistent `Doc.make`

This plan does not add a constructor, but it is what makes one clean.

A document is then its blocks plus tables that are functions of those
blocks (D4 for footnotes; `Refs` and `Ids` already work that way). So
`Doc.make : Block.t node list -> Doc.t` can run the pass and take
nothing else, and a caller cannot supply a map that disagrees with the
body, which cmarkit's `Doc.make ?defs` allows.

The input condition also shrinks. Today blocks must be "as written, with
each `FootnoteDef` in place and no `Section`" (`Html.of_blocks`), which
`Doc.blocks` does not satisfy. After this plan `Doc.blocks` differs from
as-written blocks only by section wrappers and assigned ids, which
`Undo.pass` removes, so `Doc.make (Doc.blocks d)` is meaningful, and
`pass_erase` is the statement that it gives `d` back on pristine input.

Two limits remain and are not this plan's to fix:

- `Pristine` still excludes a heading with a written id, so the
  statement above does not cover those.
- A made document has no line table, so `Doc.textloc` gives none.

With `Doc.make`, `djot.json` can decode a document: decode `children`,
put the entries of `footnotes` and `references` back as blocks, and
make.

## Risks

- A footnote body is now reachable twice, through the tree and through
  the map. Any traversal that visits both counts its contents twice.
  `Folder.fold_doc` is the known case (step 6); grep for other users of
  `doc_footnotes` that also walk `doc_blocks`. Footnote numbering in
  `Html.v` walks the blocks and looks bodies up by label, and a
  `FootnoteDef` contributes nothing on that walk, so a reference inside
  a note body is still numbered once.
- `Ids.of_list` already walks footnote bodies before the notes pass, so
  heading ids inside notes do not change. The example
  `quote_heading_unsectioned` pins this.
- Oyster reads `Doc.footnote_defs` for its duplicate-definition
  diagnostic (`djot-v-gaps.local.md`). The accessor's result is the same
  if it is kept as a fold.
