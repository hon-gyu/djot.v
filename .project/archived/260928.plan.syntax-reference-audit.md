# Plan: audit the syntax reference, rule by rule

## 0. Goal

For every rule the djot syntax reference states, record what in this
repository would fail if the parser broke it, and act on the rules
where the answer is nothing.

The footnote lazy-line bug (jgm/djot discussion #414, closed on
`hy/lazy-line-in-container-uniformity`) is the motivating case.  The
reference states the rule and gives an example (footnote section,
"lazily omit the indentation").  No theorem stated it, djot.js's test
suite has no case for it, the generated corpus has no footnotes, and the
one lemma that touched it, `step_foot_close`, proved the buggy
behaviour.  Nothing failed, so nothing was noticed.  The audit looks for
the other rules in that position.

## 1. What counts as coverage

Theorems are the trusted core; everything else helps find mismatches.
Each rule gets the strongest level that applies:

| Level | Meaning |
| --- | --- |
| T | A theorem states the rule, over all inputs it applies to.  The statement is written from the reference, not from the parser's own predicates (as `lazy_stack` is, where `lazy_ok` is not). |
| E | A kernel-checked `Example` pins the reference's own example(s) for the rule, with djot.js's output. |
| D | Only the djot.js comparison (test suite or generated corpus) exercises it. |
| none | Nothing. |

A theorem counts only if it *states* the rule.  A lemma that merely
describes what the code does is not coverage: `step_foot_close` touched
the lazy-line rule and contradicted it.

## 2. Steps

### Step 1. Pin the reference

The reference currently sits untracked in the repository root.  Record
which upstream version is audited (jgm/djot `doc/syntax.md` at a named
commit), and cite rules by that version and section, never by the local
file name.  Whether to vendor it (a submodule, like `djot.js`) is a
decision for the user.

### Step 2. Extract the rules

One row per normative statement: a sentence that says what something
parses as, what may or must appear, or what ends or continues a
construct.  Record the section, the sentence quoted, and the reference's
examples for it.  Sentences that describe rendering or intent only
("we recommend", HTML output conventions) are listed but marked
out of scope, so the table is complete.

The sections, in the reference's order:

- Inline: precedence; ordinary text and backslash escapes; link (inline,
  reference, empty label); image; autolink; verbatim; emphasis and
  strong; highlighted; super/subscript; insert/delete; smart
  punctuation; math; footnote reference; line break; comment; symbols;
  raw inline; span; inline attributes.
- Block: the block-syntax introduction (no backtracking, paragraphs are
  never interrupted); paragraph; heading; block quote; list item, task
  and definition items; list (types, style changes, ambiguity, start
  number, tightness); code block; thematic break; raw block; div; pipe
  table and caption; reference link definition; footnote; block
  attributes; links to headings.
- Nesting limits.  The security section is out of scope.

### Step 3. Every reference example as a checked `Example`

The cheapest pass and the one that would have caught #414: each code
example in the reference becomes an `Example` in a new
`dev/check/Reference.v`, one per example, named after its section, with
the HTML djot.js gives at the pinned version.  An example where our
output differs from djot.js's goes to `djotjs-divergences.md` and is
adjudicated there before it is pinned.

This gives every rule with an example at least level E.

### Step 4. Map the theorems

For each rule, name the theorems that state it (level T), reading the
statements rather than the names.  Start from the README's property
tables and `Uniformity.v`, `ListUniformity.v`, `Roundtrip.v`,
`Invariants.v`, `Document.v`.  Record partial coverage honestly: a
theorem over a restricted shape (uniformity over fully prefixed input)
covers the rule for that shape only, and the row says which shape.

### Step 5. Write the coverage table

`.project/syntax-reference-coverage.md`, undated because it tracks the
current state (see `.project/README.md`).  Columns: section, rule
(quoted), level, theorems or examples, notes.  One summary line per
section with its count at each level.

### Step 6. Triage the gaps

For each rule below T, decide one of:

- **prove it**: the rule is general and a theorem is within reach.
  Before the proof, run the statement through `dev/check/Probe.v` over
  reachable states, as was done for `step_lazy_restore`, which is how
  the one-line heading bug turned up;
- **an example is enough**: the rule is a single case with no
  quantifier worth stating (a particular escape, say), and level E
  says all there is to say;
- **spec gap**: the reference is silent or ambiguous; record it with the
  `SPEC-GAP` verdict in `djotjs-divergences.md`.

Rank the "prove it" rows by how much of the parser a violation could
hide in: container and continuation rules first (the class the lazy-line
bug came from), then list and table structure, then inline precedence,
then single-construct rules.  Each accepted row becomes its own task or
plan; this plan ends at the ranked list.

## 3. Keeping it current
