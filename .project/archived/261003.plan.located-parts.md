# Plan: list items, rows and cells as nodes

Follows F9 of [[260916.plan.source-locations]], which kept these parts
out of the tree and put their ranges on the parent (`parts` in
`provenance`). This plan takes the other branch of F9.

## Why

- A part's range is only right while the parent's children stay in step
  with the parallel list. `Mapper.map_doc` keeps a node's position, so a
  mapper that drops an item leaves the ranges pointing at the wrong
  items. The OCaml API now detects a changed count and gives up; a
  rewrite that keeps the count goes undetected.
- djot.js has `list_item`, `task_list_item`, `definition_list_item`,
  `term`, `definition`, `caption`, `row` and `cell` nodes, each with a
  position and attributes. Our tree has none of them.
- `parts`, `def_item_spans`, `list_item_spans`, `table_parts` and the
  OCaml accessors exist only to carry ranges for things that are not
  nodes. They go away.

## Decisions

### D1. Wrap in `node`, not a position-only wrapper

`node` carries a position and attributes. The parser never puts
attributes on an item, row or cell, so the slot is always empty from a
parse. Reasons to accept that:

- djot.js gives each of these nodes an attribute slot (`HasAttributes`),
  so a tree from either implementation has the same shape.
- `Doc.textloc`, `erase_*`, `set_pos`, `hull_pos` and the semantic/located
  policy work on `node A` for any `A`. A second wrapper would duplicate
  each of them.

The alternative, `located A := Located (p : pos) (x : A)`, forbids the
unused attributes by type but costs a parallel set of helpers and
lemmas.

### D2. Wrap the existing payloads; no new inductives

```coq
| OrderedList (attrs : ordered_list_attributes) (sp : list_spacing)
    (items : list (node blocks))
| BulletList (sp : list_spacing) (items : list (node blocks))
| TaskList (sp : list_spacing) (items : list (node (task_status * blocks)))
| DefinitionList (sp : list_spacing)
    (items : list (node (node inlines * node blocks)))
| Table (caption : node inlines) (rows : list (node (list (node cell))))
```

`node` and `list` are already nested in `block`, so this needs no mutual
inductive. Named item types (`Inductive list_item := Item (bs : blocks)`)
would have to be mutual with `block` and would change every induction
principle more deeply, for no gain in what the tree can say.

A table without a caption has a caption node with no inlines, as today;
its position is `NoPos`. The row's head/body flag stays on each `Cell`.

### D3. Drop `parts` from `provenance`

`provenance` keeps `node_span` and `syntax_spans`. The parser builds the
item, term, definition, row, cell and caption nodes from the extents it
already tracks for `PItems`, `PDefItems` and `PTable` (`Step.v`,
`list_item_spans`, `def_item_spans`, `table_parts`). Each range rule
stays as it is now: an item from its marker to its last content, a cell
from its leading `|`, the caption from its `^`.

### D4. Erasure reaches the new nodes

`erase_block` erases the positions of item, row and cell nodes too. Under
`semantic_pos` each is `mk x`, so the semantic parse stays position-free
by conversion, as for blocks now.

### D5. OCaml API

- `Doc.list_items`, `task_items`, `def_items`, `table_rows`,
  `table_caption_loc` are removed. An item is reached by matching the
  list and located with `Doc.textloc`, like any node.
- `Mapper` and `Folder` keep visiting blocks and inlines. They descend
  through item, row and cell nodes and keep their positions and
  attributes.
- The test printer prints the new nodes from the tree instead of from
  the accessors.

### D6. HTML renders a part's attributes where djot.js does

`<li>`, `<dt>`, `<dd>`, `<tr>` and `<caption>` carry their node's
attributes, and a cell carries its alignment style followed by its own
attributes. A task item's `<li>` and a definition item's wrapper carry
none, as in djot.js. The parser gives these nodes no attributes, so a
parsed document renders as before; the attributes reach the output only
from a tree built or mapped through the API.

## Pitfalls

- Proofs that close by `reflexivity` on a semantic parse see `mk` around
  each item. They should still compute; a `simpl` that stops at `mk` may
  need `cbn [mk]`.
- `def_term_span` reads the first paragraph of an item's blocks as the
  term. The term node's position has to come from the same split as the
  semantic `def_item`, or the located and semantic parses disagree.
- Tightness and list uniformity read item lists directly; they now read
  `node_contents` of each item.
