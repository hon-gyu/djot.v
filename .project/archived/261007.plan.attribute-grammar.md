# Plan: the attribute grammar (AT2 to AT5, C1)

## Goal

State the reference's attribute syntax ("Inline attributes", "Comment",
"Block attributes") as a grammar that does not mention the machine
(`Attributes.v`), and prove the machine accepts exactly that grammar with
the attributes the grammar gives.  This is step 2 of the move from the
coverage audit to a specification (`syntax-reference-coverage.md`); the
inline specification (step 1) builds on it.

## Why the machine is the right target

Every attribute spec goes through `astep`: block specs by `attr_open` and
`attr_feed`, inline specs by `iattr_feed`, span specs by `ispan_feed`.
A theorem about `afeed` from `ap_init` therefore covers both contexts.
What decides *where* a spec may start and what it attaches to is outside
the machine and is not this plan's (AT1, AT7, C2: inline attachment;
BA1 to BA3: already T).

## Statements

`AttrSyntax.v`, importing `Strings` and `Ast` only:

- Character classes written from the reference where it says
  (bare values: ASCII alphanumerics, `_`, `:`, `-`), from djot.js where
  it does not (identifiers, classes, keys, whitespace).
- `item`: `#name`, `.name`, `key=bare`, `key="quoted"`, `%comment%`.
- `body : string -> list item -> Prop`, the text between `{` and `}`:
  items separated by whitespace, except that a quoted value or a closed
  comment needs no separator after it; a comment left open is closed by
  the `}`.
- `value_of`: escapes resolved, then whitespace runs collapsed.
- `attrs_of : list item -> attr`, the fold: last identifier wins,
  classes combine, last value of a key wins, comments contribute nothing.

`AttrAgree.v`, the agreement:

1. `afeed (b ++ "}" ++ rest) ap_init` is done after the `}` with
   `attrs_of items`, for every `body b items`.
2. Conversely, a run that ends done read some `b ++ "}"` with
   `body b items`, and its attributes are `attrs_of items`.
3. `body` is unambiguous: one item list per body.
4. Block corollary: a one-line `attr_open` in terms of `body`, so that
   BA1 to BA3 read through the grammar.

## Gaps found while probing (both engines agree on each)

To be logged in `djotjs-divergences.md` as `SPEC-GAP`:

- `{.x class="y"}` gives `class="y"`, `{.x}{class="y"}` gives
  `class="x y"`: stacked specs are not "the same as" one spec (AT7)
  when a `class` key meets a `.class`.
- Escapes in quoted values cover ASCII punctuation except `<`, `>`,
  `@`; text escapes (O2) cover all of it.
- Value whitespace: runs of space, CR and LF become one space; a tab is
  kept.  The reference says nothing.
- Identifiers take any byte that is not whitespace or punctuation other
  than `: _ - ; ' "`, non-ASCII included; classes and keys are ASCII
  only.  `{# }` and `{.}` are accepted and add nothing.
- A bare value, identifier or class must be followed by whitespace or
  `}`: `{.a%c%}` fails, `{%c%.a}` does not.
- Inline only (step 1): a spec cannot begin with a delimiter character,
  key character or not (`a{-k=v}`, `a{_k=v}`): `{-` and `{_` open first.
