# Plan: a linear `line_table`

## Goal

Make a parse that records positions cost what `extracted-performance.md`
says it costs: about 10% over one that does not.  Through the `Doc` and
`Source` API of the `ocaml/` package it is quadratic in the size of the
document today.

Found in a downstream usage of the package, which parsed with
`~locs:true` and took over a second on a 126 KB document.

## What is slow

`Djot.Doc.of_string ~locs:true` does two things a parse without positions
does not: it cuts the pieces with `Reparse.loc_step`, and it builds the
table of line starts that turns a recorded spot into a byte offset
(`ocaml/src/djot.ml`, `of_pieces`):

    ~lines:(Some (Array.of_list (K.Strings.line_table src)))

The table is the whole cost.  Native OCaml 5.3.0, release profile,
`djot.js/bench/readme.dj` repeated, read at b0d4dc5:

| stage                                  | 63 KB | 126 KB | 252 KB |
| -------------------------------------- | ----: | -----: | -----: |
| `line_table`                           | 182 ms | 618 ms | 2712 ms |
| `pieces` with `loc_step`               | 2.3 ms | 4.6 ms | 9.6 ms |
| `pieces` with `sem_step`               | 1.7 ms | 3.4 ms | 6.6 ms |
| `assemble 0`, then `doc_pass`          | under 0.1 ms | 0.2 ms | 0.9 ms |
| `Doc.of_string ~locs:true`, in all     | 356 ms | 1507 ms | 6265 ms |
| `Doc.of_string`, in all                | 2.8 ms | 3.7 ms | 9.4 ms |

`line_table` takes four times as long when the document doubles.  The rest
of the located path is linear and within a factor of 1.5 of the plain
one.  `Doc.textloc` on every node of the 126 KB document takes under a
millisecond, so reading the table is not a cost.

The cause is the one `split_lines` had.  `line_table_aux`
(`theories/Strings.v`) destructs its string as `String c rest`, and a
native OCaml string has no tail to share: the extraction writes
`String.sub s 1 (l-1)`, a copy of the remainder, once per byte.

The 10% figure in `extracted-performance.md` ("Locations on, against the
incumbent") is right for what it measures.  `parse_blocks_located` does
not build the table, so that benchmark never ran it.

## Change

One realization in `extraction/ocaml/Extract.v`, beside the one for
`split_lines`:

    Extract Constant DjotV.Strings.line_table =>
      "(fun s ->
         let n = String.length s in
         let rec go start acc =
           match String.index_from_opt s start '\n' with
           | Some i ->
             go (i + 1)
               ({ source_line_start = start; source_line_length = i - start;
                  source_line_ending = 1 } :: acc)
           | None ->
             List.rev
               (if start < n
                then { source_line_start = start; source_line_length = n - start;
                       source_line_ending = 0 } :: acc
                else acc)
         in
         go 0 [])".

It is trusted, not proved, as the other realizations there are: the
theorems stay about the Gallina `line_table`, and the OCaml is asserted
equal to it.  `line_table_aux` is still extracted and no longer called.

Nothing in `theories/` changes, and neither does `ocaml/src/djot.ml`.

## Expected

The prototype builds the table of the 126 KB document in 0.1 ms, against
603 ms, and of an 8 MB one in 17 ms.  `Doc.of_string ~locs:true` on the
126 KB document should go from about 1500 ms to about 5 ms, the sum of
the linear stages above.

## Not in this plan

- `Array.of_list` on the result, and returning an array from the kernel:
  linear, and not measurable beside the parse.
- The Haskell extraction in `djoths`.  Whether its `line_table` has the
  same shape has not been looked at; Haskell strings are lists there, so
  it likely does not.
- Allocation in the parse itself, which `261001.plan.line-allocation.md`
  covers.
