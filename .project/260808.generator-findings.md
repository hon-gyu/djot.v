## Finding 3 — lifting the nested-list ban is not sound on its own

The decisive experiment: patch `list_content_safe` so `CList` recurses
instead of returning `false` (item 2 step 2, verbatim), and check the
roundtrip on everything the patched predicate accepts.

Coverage gain is large: 150 to 845 accepted at depth 2, 535 to 12641 at
depth 3. But **at least 222 of the newly admitted shapes at depth 2 do
not roundtrip** (222 is what a sound-negative screen catches; the true
count is not below it). The minimal one:

```
- - a

    t
```

`CList Tight [[CList Loose [[CPara ["a"]; CPara ["t"]]]]]`, which parses
back with the **outer** list `Loose`.

Why: `item_forces_loose` inspects *pairs* of blocks in an item. The outer
item holds exactly one block (the inner list), so there is no pair, and
the outer list is declared tight. But the blank line separating `a` from
`t` is a blank line inside the outer item as well, and the parser spends
it, promoting the outer list to loose.

So `item_forces_loose` **is** wrong, just not in the direction or for the
reason the plan gave: it is too *permissive*, on nesting, not too coarse
on multi-block items. The `KList` exemption covers a gap whose successor
is a nested list; it does not cover a gap nested inside an item's only
block.

**Amendment**: item 2 step 2 cannot land alone. It needs a strengthened
`item_forces_loose` that sees blanks contributed by nested content, not
just blanks between an item's own top-level blocks. This is a new step,
and it is a `Render.v` change with a real proof consequence, since the
tight/loose bit is what `scan_list_content` reasons about.

Both directions are pinned in `Generate.v` as
`nested_loose_promotes_outer` and `nested_loose_outer_loose_roundtrips`.

## Finding 4 — the render projection is not an equality oracle

To count rejected-but-roundtripping shapes, the first screen compared
`render_djot (parse ...)` with `render_djot (cb_ast ...)`, on the
reasoning that string equality is decidable and rendering is faithful.

It reported 983 wrongly-rejected shapes at depth 2, including a bucket of
22 blamed on the spacing condition. All 22 were false positives.
`CList Tight [[CPara ["a"]]]` and `CList Loose [[CPara ["a"]]]` both
render to `- a`: **the projection drops the exact field the bug lives
in.** The genuine tight/loose defect in finding 3 was invisible to it
until the screen was augmented with a spacing-tag comparison.

This is the same failure mode as the corpus comparison that missed the
nested-list bug, one level in: a projection adopted for convenience
silently erased the field under test. The harness's `--shape` mode drops
inline content on purpose and is fine for container bugs, but it is not a
roundtrip oracle either.

**Consequence for the design**: `Generate.v` ships no screen at all.
Relaxing `cb_ok` in `Render.v` re-scopes `accepted` automatically, so the
existing `gen_roundtrip_*` examples test the relaxed predicate exactly,
with no projection in the loop. That is how finding 3 was obtained, and
it is why the file has no `rt_screen`, no `block_eqb`, and no duplicate
predicate to drift.

## Finding 5 — list-item uniformity holds, and it subsumes most of item 2

Prompted by the cost asymmetry: `quote_uniformity` is a four-line proof
covering every construct with no well-formedness hypothesis, while
`Roundtrip.v` is 3240 lines, two thirds of it lists, and still does not
admit nesting. The list analogue had never been stated.

Stated and probed (`Generate.v`, "List-item uniformity, probed"):

```
parse_lines (indent_lines "- " "  " L) (PPara [])
  = [mk (BulletList (item_spacing L) [parse_lines L (PPara [])])]
```

Checked on **1716 line sets** — every generated block's rendering to
depth 2, plus every two-block sequence's, including all the nested-list
shapes `cb_ok` currently rejects. **Zero exceptions.**

Two side conditions, both already known, both independent of nesting: no
fence in `L`, and `"- " ++ first line of L` must not itself be a
thematic break (the existing `item_marker_ok`).

The item's **contents are uniform unconditionally**. Only the tight/loose
bit varies, and it is:

```
Loose  iff  some blank run in L is followed by a line that does not open a list
```

A line-level scan. Blank runs collapse: `["a"; ""; ""; "- b"]` is Tight.
This is `Parser.list_content`'s `KList` exemption read off the lines
rather than off the event stream.

**Why `item_forces_loose` cannot be patched into correctness.** It reads
the block *tree*, and the tree has lost where the blanks sit relative to
the markers. Finding 3's counterexample is not an edge case in it; it is
the predicate being the wrong shape. `item_spacing` is the replacement,
and it belongs in `Render.v` once the theorem is proved.

## Step 3, second attempt: the blocker is structural, and pad invisibility changes the shape of the fix

Applying both predicate edits and following the build (branch
`hy/260808-tmp`) turned up a circularity the earlier scope note missed.

`Roundtrip.v` has two block-parsing lemmas, and the list machinery sits
between them:

```
parse_cblock_pad  (542)   blocks *inside a list item*, hence padded;
                          excludes CList and CCode via list_content_safe
    |
    v
parse_safe_cblocks_pad (920)
    |
    v
the canonical-list section (943 .. 2500)
    |
    v
parse_cblock  (2528)      top level, unpadded, handles CList
```

Relaxing the ban means `parse_cblock_pad` must handle `CList` -- but its
`CList` case needs the list section, which needs `parse_cblock_pad`.
That is a genuine cycle, not a missing lemma, and it is why the `CList`
case cannot simply be filled in.

### What pad invisibility buys

`parse_lines_pad_invisible` (now in `Parser.v`, commit `3a7f55d`) says a
blank pad in front of every line of a run from idle changes nothing --
with no `no_columns` condition, so nested lists are covered.

`parse_safe_cblocks_pad`'s statement is exactly a padded run from idle:

```coq
parse_lines (map (fun l => pad ++ l) (sep_lines (map cb_lines cbs))) (PPara [])
= map cb_ast cbs
```

so it reduces to its *unpadded* counterpart.  The padded layer stops
being a separate development: item contents can be parsed by the same
unpadded lemma the top level uses, and `parse_cblock_pad` can go away
rather than grow a `CList` case.

### The remaining cycle, and how to cut it

`parse_cblock` (unpadded) still needs the list section, which needs item
contents parsed, which for a nested list needs `parse_cblock`.  This one
is real recursion on cblock structure and is cut by *parameterising*
rather than reordering: the list section should take

```coq
(forall it, In it items ->
   parse_lines (sep_lines (map cb_lines it)) (PPara []) = map cb_ast it)
```

as a hypothesis instead of deriving it from `parse_safe_cblocks_pad`,
and `parse_cblock`'s `CList` case supplies it from `cblock_ind2`'s
induction hypothesis.  Roughly ten lemmas between `run_canonical_item`
(1320) and `parse_canonical_list_then_nonlist` (2361) gain the
hypothesis; the threading is mechanical, but it is the bulk of the work.

### Order for the next attempt

1. Prove `run_pad_safe` holds for a `list_content_safe` rendering (no
   fence opens directly), so `parse_lines_pad_invisible` applies.
2. Restate `parse_safe_cblocks_pad` as a corollary of the unpadded
   version; delete `parse_cblock_pad`.
3. Retire `safe_cblock_no_columns`, `step_idle_bullet_cont`,
   `run_lines_first_unpadded` -- they exist only to say the pad is
   invisible inside a *flat* item, which step 1 now says in general.
4. Parameterise the list section on the item-contents hypothesis.
5. Reformulate `safe_cblock_first` to split on whether the first block is
   a `CList` (still the one genuinely new obligation: `- - b` performs
   two `step_list_open`s on one line).
6. Flip the two predicates.  `Generate.v` confirms the result
   immediately; the expected numbers are in the table above.

## Step 3, third revision: `list_content_safe` should *be* `run_pad_safe`

Probing step 1 of the order above (prove `list_content_safe` implies
`run_pad_safe`) showed the implication holds on the generator -- and that
it is very far from tight.  **1944 of 2315 generated blocks at depth 2
are `run_pad_safe` but not `list_content_safe`.**

Two reasons the structural predicate over-approximates:

- A `` ``` `` line in a paragraph's interior does not open a fence.  djot
  paragraphs cannot be interrupted, so it is just text.  `cb_ok (CPara
  ["a"; "```"])` is `true` and its rendering is `run_pad_safe`.
- A fence inside a *quote* inside an item is safe, because the quote's
  own stripping absorbs the pad.  `list_content_safe` bans it anyway --
  the conservatism its own comment acknowledges.

So the right change is not to relax the `CList` case but to replace the
predicate with the condition the pad lemmas actually need:

```coq
Definition list_content_safe (c : cblock) : bool :=
  run_pad_safe (cb_lines c) (PPara []).
```

Measured, with the `no_adjacent_lists` conjunct from the previous
section (exact equality at depth 2, not a screen):

| predicate                   | accepted d2 | accepted d3 | failures d2 |
| --------------------------- | ----------- | ----------- | ----------- |
| current                     | 150         | 535         | 0           |
| structural relaxation       | 632         | 6623        | 0           |
| `run_pad_safe` on the lines | **671**     | **7151**    | **0**       |

Why this is better than the structural relaxation, beyond the extra 39:

- It **is** the hypothesis of `parse_lines_pad_invisible`, so step 1 of
  the order above disappears -- there is no implication left to prove,
  the predicate and the lemma's precondition are the same term.
- It closes the CCode-in-quote gap that was previously listed as a
  permanent exclusion.
- It is exactly right rather than conservative, so future constructs need
  no new case: whether their rendering survives a pad is computed, not
  declared.

One small obligation replaces the old step 1: `run_pad_safe` must be
shown `false` for `CCode` with abstract arguments, where the structural
version gave it by `discriminate`.

Revised order: as above, but drop step 1 and use this definition in step
6.  The cycle and the `safe_cblock_first` reformulation are unchanged and
remain the bulk of the work.

## Step 3, fourth revision: a multi-item uniformity theorem dissolves the cycle

The cycle exists because `parse_cblock_pad` and the canonical-list
section are stated over `cblock`s and `cb_ok`, so each needs the other.
A list-level uniformity theorem stated purely on *lines* mentions neither
and so depends on neither:

```coq
parse_lines (list_lines sp (map (indent_lines bullet_open bullet_cont) itemss))
            (PPara [])
= [mk (BulletList (spacing sp itemss)
        (map (fun L => parse_lines L (PPara [])) itemss))]
```

with

```coq
spacing sp itemss =
  if existsb (lines_loose false false) itemss
     || (sp is Loose && length itemss <> 1)
  then Loose else Tight
```

Validated on **7545 `(sp, itemss)` pairs** built from every generated
block's rendering at depth 2, in single-item, first-of-two and
second-of-two positions, by exact equality -- not a screen.  Zero
exceptions.  The spacing formula alone was checked separately and is
exactly `cb_ok`'s existing condition, which is the first evidence that
`cb_ok` had it right all along.

`parse_cblock`'s `CList` case then becomes: apply this theorem, then
rewrite each `parse_lines L (PPara [])` with the induction hypothesis.
No hypothesis threading, no parameterisation, and `parse_cblock_pad`
falls out of `parse_lines_pad_invisible` rather than needing its own
development.

This replaces step 4 of the previous order, which was the bulk of it.
The work becomes: prove `list_uniformity` in `Parser.v`, restating the
existing list section's lemmas over line lists instead of `cb_ok`'d
cblock lists.  Those proofs already run through `run_lines` and
`scan_list_content`; the `cb_ok` hypotheses are consumed only to
establish line-level facts (first line nonblank, last line nonblank, the
marker line not thematic), which become direct hypotheses.

Prerequisite: `indent_lines` and `list_lines` move from `Render.v` to
`Line.v`, beside `bullet_open`/`bullet_cont`.  They are layout
primitives, not renderer policy.

## `list_uniformity` is proved

`Parser.list_uniformity`, axiom-free:

```coq
Theorem list_uniformity :
  forall sp itemss,
    itemss <> [] -> forallb item_ok itemss = true ->
    parse_lines (list_lines sp (map (indent_lines bullet_open bullet_cont) itemss))
                (PPara [])
    = [mk (BulletList (list_spacing_of sp itemss)
             (map (fun L => parse_lines L (PPara [])) itemss))].
```

Not vacuous here: all 1509 canonical item renderings at depth 2 satisfy
`item_ok`, and `Generate.v` carries an instance whose first item is
itself a nested list.

Supporting lemmas, all in `Parser.v`: `run_item_open` and
`run_item_sibling` (the marker opens the list or closes the item in
progress), `step_blank_finish` (a loose list's inter-item blank leaves
the preceding item's parse unchanged), `lines_loose_or`,
`parse_item_and_tail`, `parse_list_tail`.

One asymmetry worth recording, because it cost a false start: the
separator count is one fewer than the item count.  `list_loose_of` is the
contribution of the items *after* the first, so its Loose case is "the
tail is nonempty"; `list_spacing_of` is the whole list, so its Loose case
is "there is more than one item".  A `Loose` single-item list emits no
separator and parses back `Tight`.
