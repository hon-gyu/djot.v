Respell the inline hole from `%{e}` to `` %`e` ``, the way djot spells
math as `` $`e` ``. This reverses D1 of [[261007.plan.holes]], which
weighed the backtick form and declined it on readability. The reasons
to reverse it came out of building the brace form ([[holes]]):

- **The brace hole is its own scanner candidate.** It carries brace
  depth, escape decoding, a second ordinary reading of the same bytes, a
  rule for who wins on overlap (D9), an attribute candidate nested in
  its ordinary reading, and frames in the candidate stack
  ([[261007.plan.candidate-stack]]) so that nesting stays linear. A
  backtick hole is a code span whose opening run was preceded by `%`.
  Code spans already commit at the backtick, so the precedence story is
  theirs.
- **Braces are common in host expressions.** OCaml records, Python dicts
  and f-strings all use them, and each unbalanced one needs `\}` today.
  Backticks are rarer, and a longer backtick run handles them without
  escapes.
- **The extension gets a one-line theorem.** Turning holes on changes
  some `%`-prefixed code spans into holes and nothing else (step 5).
- **A smaller loud subset.** The brace form changed every `%{`,
  including `50%{.c}` (attributes on a word). The backtick form changes
  only `%` directly before a backtick.

## Decisions

Agreed in conversation, 2026-10-09. They replace D1 to D11 of
[[261007.plan.holes]] where they overlap. D11 carries over almost
unchanged.

**E1. Spelling.** A hole is `%` directly followed by a code span:
`` %`e` ``, ``%`` e ``%``. The payload follows the code-span rules
(djot's "Verbatim"): any run length, and one space is trimmed on each
side when the content starts or ends with a backtick.

**E2. An unclosed hole runs to the end of the paragraph,** as an
unclosed code span does. This reverses D9 ("a hole is always closed").
There is no second reading and no overlap rule: whichever opens first
wins, which is the existing rule for code spans.

**E3. No escapes inside.** Backslashes are kept as written, as in a code
span. D7 is deleted along with `hole_text` and `hole_src`.

**E4. An empty payload is a hole,** for the consumer to reject (D6 as
amended). ``%`` `` is `Hole ""`.

**E5. A raw suffix is not part of the hole.** `` %`x`{=py} `` is a hole
followed by the text `{=py}`, as for math (`vkind_verb` is false for the
new kind). Tagging a hole with a language could be added later without
breaking anything. Until then, `` `x`{=py} `` is the long form.

**E6. Attributes attach,** as they do to code and math:
`` %`x`{.c} `` is a hole with class `c`. This matches the existing
`hole_attributes` example.

**E7. `\%` writes a literal `%` before a code span.** The canonical
renderer escapes `%` in text while holes are on, as `needs_escape`
already does. Escaping only a `%` before a backtick is left to
[[261007.plan.irredundant-escapes]].

**E8. One kind, and no kinds planned.** D5's `%*{` and `%?{` are
dropped rather than respelled: `` %*` `` would cut into strong emphasis
(`` %*`x`* `` is `%` then strong code today), and a sigil of more than
one byte makes the scanner and its proofs harder. Nothing is reserved;
`` %*`x` `` and `` %?`x` `` read as they do today. A consumer that wants
a list or an option takes one fragment value and offers `of_list` and
`of_option`, as D5 already said (decided in conversation, 2026-10-09).

**E9. The block hole is a raw block in format `hole`.** The consumer
convention moves from D10's ```` ``` % ```` code block to djot's
existing raw block, ```` ``` =hole ````. The parser already reads that
as raw, not code, which keeps blank lines and indentation, and it pairs
with E10's inline form. The parser does not change.

**E10. Desugaring belongs to the consumer.** The kernel keeps `Hole s`.
That keeps E11's HTML visible and step 5's theorem clean. The OCaml
library gets a pass that rewrites `Hole s` to `RawInline "hole" s`. A
consumer then sees one shape, `RawInline "hole"` or `RawBlock "hole"`,
and `` `x`{=hole} `` written out is a hole too. Desugaring in the kernel
was rejected: a renderer drops a raw inline in a format it does not
know, so an unevaluated hole would vanish from HTML without notice.

**E11. HTML.** `<code data-hole="">s</code>`, carrying the node's
attributes, as today.

**E12 (later phase). A configurable sigil.** See "Phase 2".

**E13. A hole's text is its expression,** as math's is its formula.
`reference_text (Hole s) = s`, so `` # Total %`n` `` gets the id
`Total-n` and `` [%`n`][] `` looks up the label `n`. This reverses the
choice at `InlineTable.v:878` (a hole contributes nothing).

## The refinement theorem

The theorem says what E1 promises: turning holes on only turns some
code spans into holes. Let `unhole` rewrite every `Hole s`, attributes
and all, to the text `%` followed by `Verbatim s` with the same
attributes, and merge adjacent text. Then, for every table `C` that
holes do not conflict with (the existing condition: no row uses `%`),

    unhole (parse_inlines (with_holes true C) s)
      = parse_inlines (with_holes false C) s

The statement may need the normalization `Readable.v` already uses for
merged text. It is a statement about inline trees.

**At the document level it holds with one caveat.** Identifiers and
empty-reference labels are computed from `reference_text`, and a hole
follows math there (E13): `Hole s` contributes `s`, as `Math _ s` and
`Verbatim s` do. With holes off, the same source contributes `%` then
`s`. Where that `%` matters, the two differ:

| input | holes off | holes on |
| --- | --- | --- |
| `` # a %`x` `` | id `a-x` | id `a-x` (the space already separates) |
| `` # a%`x` `` | id `a-x` (`%` separates words in an id) | id `ax` |
| `` [a %`x`][] `` | label `a %x` | label `a x` |

So the document theorem is stated after `unhole` with identifiers and
empty-reference labels recomputed from the unholed inlines; it is the
inline theorem lifted through the block structure. Making the
difference vanish would take `Hole s` contributing `%` ++ `s`, which is
not how math reads and was declined in conversation (2026-10-09).

## Phase 2: a configurable sigil (E12)

Make the sigil a parameter of the setting, `ext_holes : option ascii`,
with a validity predicate, and state every theorem above for each valid
sigil. A valid sigil:

1. is ASCII punctuation, so that `\c` escapes it and the renderer can
   write a literal one;
2. means nothing before a backtick and opens no candidate. That excludes:
   - `` ` `` and `\`
   - `$` (math)
   - the emphasis family `* _ ^ ~ = + -`. For example, `` *`code`* `` is
     strong code today.
   - `[ ] ! < { } :` (links, images, autolinks, attributes, symbols,
     custom tags)
   - `|` (table rows)
   - `'` and `"` while smart quotes are on
3. is outside the inline table's alphabet, as `in_alphabet` requires of
   `%` today.

That leaves roughly `% & @ # ; ?`. Each profile has exactly one sigil,
and `{=lang}` covers languages. The sigil is one byte (E8).
