# Plan: replacing a node without reparsing the rest

## 0. Goal

A consumer holds a parsed document and its source.  It replaces the
source of one node with new text.  The guarantee wanted: the tree of the
edited document is the old tree with that node swapped for the parse of
the new text, so nothing outside the node is parsed again.

How the consumer finds the node (an id, a path, a selector) is not part
of this plan.  Every scheme ends at a position in the tree, and the
statements below are about the position.

## 1. Where things stand

Read at `bbb2773`.

Proved:

- **Text edit at top level.**  `Uniformity.reparse_only_new`: for lines
  `pre ++ old ++ post`, if `new` leaves the parser in the state `old`
  did, the parse of `pre ++ new ++ post` is the old blocks of `pre`, the
  blocks of `new`, and the old blocks of `post`.  No condition on the
  document.  `reparse_only_new_idle` is the form to run: both `old` and
  `new` end idle (`PPara []`).  `reparse_state_matters` shows the
  condition is needed.
- **Containers parse like the top level.**  `quote_uniformity`,
  `div_uniformity`, `list_uniformity` and their variants.  In
  `list_uniformity` each item's blocks depend on that item's lines only;
  the list shares the marker check and one spacing flag.
- **Tree edit, any depth, canonical trees.**  `Roundtrip.roundtrip_blocks`
  and `block_replace`, with `Address.replace_at_id_parse` on top.  This
  is for a tree built without text: it must be one that some text parses
  to (`cblocks_ok`).  A list placed next to a list is refused by
  `cb_pair_ok`.

Not there:

- The extracted library (`dist/src/djot.mli`) exposes no parser state
  and no `run_lines`, so a consumer cannot run the check.
- The theorems are about `parse_blocks`.  `Document.parse_doc` is
  `doc_pass (parse_blocks s)`, and the pass assigns heading ids,
  nests sections, collects footnotes and reads reference definitions
  over the whole block list.
- The theorems are about the tree without locations.  Spans in `post`
  move when the edit changes length.
- Nothing about an edit inside a container on the text side, and nothing
  about inline nodes.

## 2. Steps

Steps 1 to 3 make the existing top-level theorem usable and true for the
whole document.  Steps 4 and 5 make edits cheaper; each has a correct
fallback without them.  Step 6 is only needed if nodes are built without
text.

### Step 1. Export the check

Give the extracted library an entry point that takes the old lines and
the new lines of a top-level region and answers whether both end idle,
and one that parses the new lines alone.  A region is whole top-level
blocks, so `pre` ends idle by construction.

To decide: whether to expose `pstate` as an abstract type so a consumer
can save states at block boundaries, or to keep the idle form only.  The
idle form needs no saved state and covers every edit that starts and
ends at a block boundary.  Start with it.

Without this step no consumer outside Rocq can use the guarantee.

### Step 2. The document pass

`doc_pass` runs after `parse_blocks` and never inside the fold, so the
plain answer is: splice the block lists, then run `doc_pass` again over
the result.  It reads the tree, not the text.

State it as a theorem: under the step 1 condition,
`parse_doc (pre ++ new ++ post)` is `doc_pass` of the three block lists
appended.  This follows from `reparse_only_new` by unfolding.

Then record what the pass can change outside the edited node, so a
consumer knows what to refresh:

- a heading added or removed can renumber a duplicate auto id elsewhere
  and move section boundaries;
- a reference definition added or removed changes how links elsewhere
  resolve;
- a footnote definition added or removed changes the note map.

To verify before starting: whether a consumer needs to splice into the
tree after `doc_pass` (sections nested, footnotes removed) and not
before.  If so, the statement needs the block list from before the pass
to be recoverable, or kept alongside.

Without this step "the rest is unchanged" is false in those three
cases, with no signal.

### Step 3. Spans after the edit

The located parse is `parse_blocks_located`, and it erases to
`parse_blocks`.  State what happens to the spans of `post` when `new`
has a different length than `old`: each is the old span shifted by the
line and byte difference.  Spans in `pre` are unchanged.

To verify before starting: whether the located fold records absolute
line indices in its state.  `260916.plan.source-locations.md` mentions
states that differ in recorded line indices, which would affect how the
state comparison in step 1 is stated for the located parse.

Without this step a consumer that keeps spans has to recompute them for
everything after the edit.

### Step 4. Text edit inside a container

Extend the text-edit statement to a region inside a quote, div, callout
or list item, one container at a time, from the uniformity theorems.
Side conditions come from those theorems: `quote_header l = None`,
`div_content_ok`, and for lists `items_ok` plus a recomputed spacing
flag.

Fallback without it: treat the enclosing top-level block as the edited
region.  Correct, slower.

### Step 5. Inline edits

Nothing is proved about replacing one inline node in a paragraph.
Find out first what `InlineInvert.v` and the inline uniformity results
give; an inline container's content does not in general parse the same
alone as in place, since delimiters pair across it.

Fallback without it: replace the enclosing paragraph.

### Step 6. Tree edits without text

Only if nodes are constructed in code and inserted.  Otherwise drop.

- Replace the refusal in `cb_pair_ok` with a statement of the result: a
  function saying what two adjacent blocks become, and a theorem that
  parsing the concatenated source equals the two trees joined by it.
  `block_replace` is the case where the function does nothing.
- `cb_pair_ok` refuses any list followed by any list.  Lists with
  different markers do not merge (`list_different_types_split`), so the
  condition can be narrowed.  Check that no other proof relies on the
  wide form.
- A statement that after a nested replacement, `cblocks_ok` of the new
  tree reduces to checks at the node and on the containers along the
  path.

## 3. Done when

- A consumer of the extracted library can replace a top-level region,
  run the check, and get the edited document's tree without parsing
  `pre` or `post`, with a theorem naming that tree (steps 1 and 2).
- What the document pass can change elsewhere is listed and each item
  has a theorem or a counterexample (step 2).
- Spans after the edit are stated (step 3).
- Steps 4 to 6 are each either done or recorded as not needed, with the
  fallback named.
