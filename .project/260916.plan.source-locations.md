# Plan: source locations

## 0. Goal

Give the extracted parser optional source locations on every node it
builds, block and inline, and on the parts of the AST that are not nodes
(list items, definition-list terms and definitions, table rows, cells and
caption).  The parser is meant to be general, so no consumer's needs set
the scope.  One consumer's needs set the order (§1).  Parsing without
locations stays available and stays the thing every existing theorem is
about.

The semantic boundary:

```coq
erase (parse_blocks_located s) = parse_blocks s
```

and likewise after the document pass.  Locations describe one parse of
one buffer.  They are not identities, not part of canonical AST equality,
and not reproduced by rendering a node alone.  `cb_ast`, `cblock`,
`cinline` and `roundtrip_blocks` do not change.

This refines `260902.document-model.md`, which rules positions out of the
AST because they would break `roundtrip_blocks` as an equality.  That is
true of `cb_ast`.  It does not rule out a located parse that erases to the
semantic one.

## 2. Baseline (verified 2026-09-19)

- `Ast.pos` is `NoPos | SomePos sl sc el ec`.  Nothing constructs
  `SomePos`.  `mk` is `Node NoPos []`.
- `Document.v`'s id pass already threads `p` through unchanged
  (`Node p a ...` in every arm of `assign_ids`), so it preserves child
  positions as written.  Synthesized `Section` is built with `NoPos`.
  `add_ref` takes a `pos` and discards it.
- `split_lines` splits on LF only.  CR stays in the line and is treated
  as whitespace.  Extraction replaces it with a native definition.
- `String.length` extracts to a native length followed by a unary
  conversion: O(n) allocation per call.

### F1. djot.js reports positions and is the range oracle

`djot.js --sourcepos` and `parse(src, {sourcePositions: true})` attach
`pos` to every node but `doc`, and `djot.js/test/sourcepos.test` holds a
case the harness currently skips.  The parser downstream uses today is a
different parser with a different AST, so its spans are comparable only
where the trees agree.  djot.js decides node ranges, as it decides
behaviour; downstream's needs decide which ranges we must expose.

`harness/oracles/djotjs-sourcepos.mjs` prints djot.js positions as 0-based
half-open byte ranges with the covered source; `--trim` drops a block's
trailing newline.  Raw djot.js conventions it normalizes away:

- `line:col:offset`, `col` 1-based, `offset` 0-based, end inclusive;
- offsets and columns count UTF-16 code units: `é *ü* x` puts `strong` at
  offset 2, byte 3;
- a block's end usually lands on its own newline, reported as the next
  line's column 0; at end of input without a newline it points one past
  the last byte.

### F2. The block parser stores only suffixes of its input lines

Every string a `pstate` keeps for later reading (paragraph, heading and
caption lines, fence content, attribute slices) is a suffix of the line
being stepped, with nothing trimmed at the end: 1054 of 1054 state/line
pairs in the probe pool.  So a stored string's column needs no field.
It is `length l - length t`, or, without knowing `l`, "`length t` bytes
before the end of its line".

Exceptions found:

- table cells are trimmed infixes: 16 failures, all on `| a |`.  The row
  scanner has to record where each cell starts;
- the key label in `PKey` is an infix (from reading `key_close`; the pool
  has no keyed state);
- block metadata strings that are never inline-parsed (div class, fence
  info, reference label and destination, footnote label) are infixes, and
  only their block's span is needed;
- `iscan_lines` strips trailing whitespace from a paragraph's last line
  before scanning, so the inline layer must measure from the unstripped
  string.

### F3. Positions anchored at the end of the line survive container prefixes

Record a stored string's position as the pair *(line index, bytes from
this point to the end of that line)*.  Adding `> ` to every line,
`quote_uniformity`'s shape, leaves these pairs unchanged in 36 of 36
documents.  Columns change in 27 of 36.  Absolute offsets change on
every line after the first: `a` / `b` / `c` starts at bytes 0, 2, 4, and
under `> ` at 2, 6, 10.

This is the finding the design rests on.  Container prefixes are always
added on the left, and `step_fuel_pad`, `step_fuel_shift` and the
uniformity theorems all relate a line to the same line with something
prepended or with an offset shifted.  A coordinate measured from the right
does not see either change, so none of those statements acquires a shift
map over located data.  The first draft's slices of absolute byte ranges
would have made every uniformity statement false for the located parser.

Absolute bytes are recovered at the API from a line table:
`byte = line_start k + line_length k - r`.

### F4. Stored lines are not consecutive source lines

`{#i` / `   ` / `  <}` steps to `PPend [] (PParaOff 2 ["<}"; "{#i"])`:
lines 0 and 2, with the indented blank fed to the spec but not recorded.
So one start index per state cannot recover each stored line's index.
Each stored line needs its own line index.

(The same input yields an empty document in djot.js.  That is the known
blank-spanning-spec divergence and is not a location question.)

### F6. Our inline AST merges what djot.js splits

`para_inlines ["a\*b \"q\" -- x..."]` is `Str "a*b "`, `Quoted [...]`,
`Str " – x…"`; `it's` is one `Str "it’s"`.  Escapes and smart punctuation
consume their source bytes in place, so a merged `Str`'s source is
contiguous and its span is the hull.  Differential comparison with
djot.js on inlines is by hull over adjacent text nodes.

### F8. Located inline scanning is concentrated in a few places

The inline scanner has 18 `iscan` constructors, but they share one
`ostate`.  Node construction goes through 29 sites in definitions (of 365
`mk (` occurrences in `Inline.v`; the rest are in statements and proofs).
Statement counts for the pieces a located scanner changes:

| Symbol | occurrences | statements naming it |
| --- | --- | --- |
| `flush_text` | 195 | 23 |
| `OIn` | 74 | 13 |
| `OState` | 59 | 6 |
| `istep` / `istep_at` | 55 / 62 | 5 / 2 |
| `Frame` | 14 | 1 |

So the located scanner needs a text-run start `spot` in `ostate` and an
opener `spot` in `frame`.  If the current byte's `spot` comes from a
`Context` the way F5 does it for lines, `istep`'s own statements do not
change and only the scanning driver varies it.  A text run's stop is the
spot where it is flushed, so `flush_text` either takes the spot as an
argument (23 statements) or reads it from the same `Context`.

One place needs more than a start and a stop.  `oattach_list` splits a
merged `Str` at its last whitespace to attach an inline spec to the last
word.  The split point is computed on the *value*, and escapes and smart
punctuation make value offsets differ from source offsets.  The pending
text therefore has to remember the spot after its last whitespace byte,
carried on `OIn` inside the scanner and never in the AST.

While checking this, `a b\*c{.x}`, `a b--c{.x}` and `a b'c{.x}` turned out
to attach differently from djot.js, which stops the word at an escape or
smart-punctuation token.  Logged in `oracle-disagreements.md` (2026-09-19)
as open.  The spot that records the last whitespace would also be where a
fix records the last token boundary.

### F9. Several AST parts that djot.js positions are not nodes

List items (`list (list (node block))`), task items, definition-list
terms and definitions (`inlines * list (node block)`), table rows
(`list cell`), cells (`Cell ct al ils`) and the caption (`option inlines`)
have no `node` wrapper, so no `pos`.  Two ways to position them:

- make them nodes.  This changes the semantic AST, and with it `Html.v`,
  `Render.v`, `Roundtrip.v`, the canonical view and the generator;
- keep the AST and put their spans in the parent's provenance, as a
  structure parallel to the children (§4.2).

The second leaves every semantic statement alone and erases trivially.
Choose it.  Items becoming nodes, if wanted, is a separate AST decision
with its own reasons.

### F10. Erasure reaches the inlines, and one statement covers both sides

Once a paragraph's nodes carry spans, `erase_block` can no longer leave
inline trees alone, and `erase_blocks (parse_blocks_located s) =
parse_blocks s` is false until it does.  Making it deep then asks for two
different facts: that the located scan erases to the semantic reading,
and that the semantic reading is *itself* position-free -- the second
wherever a paragraph is still built by the ambient instance (`key_close`
retracting a key to its own line).  The second looks like a separate
invariant over the whole inline state.  It is not: stating the first
uniformly in the policy,

```coq
Theorem para_inlines_at_erase : forall `{P : PosPolicy} off l,
  erase_inlines (@para_inlines_at P off l) = para_inlines_off off (map snd l).
```

reads at `located_pos` as the refinement and at `semantic_pos` as
`erase_inlines (para_inlines_off off ls) = para_inlines_off off ls`,
which is the second fact.  One theorem, and the identity falls out of the
instance.

The reach of the deep traversal is what the located parse produces and
nothing more: a paragraph's and a heading's inlines, and a definition
term, which is a paragraph's.  A table's cells and caption and a keyed
block's label are still the ambient instance's, and deepening their arm
would oblige exactly the invariant the uniform statement avoids.  Each
becomes deep when its own layer does.

### F11. A text run stops where its interrupting construct starts

The located driver is cheap and correct: `iscan_str_located` counts
`spot_rem` down from one `String.length` per line, `iscan_lines_located`
steps each line at its own index with the break between them, and
`para_inlines_at` dispatches on the policy so that the semantic
paragraph is the same term it was.  Block-level coordinates come out
exact.

What is not in place is the scanner's own arithmetic.  Every
accumulating state -- `IDelim`, `IOpen`/`IVerb`, `IDollar`, `IPeriod`,
`IDash`, `IAuto`, `IRaw`, `IAttr`, `IEscWs` -- holds the pending text
*and* a token whose role a later byte decides, so the flush that emits
that text happens one or more bytes after the text ended.  It uses the
cursor it is dispatched at, so the `Str` swallows the token.  The same
byte is why a verbatim's node is built with no position at all and why a
delimiter frame's opener span starts after its run.

Two repairs, and which applies is a property of the construct, not of
the site.  A token that cannot cross a line break -- a delimiter run,
smart punctuation, an autolink region, a raw spec -- can have its start
recovered from the cursor by `spot_before`, which is the idiom already
in the file.  A token that can -- a verbatim's content -- cannot.

A flush is deferred exactly when it is triggered by resolving one of
those states, and at the line and paragraph boundaries it is not, so
`flush_text_at` (stop at the cursor) and `flush_text_to_at` (stop
given) already spell the distinction.

*Repaired (2026-09-21).*  The second case needed no new state after all,
and the reason generalizes.  A construct's start is the stop of whatever
its scope emitted last, because the flush at the construct's first byte
put it exactly there -- which is `text_start`, the function the text
runs already use.  So a verbatim reads its own start off the scope and
crossing a break costs nothing, `IOpen`/`IVerb`/`IRaw` keep their
fields, and the 83 mentions those three would have cost are not spent.
The same reading gives an abandoned opener its range (`fr_lit`) and
makes `oclose` carry the matched frame's opener span.

One correction fell out of it: the text after an attributed node starts
after the node's *spec*, not after the node, since the spec is recorded
as a role and is not part of the range.  `node_stop` looks past the
roles now (`roles_stop`).

## 4. Representation

### 4.1 Internal coordinates

```coq
(* A point in the source: a line index, and the bytes from the point to
   the end of that line (newline excluded).  Measured from the right so
   that prefixing a line, or shifting its offset, does not move it. *)
Record spot : Type := Spot { spot_line : nat; spot_rem : nat }.

Record span : Type := Span { span_start : spot; span_stop : spot }.
```

Half-open: `span_stop` is the first point after the construct.  A block
ending at the end of line `k` stops at `Spot k 0`.

### 4.2 Provenance on a node

```coq
Inductive syntax_role : Type :=
  | RAttrSpec      (* one authored attribute spec *)
  | ROpenFence     (* a div's or code block's opening line *)
  | RCloseFence.   (* its closing line, absent when input ended first *)

(* Spans of the AST parts that are not nodes (F9), parallel to the
   children they belong to. *)
Inductive parts : Type :=
  | PNone
  | PItems (items : list span)                      (* list and task items *)
  | PDefItems (items : list (span * span * span))   (* item, term, definition *)
  | PTable (caption : option span) (rows : list (span * list span)).

Record provenance : Type := Provenance {
  node_span : span;
  syntax_spans : list (syntax_role * span);
  part_spans : parts
}.

Inductive pos : Type := NoPos | SomePos (p : provenance).
```

`ROpenFence` and `RCloseFence` are here because a downstream feature
reads them (§1).  Add a role only when something reads it.  `parts` is
not a role list because its shape follows the children's, which lets a
consumer pair item `i` with its span without searching.

### 4.3 API coordinates

The public located entry points convert `spot`s to 0-based half-open byte
offsets with a line table built once from the input.  Line numbers are
available from the same table.  Columns are bytes; converting to UTF-16
is downstream's business, and it already does it.

### 4.4 Range rules

From F1, with ours differing where djot.js's rule is an artifact:

- a node covers its construct from the first byte of its opener or first
  content byte to the last byte of its closer or content, excluding the
  line ending that separates it from what follows;
- a container starts at its own marker (`>`, `-`, `:::`), not at column 0
  and not at the enclosing container's prefix;
- attached attributes do not widen `node_span`.  Each authored spec is
  one `RAttrSpec` entry, in source order;
- a merged `Str` covers the source bytes that produced it, escapes and
  smart-punctuation sequences included, and an interior line's trailing
  spaces, which stay in the `Str` (F6);
- `SoftBreak` covers its line terminator.  `HardBreak` covers the `\`,
  any whitespace after it, and the terminator.  Internally a break stops
  at `Spot k 0`; the API extends a break node, and only a break node, by
  line `k`'s terminator, which the line table knows;
- `NonBreakingSpace` covers the `\` and the space.  `Symbol`, `Math`,
  `Verbatim`, `UrlLink`, `EmailLink` cover their delimiters; `RawInline`
  also covers its `{=fmt}`; `Image` starts at its `!`;
- `Section` is built by the document pass, not from a line, and gets the
  hull of what it encloses: from its heading's start to its last child's
  stop.  It has a source region, so this is not an invented span, and it
  agrees with djot.js;
- list and task items span from their marker to their last content;
  definition-list terms span their inline text, definitions their first
  to last block; table rows span the row line, cells from their leading
  `|`, the caption from its `^` (all in `parts`);
- a reference definition ends at the end of its last continuation line.

## 5. Architecture

One grammar, two observations.  No second `step`, no reparse of the
finished AST.

1. **Index.**  `Class LineIx := { lix : nat }` joins `T` and `K` as a
   `Context` in every `WithTable` section.  `step` reads `lix` only to
   tag what it stores.  `parse_lines` keeps using the ambient instance,
   which leaves every statement in F5's count unchanged; the located
   driver `parse_lines_located` passes `{| lix := i |}` for line `i`.
2. **Stored lines.**  The line lists in `PPara`, `PParaOff`, `PHeading`,
   `PFence`, `PAttr` and `TCaption` hold `(nat * string)`, line index
   and suffix (F2, F4).  The column is the suffix's length and is not
   stored.
3. **Container starts and ends.**  Each container state records the
   `spot` of its marker at open and the `spot` of the last line it
   claimed; a list does the same per item, and a table per row.  Div and code fence states record whether and where their
   closer was seen.  All are end-anchored, so `pad_state` leaves them
   alone and F3 says `step_fuel_pad`/`step_fuel_shift` stay true as
   stated.
4. **Positions on output.**  Block and inline constructors go through
   one function, `Class PosPolicy := { mkpos : provenance -> pos }`.  The
   semantic instance is `fun _ => NoPos`, so under it `Node (mkpos p) [] x`
   reduces to `mk x` and the canonical theorems see the ASTs they see
   today.
5. **Inline.**  The scanner receives `(line, suffix)` pairs.  Each
   byte's `spot` reaches `istep` through a `Context`, the pattern of
   step 1 one level down (F8): the semantic `iscan_str` keeps the ambient
   instance, and the located driver counts `spot_rem` down from the
   unstripped line length, not by `String.length` per byte (§8).
   `ostate` gains the pending text's start and the spot after its last
   whitespace byte; `frame` gains its opener's spot.  Every inline node
   then has a span: a text run from its start to where it is flushed, a
   construct from its opener to its closer, a break from the end of its
   line's content.
6. **Merging.**  `osnoc`/`isnoc` merge adjacent `Str` nodes; the merged
   span is the hull of two adjacent spans.  `oattach_list`'s word split
   takes the recorded spot after the last whitespace as the attached
   word's start (F8).
7. **Parts.**  `table_row` records each cell's start as bytes to end of
   line (F2).  List closing (`list_block`, `def_items`, `task_items`)
   builds `PItems`/`PDefItems` from the per-item spots of step 3, and
   `table_block` builds `PTable` from the per-row and per-cell spots.
8. **Document pass.**  Already position-preserving (§2).  `Section`
   gets the hull of its children (§4.4).  `add_ref` keeps the
   definition's span for the located result.

What this costs the semantic development, to confirm at C1:

- `pstate` constructors with a changed field: every statement or proof
  that writes one of them with explicit arguments;
- the erasure lemma for `step` (F7) and for `para_inlines`;
- in `Inline.v`, the statements naming `ostate`, `frame`, `OIn` or
  `flush_text` (under 50, F8), if their fields are written explicitly;
- nothing in the uniformity or roundtrip statements, if F3 and F5 hold
  under a real build.

What the location-off parse carries that it does not need: one `nat` per
stored line and a few `spot`s per open container.  Accepted in exchange
for a single `step`; measured at C3.

through the extracted `--convert` takes 0.31 s before and after.

*Outcome of step 3's elaboration probe (2026-09-20).*  Twenty lines
decided it before any parser file was touched.  `Node (mkpos p) [] x`
reduces to `mk x` at the semantic instance, `vm_compute` goes through an
instance and through a fixpoint defined under an abstract one, and an
`mk`-shaped statement written *inside* a section with `Context {P :
PosPolicy}` is refuted -- which is the real content, because it says
where each statement has to live.  A file that opens no policy context
resolves `mkpos` to the semantic instance silently, so the semantic
equational theory stays where it is (`Uniformity.v`, `Wf.v`,
`Roundtrip.v`, `ListUniformity.v`) and only `Step.v`, whose section
carries the policy, states anything uniform in it.  `Check @thm` is the
test and it reports what it should: `step_fuel_pad` carries `P`,
`finish_wf` and `roundtrip_blocks` do not.

**C2. Erasure for `step`.**  State and prove
`erase_state (snd (step l st)) = snd (step l (erase_state st))` and the
same for emitted blocks, with the located and semantic policies.
*Falsifier:* a branch whose case does not close by rewriting.  That would
mean a decision reads a location, which §5 rules out.  *Budget:* F7's
388 lines.

*Outcome (2026-09-20).*  Not falsified: no branch of `step_fuel` reads a
location, and every case closes by rewriting erasure through the
constructors it builds.  `step_fuel_erase` is ~180 lines, under budget,
because the per-state helper lemmas (`list_*_erase`, `feed_lazy_erase`,
`key_claims_erase`, `close_reopen_*_erase`) carry work that
`step_fuel_shift` does inline.

Erasure turned out to have *two* halves, and the second was not in the
plan.  `run_lines_tagged` steps each line at its own `LineIx` while
`parse_lines` steps every line at the ambient one, so the two runs reach
states that differ in the line indices they recorded -- and no theorem
about positions alone can bridge that.  The repair was to make
`erase_state` forget the coordinates too, setting every `spot_line` to
what `semantic_line_ix` would have written, and to point the statement's
right-hand side at the ambient instance:

```coq
erase_result (@step_fuel T K LI located_pos n off l st)
= @step_fuel T K semantic_line_ix semantic_pos n off l (erase_state st)
```

That is one induction rather than two, and the extra cost was a dozen
one-line lemmas saying each coordinate constructor is the ambient one
erased (`erase_open_extent`, `erase_touch_extent`, `erase_push_text`,
`erase_remember_line`, `erase_line_texts_rev`), plus the same rewrites
threaded through `finish_erase` and the openers.

`parse_blocks_located_erase : erase_blocks (parse_blocks_located s) =
parse_blocks s` follows, closed under the global context.  The general
form is worth keeping: *a refinement whose two sides run under different
instances of a parameter has to erase that parameter's trace as well as
the data it was introduced for.*  Nothing about the positions says so --
the tell was that the theorem could not be composed into a statement
about whole documents.

**C3. Location-off cost.**  `extracted-performance.md`'s inputs, before
and after C1.  *Falsifier:* a regression beyond noise on the 16x input.

*Outcome (2026-09-20).*  Block spans landed before C2 rather than after
it, because C2's cost depends on how the policy reaches the output and
that was the thing to settle first.  Positions are attached by
`set_pos`, a wrapper over the node a helper built, rather than by a
provenance argument on each of the thirteen block constructors: the
argument would have cost ~180 mention edits across five files, the
wrapper costs none, because `set_pos` tests `mkpos p` before the node
and so is the identity at `semantic_pos` for an arbitrary node *by
conversion*.  What it does cost is ~25 tactic lines: `rewrite` is
syntactic, so a proof that reduces a closing arm and then rewrites needs
`nopos` to see through the wrapper.  All the spans are read off state
that C1 already recorded, except a heading's marker, which needed an
extent on `PHeading`.

Agreement with `djotjs-sourcepos.mjs --trim` on the shapes checked so
far (heading, paragraph, quote, div, bullet list, and the blocks nested
in each) is exact.

**C4. Inline positions on the hard witnesses.**
`> - a [link](dest){.c}`, a paragraph spanning a soft break inside
emphasis, `a b\*c{.x}` (a word split after an escape), a failed opener
that decays to text, and a verbatim closed by end of line, against
`djotjs-sourcepos.mjs --trim`.  *Falsifier:* a node whose start or stop
is not available as a recorded spot when the node is built.  *Measure:*
statements edited in `Inline.v` against F8's counts.

*Outcome (2026-09-20, items only).*  List, ordered-list and task items
are `PItems` off the per-item extents the state already carried, and
agree with djot.js exactly on the four shapes tried.  A definition
list reports its item whole for now.  The falsifier did not fire for
items: every one of them is read off the state that closes the list.
Table rows and cells have not been tried, and are the case the
falsifier is really about -- a cell is a trimmed infix (F2), so the row
scanner has to record where each cell starts, which changes `trow` and
therefore what `cb_ast` has to determine.

*Outcome (2026-09-21, the paragraph scan).*  The falsifier fired, and
not on the case it was aimed at.  With the located driver in place
(F11) the block-level coordinates are exact -- a paragraph of plain
text agrees with djot.js byte for byte, under a container prefix and
across a soft break -- and every node built *after* an accumulating
scanner state is one token late:

| Input | djot.js | ours |
| --- | --- | --- |
| `para more` | str `[0,9)` | `[0,9)` |
| `> a b` / `> c d` | str `[2,5)`, break `[5,6)`, str `[8,11)` | `[2,5)`, break `[5,8)`, `[8,11)` |
| `a  ` / `b` | str `[0,3)`, break `[3,4)`, str `[4,5)` | same |
| `a *b` / `c* d` | str `[0,2)`, strong `[2,7)` | str `[0,3)`, strong start missing |
| `a b\*c{.x}` | str `[0,3)`, str `[4,6)` | `[0,2)`, `[2,9)` |
| `b\` / `c` (hard break) | str `[4,5)`, break `[6,7)` | str `[4,6)`, break `[6,7)` |
| `` v `code `` | verbatim `[2,7)` | no position at all |

The break's own span is a deliberate difference: ours runs to the start
of the next line's content, so it covers the terminator *and* the next
line's container prefix, because the node after a break reads its start
from the break's stop (`text_start`).  Narrowing it is an API concern,
not a scanner one.  Everything else in the table was F11, and is fixed.

*Outcome (2026-09-21, the inline nodes).*  Every row above now agrees
with `djotjs-sourcepos.mjs --trim`, and so do the constructs it did not
reach: reference and footnote references, spans, urls, math, nested and
intraword delimiters, a marked token with a spec after it, a verbatim
spanning a break or closed by the line, and the three decays (a
delimiter, a bracket and a destination that never close, each merging
into one text node whose range is the hull).  Two differences are ours
and are stated where they are pinned: an image starts at its `!`, and a
raw inline covers the `{=fmt}` that selects its format.  What the
falsifier asked -- a node whose start or stop is not a recorded spot --
is answered by `text_start`: the scope's last stop *is* the next
construct's start.  Cells are still untried and still the interesting
case.

**C5. Parts.**  A loose list with a nested list, a definition list, a
task list, and a table with a separator and caption.  *Falsifier:* an
item or cell whose span cannot be read off the state that closes it.

## 7. Implementation sequence

Ordered so that downstream gets something usable before the inline
layer, which is the expensive part.

1. **Coordinates and line table.**  `spot`, `span`, `provenance`, the
   line table, `spot`-to-byte conversion, and
   `map snd (split_lines_indexed s) = split_lines s`.
2. **C1 and C2.**  *(done 2026-09-20: `step_fuel_erase`,
   `finish_erase` and `parse_blocks_located_erase`.)*
3. **Located blocks.**  *(done 2026-09-20 but for the bounds: node
   spans, `ROpenFence`/`RCloseFence`/`RAttrSpec`, and fixtures in
   `dev/check/Located.v`.)*  `parse_blocks_located` with `node_span` on every
   block and `ROpenFence`/`RCloseFence`/`RAttrSpec` on the blocks that
   have them.  General erasure theorem; spans bounded by the input;
   child within parent where the AST nests them.
4. **Located document, blocks only.**  Headings with ids, block
   attribute anchors, divs with fences, code blocks, reference and
   footnote definitions.  This covers outline, block-level anchors,
   generated regions and command blocks from §1.  *(done 2026-09-20:
   `parse_doc_located`, `Section` hulls, and the heading's spec
   following its id onto the section.)*
5. **Located inlines.**  C4, then every inline node.  Links, images,
   references, footnote references and inline attribute anchors are the
   ones downstream reads first, so their fixtures go in first.
   *(in progress 2026-09-21: the scan is parameterized by a cursor
   (`6af682e`) and driven by one (`iscan_str_located`,
   `iscan_lines_located`, `para_inlines_at`), which makes a plain
   paragraph exact; the token starts of F11 are repaired and pinned
   against djot.js in `dev/check/Located.v` (24 shapes, exact but for
   the image's `!` and a raw inline's `{=fmt}`), and the scan is not yet
   wired into the block layer because the located inlines falsify C2
   until F10's theorem is proved.)*
6. **Parts.**  C5, then item, term, definition, row, cell and caption
   spans.  *(list, ordered and task items done 2026-09-20; term,
   definition, row, cell and caption open.)*
7. **Located document, complete.**  Link and anchor occurrence lists.
8. **Extraction and API.**  Separate location-on entry points, byte
   offsets and line numbers, fixtures from §9.

## 8. Performance

- Extracted `String.length` allocates a unary `nat` per byte of its
  argument.  Per stored line (once) this is fine; per scanned byte it
  would make each line quadratic.  The inline scanner counts `spot_rem`
  down from one length per line.  A predecessor allocates nothing.
- Line indices count up once per line in the located driver: one cell
  per line in total.
- Measure the semantic parse, the location-off parse after C1, and the
  located parse, next to the incumbent parser with locations on and off.

## 10. Non-goals

- Identity across edits.
- Lossless layout or a concrete syntax tree.
- Semantic changes while plumbing, including bare-CR line endings.
- Turning list items, rows or cells into AST nodes (F9).
- Per-key and per-value attribute spans.
- Matching the incumbent parser's AST shape or its wrapper nodes.
- Speeding up the parser.
