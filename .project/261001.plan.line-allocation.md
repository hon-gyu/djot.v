# Plan: allocation in line classification

## 0. Goal

Cut what the extracted parser allocates per line of input, and find out
whether that buys time.  The profile below says most allocation comes
from classifying a line, not from building the tree.  The plan is staged
so that a cheap change answers the time question before any proof work
starts.

## 1. Where things stand

Measured 2026-10-01 at `40e3d39`, `dist/` built with OCaml 5.4.1 release
profile, Apple Silicon.  Input is `djot.js/bench/readme.dj` joined 64
times (806527 bytes, 22080 lines).  Totals are exact (`Gc.quick_stat`);
shares are sampled with `Gc.Memprof` at rate 1e-4 over five runs and
attributed to the innermost frame in `dist/kernel`.

| | parse (`parse_doc`) | `Html.convert` |
| --- | --- | --- |
| time per run | 33 ms | 40 ms |
| allocated on the minor heap | 132 MB | 147 MB |
| promoted | 12.5 MB | 17.4 MB |
| minor collections | 63 | 71 |

That is about 160 bytes allocated per input byte, of which 9.5% survives
a minor collection.

Parse allocation by module: `Line` 37%, `InlineScan` 19%, `Strings`
17.5%, `Step` 17%, the rest 10%.

By kind:

- String copies (allocated through `Bytes`): 36%, 41 MB, about 50 times
  the input.  They are spread over the block recognizers at 1 to 4%
  each: `marker_shape`, `list_marker`, `foot_open`, `fence_open`,
  `quote_prefix`, `div_open`, `row_body`, `ref_open`, `attr_open`,
  `heading_open`.  Each matches the head of the line, and a native
  string match copies the tail (see "The mechanism" in
  [[extracted-performance]]).
- `Strings.drop_leading_ws`: 10%, the largest single site.  The
  realization's inner `go` is a closure over `s`, `n` and `ws`,
  allocated per call.  `Line.v` names `drop_leading_ws` 140 times; the
  sample works out to about ten calls per line.  The same closure shape
  in `count_run`, `thematic_count`, `take_while` and `indent_of` adds
  about 5%.
- The inline scanner: `ilead`, `istep_at`, `chunks_push`,
  `chunks_value`, `iscan_str` at 2 to 3% each, no dominant site.

What survives is the tree and the block state (`split_lines`' lines,
`Ast.mk`, `Step.list_content`, `Step.line_stop`).  None of the hot
recognizer sites survives.

The collector is not the cost.  With the minor heap at 32 MB and 256 MB
(`OCAMLRUNPARAM=s=4M`, `s=32M`) the parse time stayed within run-to-run
variation.  The remaining cost is writing 132 MB and copying 41 MB,
which this profile does not convert to time.

Cause, read from `Line.classify`: it tries up to eleven recognizers in
sequence, and each one strips leading whitespace and matches the head of
the line for itself.  `Step.step_fuel` calls `classify` from several
branches.

## 2. Steps

### Step 1. Allocation in the bench

Add an allocated-bytes-per-input-byte column to `make bench`, from
`Gc.minor_words` and `Gc.promoted_words` around the timed call.  It is
exact, needs no sampler, and works on the 5.2.1 switch the repo builds
with.  It makes each later step checkable and guards against
regressions.

The per-site ranking needs `Gc.Memprof`, which OCaml 5.0 to 5.2 do not
have.  The driver used for the numbers above was a throwaway in a
scratch directory, built against `dist/` under a 5.4 switch.  Whether to
keep one in the repo is decided after step 2: if the work continues, add
it under `test/` with a note that it needs 5.3 or later; if not, it
stays out.

### Step 2. Closures in the realizations, as the time test

In `extraction/ocaml/Extract.v`, give the inner loops of
`drop_leading_ws`, `indent_of`, `count_run`, `take_while` and
`thematic_count` their captured values as arguments, so no closure is
allocated.  No Gallina changes.  These are trusted realizations, so the
change gets the usual old-against-new differential check.

Expected: about 15% less allocation on the parse.  Measure time on
`readme.dj` x64 and the prose shapes in `make bench`, old and new in one
process.

Gate: if a 15% cut in allocation moves time by less than run-to-run
variation, allocation is not what the remaining constant factor is made
of.  Then stop here, record the result in [[extracted-performance]], and
take a time profile before planning anything else.

### Step 3. Classify once per line

Proved, no new trusted code.  Two parts, each useful alone.

- Dispatch on the first byte.  After leading whitespace, the first byte
  decides which recognizers can match: `>` a quote, `#` a heading, a
  backtick or `~` a fence, `:` a div or definition, `{` attributes, `[`
  a footnote or reference, `|` a table row, and so on.  Define
  `classify_fast` that reads that byte and runs only the recognizers it
  admits, and prove `classify_fast l = classify l`.  `classify` stays
  the specification; `Step` calls `classify_fast`, and existing proofs
  rewrite with the equation.  This follows `dstyle_at_fast_eq`.  A text
  line, the common case, then runs the list and table recognizers at
  most, not eleven.
- One classification per step.  Check whether `step_fuel` can reach more
  than one `classify l` for the same line, and if so bind it once, as
  was done for `finish` on `PList`.

To verify before starting: that every recognizer strips leading
whitespace first, so the dispatch byte is well defined, and which
recognizers each byte admits (ordered list markers start with a digit, a
letter or `(`).

Expected: most of the `Line` and `Strings` share, which is about half of
all parse allocation.

### Step 4. Not in this plan: offsets through the recognizers

Passing an offset, or extracting `string` to a slice, removes the tail
copies that remain and is also the fix for nesting depth on one line
(open item 1 in [[extracted-performance]]).  It changes every
realization and is its own plan.  Step 3 does not make it harder.

## 3. Done when

- `make bench` prints allocation per input byte.
- The step 2 result is recorded, with the gate's outcome.
- If the gate passes: `classify_fast` proved equal to `classify` with no
  admits or new axioms, the differential check and suites pass, and
  [[extracted-performance]] carries the before and after.

## 4. Notes

OxCaml's `zero_alloc` check was tried on the realizations first.  It
lists allocation sites without counts, flagged the same closures, and
could not rank them; the sampler did.  Not worth adding to the build.

memtrace 0.2.3 wrote a trace on OCaml 5.4.1 but its reader failed on it
(assertion in `location_codec.ml`).  `Gc.Memprof` used directly was
enough.
