# Plan: one traversal per pass (pilot on Document.v)

## Why

Making list items nodes ([[261003.plan.located-parts]]) touched about
390 places across 14 theory files and 9 users of `block_ind2`. Most of
those edits were not about lists. They were copies of the same
traversal:

- Every function over blocks writes its own inner `fix` loops for the
  block list and for each item shape (plain, task, definition), because
  the guard checker will not follow `list (node block)` through a
  separate definition.
- Each copy needs equation lemmas (`inner_go`, `blist`, `olist`,
  `deflist`, `tasklist`) whose statements repeat the loop body word for
  word, so they break in text whenever the loop changes.
- `block_ind2` takes five predicates (block, block list, items,
  definition items, task items), and every proof restates all five.

`Document.v` alone has about twelve such copies (`Ids`, `Refs`, `Notes`,
`Undo.pass`, `Pristine`). The goal is that the next change to a list or
table constructor touches a handful of places instead.

This also helps a later port to Lean 4: the structure that ports
(definitions, statements, lemma dependencies) gets smaller and more
uniform, and fewer proofs rest on unfolding inlined fixpoints by
conversion.

## Questions the pilot answers

Q1. Does the guard checker accept a pass written with `map` (stateless)
and with a generic accumulating map (stateful: `Ids`, `Notes`) instead
of hand-inlined `fix` loops?  `BlockShape.of_block` already recurses
through `map`, so the stateless case is expected to work.

Q2. If not, does `Equations` give the same definitions with generated
equation lemmas, at an acceptable cost in dependencies and extraction?

Q3. Can one induction principle replace `block_ind2`: "P holds of `b` if
it holds of every block among `b`'s children", with `children : block ->
list blocks` listing the blocks under a block, items' blocks included?

## Steps

0. **Probe Q1** in a scratch file, outside the build: a stateless map
   over blocks through `map`, and a stateful one through a generic
   `map_acc : (S -> A -> S * A) -> S -> list A -> S * list A`, both over
   every constructor. Record what the guard checker accepts. If it
   accepts neither, probe Q2 the same way.
1. **`children` and the induction principle** (Q3), in `Ast.v`, beside
   `block_ind2`. Prove it from `block_ind2`, so nothing else changes
   yet. Also `rebuild`-style lemmas only if step 2 needs them.
2. **Port `Refs`**, the smallest module: definition, equation lemmas,
   and its users (`collect_refs_erase`). Compare line counts and the
   number of lemmas before and after.
3. **Decide.** If step 2 removes the equation lemmas and shortens the
   proofs, port the rest of `Document.v` (`Ids`, `Notes`, `Undo.pass`,
   `Pristine`). If it does not, stop and record why.
4. **Only then** consider `Wf.v`, `Html.v`, `Render.v` and the shift and
   erase functions in `Ast.v`, one file at a time.

Tactic cleanup (generated hypothesis names, positional `inversion`
patterns, long `all: try solve` batteries) is not part of this plan.
It happens file by file, when a file is touched for other work.

## Results (2026-10-12)

Q1, yes, and more than asked.  The guard checker follows a recursive
call through a combinator that matches on the block, so a pass needs no
loop of its own:

- `fold_children f b acc` (`Ast.v`) folds `f` over the blocks right
  under `b`.  A read-only pass is one line:
  `of_block b m := add b (fold_children (fun acc n => ...of_block...) b m)`.
- A rebuilding pass works the same way through a combinator that takes
  the function for a child list, `rebuild (g : blocks -> S -> S * blocks)
  b st`, with state (`map_acc`) and with a `g` that changes the list's
  length (`flat_map`).  Probed, not in the tree.
- What the checker rejects is recursion over a list computed from the
  block, such as `fold_left ... (children b)`: `children` is for
  statements, `fold_children` for definitions, and `fold_children_spec`
  joins them.

## Further ideas, beyond the pilot

Not steps of this plan. Each is something the located-parts work ran
into, with an idea worth a probe of its own. Ordered by how much they
would have saved on that work.

### E1. Positions as a type parameter of the tree

What we saw: erasure (`Erase.of_block`), line shifting
(`Shift.of_block`), the shape projection (`BlockShape.of_block`) and
`drop_auto_ids` are each a full traversal of the tree, and each needed
rewriting when the constructors changed. Three of them change only the
position or the attributes and keep everything else.

Idea: make the annotation a parameter, `block (ann : Type)` with
`Node (p : ann) (a : attr) (x : A)`, and define one `map_ann`. Erasure
is `map_ann (fun _ => NoPos)`, shifting is `map_ann (of_pos d)`, and
"a shift is invisible to erasure" is map fusion, proved once. The
semantic parse could be the tree at `ann := unit`, which would replace
the `PosPolicy` instance and its "identity by conversion" arguments with
a type distinction.

Cost: a type change of the same size as located parts. Probe first on
`Ast.v` alone: define the parametric tree beside the current one and see
whether `Erase` and `Shift` and their lemma collapse as expected.

### E2. One copy of each located/semantic pair

What we saw: `table_fold` and `table_fold_located`, `cells_of` and
`cells_of_located`, and similar pairs make the same structural decisions
and differ only in which scanner they call. Each pair needs an erasure
lemma linking the two.

Idea: write the shared part once, parameterized by the scan (as
`posnode` is parameterized by the policy), so the link lemma becomes an
instance of one general one. Smaller than E1 and independent of it.

### E3. Examples that survive type changes

What we saw: about 140 literal trees in `dev/` and `theories/` examples
(`[mk [mk (Para [mk (Str "a")])]]`) had to be rewritten by a script for
this change, and nested ones by hand.

Idea: write examples with small builders (`para "a"`, `ul [[...]]`,
`row [...]`) defined once, as `para` partly is already. A constructor
change then touches the builders, not the examples. Cheap, and it makes
the examples easier to read.

### E4. Measure how far a change spreads

What we saw: the cost of a refactor was only known after doing it.

Idea: a throwaway script that adds a dummy constructor to `block` and
counts the files and proofs that stop compiling. Run it before and
after the pilot and after E1. It turns "more maintainable" into a number
we can compare.

### E5. A small Lean 4 spike

What we saw: which Rocq habits will hurt a port is a guess until
something is ported.

Idea: port `Ast.v`'s types, one traversal (erasure) and one lemma
(erasure commutes with shifting) to Lean 4. Lean handles nested
inductives and generates equation lemmas, so the spike shows which of
this plan's refactors matter for porting and which only matter for Rocq.
A day or two of work, kept outside the repository.

### E6. Which theorems are the results

What we saw: 222 `Theorem`s, mixing the results that matter (round
trip, well-formedness, uniformity, located refinement) with internal
steps. When checking that nothing was weakened, all 222 counted the
same.

Idea: mark the results (a naming convention or a single file that
restates them), so a refactor's check is "these hold, unchanged", and a
port knows its target. Internal lemmas can then change freely.

### E7. Strings behind an interface

What we saw: the parser computes on Rocq's `string` as a list of
characters, and proofs match on `String c s` / `EmptyString`. Lean's
`String` is not built that way, and the extracted OCaml converts at the
boundary.

Idea: state what the parser needs of strings as a small interface and
prove against it. Large, and only worth it if a port becomes real; E5
would show how much of the code depends on the representation.

### E8. Fewer tactics that depend on the goal's exact shape

What we saw: hypothesis names Rocq generates (`H1`, `H5` after
`inversion`), positional `inversion` patterns, `cbn` with hand-picked
unfold lists, and long `all: try solve [...]` batteries. They work, but
when one fails the error points at the wrong place, and the fix needs an
interactive session. They also do not port: Lean has no Ltac.

Idea: a short style note for new and touched proofs: name what
`inversion` produces, prefer rewriting with a named equation over
`cbn [...]`, one bullet per case where cases differ. Applied when a
file is touched, not as a sweep.

## Out of scope

- Porting to Lean.
- The parser's string representation (`String`/`EmptyString` pattern
  matching), which a Lean port would have to decide separately.
- Changing any definition's behaviour.
